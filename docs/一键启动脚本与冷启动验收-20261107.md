# 一键启动脚本与冷启动验收（2026-11-07）

> 目标：把"答辩/演示时要手动敲 8 条命令、还要记得先起 Redis 后起后端"这件事收敛成一条命令，
> 并且用**真的从零冷启动**的栈跑一遍全部 E2E，证明脚本拉起来的栈和手工拉起来的完全等价。

## 2. 脚本设计要点

1. **幂等**：先探端口再看健康端点，已在跑且健康的服务直接跳过；端口被占但健康不过则告警，不盲杀。
2. **健康门禁是内容匹配**，不是端口连通：`/actuator/health` 必须含 `UP`，`/api/ready` 必须含服务名，
   避免"端口起来了但应用是死的"假成功。
3. **环境注入**：统一从根 `.env` 读取；`Import-ProjectEnvironment` 用不区分大小写的 HashSet 去重
   （Windows 环境变量大小写不敏感，`.env` 里 `MYSQL_USERNAME` 写了两遍，不去重会让 `SetEnvironmentVariable` 抛异常）。
4. **代理归一化**：启动时清掉全部 `*_proxy`，只留 `NO_PROXY=127.0.0.1,localhost,::1`。
   本机代理曾把 `127.0.0.1` 的健康检查也劫持出去，导致服务明明活着却判定失败。
5. **可追溯**：PID → `.runtime\pids\<svc>.pid`，日志 → `.runtime\logs\<svc>-<时间戳>.log`；停止时按进程树杀（cmd → mvn → java）。
6. **失败即失败**：收尾时关键服务（mysql/redis/backend/knowledge/ai-service/frontend）任一未就绪，
   打印排查路径并以退出码 1 结束，不打印"完成"欺骗使用者。

## 3. 修复的三个脚本缺陷（都是写完就挂的那种）

| # | 缺陷 | 现象 | 修复 |
| --- | --- | --- | --- |
| 1 | `Clear-ProxyVarDuplicates` 在 `Write-Ok` 定义之前调用 | `$ErrorActionPreference='Stop'` 下第一行就抛 "无法识别 Write-Ok"，脚本直接退出 | 函数定义上移，调用移到动作分发处 |
| 2 | `-ExtraEnv @{ MYSQL_PASSWORD = $env:SMARTOPS_MYSQL_PASSWORD }` 取错变量名 | 拼出 `set "MYSQL_PASSWORD=" `，**把 .env 里 8 位真实口令清空**，后端退回默认 `root` 连不上库 | 改为 `$env:MYSQL_PASSWORD`；并新增 `Select-EnvTable` 过滤空值，空值不注入 |
| 3 | 环境变量用 `set "K=V" && ` 拼进命令行 | 口令含 `&`、`"`、`%` 时 cmd 解析错乱 | 改为父子进程继承：`Start-Process` 前临时设进程环境，创建后立即还原 |

另外把 ai-service E2E 的默认端口从遗留的 `8010` 改回项目约定 `8001`（与 `.env` 的 `AI_SERVICE_URL` 一致），
否则脚本每次都要额外设 `SMARTOPS_AI_BASE` 才能跑。

## 7. 已知限制

- **受管会话里的进程回收**：在 WorkBuddy/CI 这类把 shell 放进 Job Object 的环境里，脚本退出时
  子进程会被一并回收（实测：脚本报 9 个 UP、退出码 0，随后全部消失）。这是宿主行为，不是脚本缺陷。
  这类场景用 `-KeepAlive` 让父进程常驻即可。**用户自己双击 .cmd 或在普通 PowerShell 窗口运行不受影响**
  （`Start-Process` 给每个服务开了独立控制台，关掉启动窗口不会带走服务）。
- **WMI 脱离方案不可用**：尝试用 `Win32_Process.Create` 彻底脱离 Job Object，被本机安全策略拦截，已放弃。
- MySQL 仍作为系统服务管理，脚本只在 3306 未监听时尝试 `Start-Service MySQL*`，`-Stop` 不会停它。

## 9. 运行内存优化（同日 13:00）

### 优化前的真实占用

用「提交内存（Private Bytes）」而不是工作集统计——Windows 会把空闲进程的工作集裁到接近 0，
只看工作集会严重低估（knowledge 工作集显示 2.8MB，实际提交 2.6GB）。

| 服务 | 优化前提交 |
| --- | ---: |
| knowledge | 2641 MB |
| backend 应用 JVM | 410 MB |
| Maven 父 JVM（spring-boot:run 的副产物） | 420 MB |
| mysql（系统服务） | 382 MB |
| frontend | 237 MB |
| admin | 129 MB |
| ai-service | 60 MB |
| ollama | 61 MB |
| mock-ssh | 31 MB |
| redis | 9 MB |
| **合计** | **3960 MB** |

### 两处根因与改法

1. **knowledge 2641 MB**：torch/OpenMP 默认按物理核数起线程（本机 32 核），每个线程自带
   arena，提交内存随核数线性膨胀，而语料只有 299 条。
   改法：启动时注入 `OMP_NUM_THREADS=1`、`MKL_NUM_THREADS=1`、`OPENBLAS_NUM_THREADS=1`、
   `NUMEXPR_NUM_THREADS=1`、`TOKENIZERS_PARALLELISM=false`。
   实测线程数 48 → 3，提交内存 **2641 → 1142 MB**，`/api/ready` 就绪时间仍是 14 秒（无退化）。

2. **后端多养一个 JVM**：`mvn spring-boot:run` 会 fork 出应用 JVM，Maven 那 420MB 纯属空转，
   而且每次启动都要走一遍 Maven 生命周期。
   改法：默认改为**单 JVM 跑 jar**
   （`target/smartops-backend-0.0.1-SNAPSHOT.jar`），并给应用固定 JVM 参数
   `-Xms128m -Xmx640m -XX:MaxMetaspaceSize=320m -XX:+UseSerialGC -XX:TieredStopAtLevel=1 -Xss1m`。
   脚本会比较 jar 与 `backend/src` 下最新文件的时间戳，**源码有更新就自动重新打包**，不会跑到旧代码。
   需要 Maven 的热重启行为时用 `-Dev`（会保留 420MB 的 Maven JVM，这是代价）。
   实测 java 进程数 2 → 1，后端总占用 **830 → 310 MB**。

3. 前端 `NODE_OPTIONS=--max-old-space-size` 由 512 收到 384，避免 node 过度预留堆（两个前端各降约 90MB）。

### 顺带修掉的三处脚本/测试缺陷

- **`-Stop` 重复执行会崩**：`taskkill` 对已不存在的 PID 往 stderr 写错误，在
  `$ErrorActionPreference='Stop'` 下被提升成 NativeCommandError，直接中断停止流程，
  后面的服务就不再杀了。改为临时降级 + 吞掉，退出码仍以 `$LASTEXITCODE` 为准。
  现已验证重复 `-Stop` 输出「未运行」而非异常。
- **跨套件污染（口令）**：`sec0405` 用的口令是 `E2eOps#2026!`，夹具是 `E2eOp#2026`；
  它的 `ensure_user` 发现账号已存在就无条件重置 `password_hash`，把共享夹具的密码改掉，
  后续平台 E2E 登录 401。已统一口令，并把流程改成「先拿现有口令试登录，失败才建号/重置」。
- **跨套件污染（删号）**：`sec0405` 的 cleanup 会 `DELETE FROM app_user WHERE id IN (op1,op2)`，
  把共享夹具删掉。已移除该删除，账号统一由 `seed_sec_fixtures.py --cleanup` 管理。

修完后按「seed → sec0405 → sec03 → platform → run token」顺序连跑，无需中途重建夹具，
四套 19/19、8/8、23/23、6/6 全过——套件之间已无顺序依赖。
