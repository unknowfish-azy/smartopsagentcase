## 0. 三个问题的直接回答

| 问题 | 回答 |
|---|---|
| 能不能用 AI Infra 训练模型？ | 能，但**分层看**：7B 级全参微调需要 ≥2×A100/80G，竞赛环境不现实；**LoRA 微调 7B（单卡 24G 勉强、40G 舒适）、CPU 可跑的异常检测/容量预测、embedding/rerank 微调都能做**。本方案按「无 GPU 也能先跑通闭环」设计。 |
| 用什么算法？ | 四条线：① 指标异常检测（IsolationForest / LightGBM / 时序自编码器）② 容量与故障预测（LightGBM / Prophet / TFT）③ 检索与 RAG（embedding 微调 + rerank 蒸馏）④ Agent 决策（SFT + DPO 偏好优化）。详见 §2。 |
| KV cache 怎么算？ | 单 token 显存 = `2 · L · H_kv · d_head · b`；单序列 = 上式 × 序列长度。7B（GQA 4 头）fp16 约 **56 KiB/token**，4K 上下文 **224 MiB/序列**。完整公式与并发预算见 §3。 |

**关于「数据就是石油」**：我们能合法拿到的只有**本平台自己产生的运维数据**（指标、轨迹、核查记录、评测集），加上公开学术数据集。云厂商的存量数据不属于我们，抓取既不合法也不现实——这一条必须写进答辩口径。

## 2. 四条算法线（按投入产出排序）

### L1 指标异常检测（最先做，CPU 可跑）
- 基线：3σ / IQR（已有阈值规则，作为对照组）
- 模型：IsolationForest → LightGBM（有标注后）→ 时序自编码器
- 数据：`sentinel_metric_sample` + 公开 SMD（ServerMachineDataset）
- 指标：Precision/Recall/F1、误报率（运维场景误报代价高，要求 Precision ≥ 0.8）

### L2 容量与故障预测
- LightGBM 回归（容量）/ Prophet（周期）/ TFT（多变量，需 GPU）
- 数据：指标时序，按服务器聚合
- 指标：MAPE、峰值时段命中率

### L3 检索与 RAG（收益最直接）
- embedding 微调（对比学习，query-doc 对来自 golden_set 扩写）
- rerank 蒸馏：教师 = 大模型打分，学生 = 小 cross-encoder
- 数据：现有 70 条 → 扩到 ≥300 条，配合知识库文档构造难负例
- 指标：Recall@k、MRR、nDCG@10（现有评测脚本可直接复用）

### L4 Agent 决策（SFT + DPO，最贵）
- SFT：把「任务 → 工具序列 → 结果」轨迹转 chat 样本（含失败样本与重试轨迹）
- DPO：需要采纳/驳回反馈，**当前无数据源**，须先建 `agent_feedback`
- 数据量经验值：SFT 3k-10k 条高质量轨迹起步；DPO 1k-3k 对偏好
- 指标：任务成功率、平均步数、工具调用合法率（现有 `agent/tools/validation.py` 可测）

> TTS 音色克隆已有能力（`TTS_VOICE_PRESETS`，VoxCPM2/F5-TTS），不在本方案重复。

## 3. KV cache 与显存预算（AI Infra 部分）

### 3.1 核心公式

```
单 token KV 显存   C_token = 2 · L · H_kv · d_head · b
单序列 KV 显存     C_seq   = C_token · s
总 KV 显存         C_total = C_token · Σs_i        （i = 并发序列）
```

- `2`：K 和 V 各一份
- `L`：层数；`H_kv`：KV 头数（GQA 时 < 注意力头数）；`d_head`：每头维度
- `b`：每元素字节数（fp16=2，int8=1，4bit=0.5）
- MHA 退化为 `H_kv = H`，显存直接翻 `H/H_kv` 倍（7B 是 7 倍）

### 3.2 实算对照（fp16，b=2）

| 模型 | L | H_kv | d_head | 每 token | 4K 单序列 | 32K 单序列 |
|---|---|---|---|---|---|---|
| Qwen2.5-7B | 28 | 4 | 128 | 56 KiB | 224 MiB | 1.75 GiB |
| Qwen2.5-14B | 48 | 8 | 128 | 192 KiB | 768 MiB | 6 GiB |
| Qwen2.5-32B | 64 | 8 | 128 | 256 KiB | 1 GiB | 8 GiB |

### 3.3 并发估算

```
N_max ≈ (GPU_mem · util − W_weights − W_act) / C_seq
```

示例：24 GB 卡跑 7B fp16（权重 ≈15.2 GB），util=0.9，激活预留 1 GB：
KV 可用 ≈ 24×0.9 − 15.2 − 1 ≈ 5.4 GB → 4K 上下文约 **24 并发**，2K 约 **48 并发**。

### 3.4 PagedAttention（vLLM）

- 分块：每 block 固定 16 token，按需分配 → 内部碎片上界 15 token/序列
- 论文口径：显存利用率由 20-40% 提升到 ~96%，同卡吞吐 2-4×
- 共享前缀（系统提示、工具 schema）可跨请求复用 block，长 system prompt 场景收益最大

### 3.5 训练侧显存（粗略，用于判断可行性）

```
全参 SFT  ≈ 16-20 × P（fp32 Adam 状态 + 梯度 + 激活，取 grad checkpoint 后）
LoRA SFT  ≈ 权重 + 少量激活 ≈ 1.2-1.5 × 权重
```

- 7B 全参：≈112-140 GB → 需 2×A100-80G + ZeRO-3
- 7B LoRA（r=16，2K ctx，bs=1）：≈20-26 GB → 24G 卡勉强，建议 40G
- 训练 FLOPs ≈ `6 · P · D`（D = 训练 token 数）；推理 prefill ≈ `2 · P · s`，decode ≈ `2 · P`/token

## 4. 数据获取方案（合法、可复现）

### 4.1 内部数据（主力，占比目标 ≥70%）

| 阶段 | 动作 | 产出 |
|---|---|---|
| 采集 | 指标按分钟落 Parquet（日分区）；决策链/核查落 JSONL；执行轨迹从运行期事件导入 | `ai-service/scripts/export_training_data.py` → `data/lake/{metrics/dt=YYYY-MM-DD/metrics.parquet, decisions/, inspections/, trajectories/}`，全部覆盖写、重跑幂等 |
| 治理 | 字段字典、去重、空值率、时间对齐；**日志/对话脱敏**（IP、主机名、token、手机号） | 数据字典 + 质量报告 |
| 标注 | 告警复核结论、Inspector 判定、检索命中 | 标注集 + 一致性（双人 κ ≥ 0.6） |
| 回流 | 新增 `agent_feedback`（采纳/驳回/改判） | DPO 偏好对 |

### 4.2 公开数据集（补冷启动，占比 ≤30%）

- **LogHub**（logpai）：HDFS_v1（约 1.1×10⁷ 行）、BGL（约 4.7×10⁶ 行）→ 日志解析/异常检测
- **CCF AIOps 挑战赛数据集（2020-2022）**：metric + trace + log 多模态 → 故障定位
- **SMD / SMAP / MSL**：服务器多指标异常检测基准
- **TrainTicket、Online Boutique / Sock Shop**：微服务 trace → 调用链分析
- 使用要求：记录来源与许可，不二次分发，论文/答辩注明出处

### 4.3 合成数据（补长尾）

- 教师模型生成「问法变体 / 故障场景 / 工具调用轨迹」，**人工抽检 ≥10%**，抽检不通过则整批降权
- 合成数据只用于 SFT 冷启动与评测扩充，**不用于宣称真实线上效果**

### 4.4 合规红线

- 用户对话内容入库前脱敏，未经授权不用于训练
- 不抓取第三方云平台数据；不使用未授权版权语料
- 训练数据与评测数据**按时间切分**，防止泄漏

## 6. 风险

| 风险 | 应对 |
|---|---|
| 数据量不足 | 公开集补冷启动 + 合成 + 时间切分评测，不夸大效果 |
| 无 GPU | D0-D3 先落地，D4 用云上按小时租卡（A10/A100）跑一次出结果 |
| 标注成本 | 先用 Inspector 自动判定做弱标注，人工只审争议样本 |
| 答辩质疑「数据从哪来」 | 用 §1 表格逐条对应代码位置，公开集注明来源 |
| 误报伤运维信任 | 异常检测默认「建议模式」，人工确认后才触发动作 |
