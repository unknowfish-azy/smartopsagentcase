# Team Shared Agent Design

## Goal

在保留现有个人空间、团队成员管理和 Astra6 已完成能力的前提下，为 SmartOpsAgent 增加团队共享 Agent、协作运维、审批和审计能力。

## Scope

本设计只扩展团队协作能力，不重写已有个人 Agent、个人知识、个人连接、团队邀请、团队冻结和平台管理员功能。

平台采用两层作用域：

- `user`：用户个人资源，只能由资源所属用户访问。
- `team`：团队共享资源，只能由团队成员按团队角色和资源授权访问。

平台 `root` 是平台管理员，负责平台治理和全局模板；团队内部继续使用现有 `owner/admin/member/viewer` 角色。`member` 在 Agent 运行场景映射为 operator 能力，`viewer` 保持只读，不修改历史角色数据。

## Existing Capability Reuse

- 复用 `TeamWorkspaceService` 的团队、邀请、成员角色和冻结状态。
- 复用 `UserAccountService`、`SessionUser` 和服务端会话认证。
- 复用现有 Operation Tool Catalog、运行时、trace、执行记录和只读工具约束。
- 复用现有个人 Agent、聊天历史、模型连接和知识空间作为 `user` scope。
- 复用现有平台管理员账户和审计机制，不创建第二套 root 身份系统。

## Resource Model

新增团队作用域资源。具体表名可以在实现计划中按现有命名规范落地：

### Team Agent

`team_agent` 保存 Agent 的团队归属、名称、描述、状态、创建者和当前发布版本。每个 Agent 必须有一个 `team_id`，不能通过请求参数切换团队。

### Agent Version

`team_agent_version` 保存不可变的发布内容，包括系统提示、模型策略、工具白名单、知识范围和运行参数。草稿可编辑，发布后版本内容不可修改，只能创建新版本。

### Agent Binding

`team_agent_binding` 保存团队成员或团队角色对 Agent 的授权。能力至少包括：

- `view`：查看基本信息和脱敏结果。
- `run`：运行已发布版本。
- `approve`：审批高风险操作。
- `manage`：编辑草稿、发布版本和修改策略。

### Agent Run

`team_agent_run` 保存团队、Agent、版本、发起人、审批人、目标资源、状态、trace、开始和结束时间以及结果摘要。详细命令和证据继续复用现有运行记录体系，并通过 run 关联到团队作用域。

### Secret Reference

`team_agent_secret_ref` 只保存团队连接或凭据的引用和用途，不保存明文密钥。实际凭据由连接中心管理，Agent 运行时只能获得短生命周期的服务端解析结果。

### Team Agent Policy

`team_agent_policy` 保存工具白名单、审批要求、允许的目标环境、并发上限、每日运行额度和结果脱敏策略。

## Role Compatibility

| Capability | root | owner | admin | member | viewer |
|---|---:|---:|---:|---:|---:|
| 查看团队 Agent | 全部 | 团队内 | 团队内 | 已授权 | 已授权 |
| 创建/编辑草稿 | 是 | 是 | 是 | 否 | 否 |
| 发布版本 | 是 | 是 | 可配置 | 否 | 否 |
| 运行 Agent | 是 | 是 | 是 | 已授权 | 否 |
| 审批高风险动作 | 是 | 是 | 是 | 否 | 否 |
| 查看完整执行证据 | 是 | 是 | 是 | 按授权 | 脱敏 |
| 删除 Agent | 是 | 是 | 否 | 否 | 否 |

`root` 的平台管理权限不等于自动读取所有个人资源；root 读取个人数据仍需遵守既有平台审计和最小权限规则。团队冻结后，成员可以查看允许的基础信息，但不能创建、修改、邀请、发布或启动新的团队运行。

## Authentication and Authorization

所有团队 Agent、运行时、工具、知识和连接接口必须从服务端会话获得操作者身份：

1. 从 `SessionUser` 获取当前用户和平台角色。
2. 根据资源 ID 查询所属 `team_id` 或 `user_id`。
3. 校验当前用户是否为该团队成员，以及是否拥有所需能力。
4. 校验团队状态、Agent 状态、版本状态和策略。
5. 将授权决策写入审计记录和运行 trace。

客户端传入的 `X-User-Id` 不得作为身份来源。兼容迁移期间可以保留旧接口路径，但必须忽略该请求头，并通过认证会话确定用户。所有旧的个人接口继续使用 `user` scope，不自动暴露团队资源。

## Collaboration Flow

1. `root` 创建或发布全局 Agent 模板。
2. 团队 `owner/admin` 将模板实例化为团队 Agent，绑定团队知识、连接和工具策略。
3. Agent 在草稿状态编辑；发布后产生不可变版本。
4. `member` 只能运行已授权的已发布版本，不能直接修改提示词、工具或凭据引用。
5. 只读诊断工具直接进入运行；变更工具生成审批任务。
6. `reviewer` 能力由团队 `owner/admin` 或显式绑定授予，审批通过后生成一次性执行授权。
7. 运行期间记录操作者、Agent 版本、审批者、目标、命令、输出摘要、证据和结果。
8. 成员撤权、团队冻结、Agent 下线或凭据失效时，未开始的运行立即阻断；进行中的运行按工具策略停止或只读收尾。

## Safety and Isolation

- 所有查询必须带服务端推导的 scope，不能使用客户端提供的团队 ID 作为唯一授权依据。
- 团队 Agent 不能读取成员私人聊天、个人知识或个人连接，除非资源被显式复制或授权到团队。
- 工具白名单、目标主机、命名空间和环境必须由服务端策略校验。
- 高风险工具必须经过预览、确认和审批，不能仅依赖前端按钮状态。
- 运行结果对 `viewer` 默认脱敏，凭据、令牌、环境变量和原始敏感输出禁止进入普通成员视图。
- 每次授权变化、发布、审批、运行、撤销和失败都写入不可篡改的审计事件。
- 团队配额按团队统计，个人配额和团队配额分别执行。

## API Boundary

新增接口建议统一使用 `/api/team-agents`，由服务端会话和路径中的 Agent ID 推导团队范围：

- `GET /api/team-agents`
- `POST /api/team-agents`
- `GET /api/team-agents/{id}`
- `PUT /api/team-agents/{id}/draft`
- `POST /api/team-agents/{id}/versions`
- `POST /api/team-agents/{id}/publish`
- `POST /api/team-agents/{id}/runs`
- `GET /api/team-agents/{id}/runs`
- `GET /api/team-agent-runs/{runId}`
- `POST /api/team-agent-runs/{runId}/approve`

现有 `/api/operations` 个人运行接口保持兼容；团队运行必须使用团队作用域接口，避免通过旧接口隐式共享个人 runtime。

## Frontend Experience

用户从主菜单选择“团队协作”后，进入独立的团队协作工作台。团队工作台拥有自己的上下文、工具菜单和会话区域；切换到团队协作时，不复用个人空间的 Agent、工具选择或聊天会话。

团队协作工作台布局分为三块：

- **团队上下文栏**：显示当前团队、成员身份、团队状态、当前 Agent 和当前运行目标；支持切换用户有权访问的团队。
- **团队工具菜单**：显示当前团队可用的 Agent、只读诊断工具、变更工具、连接资源、运行历史和审批中心。菜单内容由服务端返回的能力矩阵决定，不能只依赖前端隐藏。
- **协作会话区**：承载团队 Agent 对话、工具预览、审批卡片、运行日志、证据和结果摘要。会话必须绑定 `teamId`、`agentId`、`agentVersionId` 和 `runId`，不能混入个人聊天历史。

团队协作工作台中的工具菜单至少包含以下分组：

- **Agent**：团队 Agent 列表、草稿、已发布版本和运行入口。
- **诊断工具**：健康检查、日志查询、指标查询、进程和服务诊断等只读能力。
- **运维工具**：需要确认或审批的变更操作，显示风险等级和审批状态。
- **连接与目标**：团队授权的服务器、集群、命名空间和观测源，只显示脱敏标识。
- **运行与审批**：当前运行、历史运行、待审批任务和执行证据。

团队空间增加三个主要入口：

- **Agent 工作台**：Agent 列表、状态、当前发布版本、授权范围和策略摘要。
- **协作运行**：创建运行、选择目标、预览工具调用、查看审批状态和实时 trace。
- **审批中心**：reviewer 查看风险、变更范围、证据和审批历史。

界面继续沿用现有团队空间视觉和权限路由。个人空间保持原有入口，团队空间不显示个人 Agent 和私人资源。所有按钮根据能力隐藏或禁用，但实际权限由后端强制校验。

## Rollout

### Phase 1: Scope and Authorization

- 统一使用 `SessionUser`。
- 为团队资源建立 scope 查询和授权服务。
- 增加团队 Agent、版本、绑定和运行基础表。
- 覆盖跨团队读取、撤权、冻结和旧接口兼容测试。

### Phase 2: Agent Workspace

- 实现草稿、版本发布、工具白名单和团队连接引用。
- 增加团队 Agent 前端工作台。
- 复用现有知识和运行记录能力，不复制个人存储。

### Phase 3: Approval and Collaboration

- 增加审批队列、一次性执行授权、运行接管和协作备注。
- 增加完整执行证据、脱敏视图和通知。

### Phase 4: Governance

- 增加团队配额、成本统计、SLA、模板市场和跨团队复制。
- 跨团队复制只复制模板和非敏感策略，凭据必须重新绑定。

## Acceptance Criteria

- 成员无法读取或运行其他团队 Agent。
- 成员撤权后不能创建新运行，旧运行不会获得新的工具授权。
- 团队冻结后不能发布、邀请、修改或启动运行。
- 发布版本不可被运行者修改，运行记录能追溯到准确版本。
- 变更工具在无审批时不能执行。
- 个人资源不会出现在团队列表、团队 Agent 上下文或团队运行结果中。
- 从主菜单进入“团队协作”后，工具菜单、Agent 选择和会话历史都绑定当前团队，不复用个人空间状态。
- 成员在团队工具菜单中只能看到服务端授权的 Agent、工具和目标，点击无权资源不能通过接口执行。
- 客户端伪造 `X-User-Id`、`teamId`、`agentId` 或 `runtimeId` 不会改变服务端授权结果。
- 现有个人空间、团队成员管理和平台管理员功能的回归测试继续通过。
