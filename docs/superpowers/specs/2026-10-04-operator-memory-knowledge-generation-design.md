# 智能运维知识分层与操作员记忆设计

## 1. 背景与目标

SmartOpsAgent 已有系统内置知识、运行记录、知识候选审核、Skill 中心、插件中心和团队 Agent 审批能力，但这些能力目前彼此独立：知识主要是静态目录，个人经验没有持久化模型，运行记录生成的候选只保留 Markdown，Skill/脚本/插件也不能从故障上下文进入受治理的生成流程。

本设计建立一条可审计闭环：

```text
故障上下文 -> 知识检索 -> 操作员记忆 -> 处理建议 -> 用户确认
                                      |
                                      v
              个人知识 / Skill 草稿 / 脚本草稿 / 插件草稿
                                      |
                         校验 -> 审核 -> 发布 -> 审计
```

目标是让 Agent 能按操作人员的历史习惯给出可解释建议，同时保证个人数据、团队数据和系统知识严格隔离，任何可执行产物都不能绕过现有审批链路。

## 2. 非目标

- 不自动执行模型生成的命令。
- 不自动把个人知识共享给团队。
- 不自动安装第三方 Skill、插件或远程代码。
- 不把一次失败运行直接认定为正确的故障根因。
- 不替换现有团队 Agent 的成员权限、预览、审批和审计机制。

## 3. 知识作用域

### 3.1 系统知识库

系统知识库由 SmartOpsAgent 发布，前端只读。每条资料必须包含平台、服务、适用版本、风险级别、内容版本和来源。Agent 可以检索和引用，不得通过个人接口修改。

### 3.2 个人知识库

个人知识库按 `user_id` 隔离，默认只有创建者可读写。支持用户创建知识库、条目、标签、适用环境、验证记录、归档和删除。个人条目可以引用运行记录、会话、故障候选或系统知识，但引用不会复制系统知识的所有权。

### 3.3 故障沉淀候选

候选由运行记录、诊断证据或用户确认的聊天内容生成，状态为 `DRAFT` 或 `PENDING_REVIEW`。候选必须保留来源、证据、生成时间和生成器版本；审核前不能被作为已验证知识推荐，也不能发布为团队知识。

### 3.4 团队共享知识库

个人条目只能由用户主动发起共享申请。团队管理员或负责人审核后，生成团队作用域的版本副本，并保留原个人条目的来源和审计关系。团队成员只能读取已发布版本，团队权限沿用 `owner/admin/member/viewer`。

## 4. 操作员记忆模型

操作员记忆记录可复用的工作偏好，而不是保存未经筛选的全部聊天内容。建议字段：

- `user_id`：归属操作员。
- `scope_type/scope_id`：个人或已授权的团队作用域。
- `memory_type`：工具选择、排查顺序、参数偏好、验证习惯、回滚习惯。
- `trigger`：错误码、日志特征、服务、平台或故障标签。
- `preferred_action`：建议动作或动作序列，只描述建议，不授予权限。
- `evidence_count`：支持该记忆的已确认案例数。
- `confidence`：由成功验证、用户确认和最近使用时间计算。
- `status`：`ACTIVE`、`DISABLED`、`ARCHIVED`。
- `source_refs`：来源运行记录、知识条目和反馈记录。

记忆写入条件至少满足一项：用户明确保存；用户确认 Agent 建议；运行结果成功且用户完成验证。模型猜测、未完成运行和未经确认的聊天内容不能直接写入长期记忆。

## 5. 故障识别与推荐

新增故障上下文规范化对象 `IncidentPattern`，包括：

- 症状和错误码；
- 日志、命令输出和监控证据摘要；
- 主机、平台、服务和版本；
- 已尝试动作及结果；
- 当前风险和执行边界；
- 关联的系统知识、个人知识、团队知识和历史记忆。

推荐服务按以下顺序工作：

1. 对输入做脱敏和字段归一化。
2. 检索系统知识和可见个人/团队知识。
3. 按触发条件、环境匹配度、验证成功率和最近使用时间排序记忆。
4. 输出建议、证据引用、置信度、风险等级和下一步验证方式。
5. 对高风险动作只输出预览和审批请求，不输出可直接执行的授权。

推荐结果必须标识来源，例如 `SYSTEM_KNOWLEDGE`、`PERSONAL_KNOWLEDGE`、`OPERATOR_MEMORY` 或 `INCIDENT_HISTORY`，前端不得把推测显示成已确认事实。

## 6. 产物草稿与治理

Skill、脚本和插件统一使用 Artifact Draft 模型：

```text
DRAFT -> VALIDATING -> PENDING_REVIEW -> APPROVED -> PUBLISHED -> ARCHIVED
```

### 6.1 Skill 草稿

必须包含目标、触发条件、输入证据、只读排查步骤、输出格式、禁止事项、验证标准和回滚说明。生成结果只允许进入现有 Skill 审核/启用流程。

### 6.2 脚本草稿

必须声明语言、参数、只读模式、超时、退出码、敏感信息处理、影响范围和回滚方式。生成后进行语法检查、危险命令扫描、敏感信息脱敏和沙箱试运行。

### 6.3 插件草稿

必须包含 Manifest、入口、依赖、工具声明、权限、网络访问范围、版本和风险级别。不加载远程代码，不自动安装依赖；发布前需人工审核和签名或内容摘要绑定。

任何需要改变环境的脚本、工具或插件，都必须复用现有运行审批链路：命令预览、摘要绑定、权限校验、审批、执行和审计。

## 7. 后端接口边界

第一期建议新增以下资源，所有接口从认证上下文取得 `user_id`，不信任客户端传入的归属用户：

- `GET/POST /api/knowledge/personal/libraries`
- `GET/POST/PATCH/DELETE /api/knowledge/personal/entries`
- `GET/PATCH/DELETE /api/knowledge/memories`
- `POST /api/knowledge/candidates/{id}/promote`
- `POST /api/knowledge/candidates/{id}/reject`
- `GET /api/knowledge/recommendations`

团队共享申请和 Artifact Draft 接口在第二期设计，复用团队资源授权器和运行审批服务，不在第一期绕过权限体系。

## 8. 前端信息架构

知识库页面改为以下入口：

```text
知识库
├── 系统知识库
├── 我的知识库
├── 故障沉淀
├── 团队共享
└── 生成中心
```

“我的知识库”提供创建、编辑、归档和删除；“故障沉淀”显示候选来源、证据和审核动作；“生成中心”显示 Skill、脚本、插件草稿状态。所有页面显示作用域、来源、验证状态和风险级别。

## 9. 分阶段交付

### 第一阶段：知识分层和个人知识

建立个人知识库表、条目 API、前端工作区和作用域过滤；保留现有系统知识目录和候选审核页面。

### 第二阶段：操作员记忆

建立记忆表、确认/禁用/删除 API，将已确认的运行结果接入记忆更新；在 Agent 上下文中返回可见记忆摘要。

### 第三阶段：故障识别与推荐

建立 `IncidentPattern` 和推荐服务，输出可解释的匹配证据、置信度和风险等级。

### 第四阶段：产物生成与发布

建立 Artifact Draft、校验、沙箱、人工审核、版本发布和回滚；将高风险执行绑定现有团队审批链路。

## 10. 验收标准

- 系统知识、个人知识、故障候选和团队知识在 API 与 UI 中明确区分。
- 用户 A 无法读取或修改用户 B 的个人知识和记忆。
- 未审核候选不会进入已验证知识检索结果。
- 个人记忆只有在用户确认或成功验证后才会被长期保存。
- 推荐结果能展示来源证据、置信度和风险等级。
- 生成的 Skill、脚本和插件始终先进入草稿状态。
- 高风险产物不能绕过预览、审批和审计直接执行。
- 现有系统知识检索、知识候选审核和团队 Agent 审批测试保持通过。
