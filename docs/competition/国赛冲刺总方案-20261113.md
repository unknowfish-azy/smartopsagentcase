## 1. 冲刺目标与一句话战略

**目标**：四件套（技术方案 / 技术报告 / 佐证材料 / 商业报告书）+ 演示录屏 + 答辩稿，全链路同一套事实、同一句主张，按评分点逐条对齐，零内部矛盾、零越界吹牛。

**一句话战略（复用 submission 三条主线，必须出现在四份材料与答辩稿）**：
1. 定位：不是"会聊天的运维助手"，是**敢让它动手的可信运维智能体**。
2. 机制：**三道锁 + 一本账**（证据锁 / 风险锁 / 边界锁 + 全链路审计）。
3. 主张：**AI 负责思考，人负责授权，系统负责留痕。**

**决战原则**：先有口径台账 → 再写技术方案 → 其余三份从方案与报告"派生"（派生比分头写快 3 倍且天然一致）。

## 2. 评分点对齐矩阵（评分点 → 资产 → 落点 → 门禁）

依据 `submission-master-plan.md` F09：**竞赛 AI 技术分项占 35%**（LLM 8 + Agent 8 + RAG 6 + 多模态 5 + 安全 4 + MCP 4）。另两类尺子是"材料规范"与"演示/答辩表现"。

| 评分维度 | 评委关注 | 我们的对应资产 | 落点文档 | 交付门禁 |
|---|---|---|---|---|
| **算法/技术创新**（权重最高） | 有没有真创新、是否自洽 | 版本感知混合检索(0.6/0.4) · `trust_score` 聚合 · **四级纠察**(Rule→Evidence→AI→StateVerifier) · 风险双闸 | 技术方案 §4·§6；技术报告 §3 | 每个创新点写清"痛点→做法→与竞品差异"，禁写"我们用了 RAG" |
| **Agent / LLM 工程**（8+8） | 多角色协同是否真落地 | Planner→Executor→Inspector 流水线 · 6 角色(policies/kernel/tools) · SSE 流式 · 沙箱执行 | 技术方案 §3；技术报告 §2·§4 | 架构图必须与 `agent/` 目录一一对应，图下标注模块路径 |
| **RAG / 知识**（6） | 检索质量、知识资产 | 混合检索 + 版本过滤 + 知识库 | 技术报告 §3·§5(M01) | 指标带 `n=`；声明数据集 DRAFT |
| **安全 / 可信**（4） | 高危操作是否被管住 | 三道锁 · 四级纠察 · 审计落库 · 审批流 | 佐证 §6；技术报告 §4·§8 | 提供"一次高危被拦截→审批→执行→审计"全链路证据 |
| **多模态 / MCP**（5+4） | 能力边界与扩展 | 终端/图像/插件生态（如有） | 技术报告 §2；商业 §5 | 没做满就写"接口已预留"，不夸大 |
| **材料规范与一致性** | 四份是否打架 | 口径台账 + 一致性矩阵 | 全部 | 30 项自检全过；同事实四份同口径 |
| **演示与答辩** | 表达与应变 | 演示录屏 · 答辩稿 · 70 题问答库 | 演示脚本 · `defense-*` | 答辩每个数字可溯源；红线话术背熟 |

> **对齐心法**：权重最高的"算法创新 + Agent 工程"正好是本项目最强项（四级纠察、三道锁），冲刺资源应向这两块倾斜；多模态/MCP 短板用"接口预留 + 诚实边界"对冲，不硬凑。

## 5. 多模型协作节奏（本方案核心新增）

按你"我只出方案，剩下的交给其他大模型"的约定，定义如下流转：

### 5.1 三种角色
- **规划者（我）**：产出本总方案、各工作包模板、门禁清单、一致性终检。不动手改文件/跑构建。
- **实现者（其他大模型）**：认领 T1–T10，按模板交付，交付前自测。
- **校验者（测试模型 / 我）**：跑门禁清单与回归（既有 503 测试 + 前端契约），不过门禁打回。

### 5.2 单工作包流转
```
规划者出包(目标+输入+门禁) → 实现者执行 → 实现者自测 → 提交门禁清单
        → 校验者跑门禁/回归 → 通过则归档，不通过则打回重做
```

### 5.3 交接协议（防扯皮）
1. 每个包必须带**统一模板**（§4），缺"验收门禁"的包规划者不发出。
2. 实现者交付时**逐项勾选门禁**并附证据（如脚本输出、截图）。
3. 回归保护：前端改动走 `git worktree` 或独立分支，跑 `npm test` + 浏览器契约后再合并；**严禁直接动 main**。
4. 所有材料数字必须先入 `fact-sheet.md`（T1），实现者只能从台账抄，不准现场编。

### 5.4 防回归基线
- 前端：复用已通过的 `login-glass` / `login-layout` / `meteor` 契约 + 503 单测。
- 已知 4 个历史失败用例（server-demo-theme / visual-mode / milky-way / home-orbit）经 `git stash` 对照确认是仓库既有问题，**不计入本次门禁**，校验者遇之直接放行并备注。

## 8. 红线与一致性（复用，重点强调）

**三条红线（背熟，见 submission §6）**：
1. 数据集仅 14 条且全 DRAFT → 禁写"准确率 9X%"，改用"链路打通 + n= 小样本 + 局限声明"。
2. 实验标记 NOT RUN → 只呈已完成，未完成标 NOT RUN 并给协议。
3. 多组件是规则基线（Planner/BM25/向量检索/AI Judge）→ 统一写"确定性基线 + 可插拔接口"。

**一致性口诀**：方案说"要"，报告说"了"，佐证说"证"，商业说"值"。任一份越界即漏洞。

**提交前 30 项自检**：直接复用 `submission-master-plan.md` 第 10 节，T8 逐条勾选。

## 9. 风险登记与应对

| 风险 | 影响 | 应对 |
