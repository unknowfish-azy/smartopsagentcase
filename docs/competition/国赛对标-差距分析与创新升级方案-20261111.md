## 0. 先澄清一个容易致命的混淆：AIC ≠ 睿抗

| 项 | AIC 算法创新赛 | 睿抗机器人开发者大赛 |

| 全称 | 全球校园人工智能算法精英大赛 · 算法创新赛（第八届 2026） | RAICOM（原名 RoboCom），工信部人才交流中心主办 |

## 1. 执行摘要（先看这 6 条）

1. **最大问题不是「功能少」，而是「算法贡献不可核验」**。项目工程完成度高（Vue3 双入口 + SpringBoot + FastAPI + Python Agent 框架 + 混合检索链），但 `docs/experiments/` 全部 `NOT RUN`、`training/training-gate-report.md` 为 `BLOCKED / Approved samples 0`、无专利/软著/论文/第三方他证。在 AIC「创新性 20 + 技术实现 20」共 40 分里，可举证的算法贡献目前是规则表、加权公式与 CRUD 状态机。
2. **评分权重可能与官方规程错位**。仓库 `docs/competition/project-plan.md:73-80` 用的是「AI 技术深度 35% + 创新性 25% + 前端工程质量 10% + …」，而 2026 AIC 赛题 2 官方是「创新性 20 / 技术实现 20 / 功能完整性 20 / 方案完整性 20 / 应用价值 15 / 总结与展望 5」——**「前端工程质量」在官方不是独立评分项**。这套 35/25 权重在仓库与本次核实的官方规程中均未找到出处，建议立即溯源或改写。
3. **默认演示路径会把「AI 深度」拉到最低档**。`ai-service/app/core/config.py:24` 默认 `llm_provider="mock"`，`llm.py:110-178` 的回答是固定模板 + 原样回显；`chat.py:374-388` 的「思考阶段」是 3 段静态列表，文档宣称的 evidence/plan/risk 三步在该链路未执行；`agent/planner/planner.py` 是正则三分支单步规则且**生产链路无调用点**。评委不主动配 Ollama 时，看到的是「演示级 AI」。
4. **睿抗 CAIP 2026 的决赛任务简直是为本项目写的**：模块三「智能体应用与开发」占 35%，任务一就是「企业 IT 运维工单处理」的 Planner / 执行 Agent / 质检 Agent 拆解，任务二多工具调用，任务三跨场景编排，任务四敏感指令识别 + 权限校验 + 操作审计。项目现有 `policies` / `approval` / `audit` / `inspector` 正好对得上，但 Planner、多智能体编排、真实 LLM 循环三块是空的。
5. **GitHub 上有成熟「模式」可借鉴，但没有可直接复刻的「作品」**。AIOpsLab / OpenRCA / ITBench 给的是评测协议，HolmesGPT / K8sGPT 给的是 agentic 排障循环，LangGraph / AutoGen 给的是编排骨架，RAGFlow / RAGAS 给的是检索与评测。正确用法是**借协议与骨架、自研判据与数据**，且必须按 AIC 原创性条款标注引用（见 §5.3）。
6. **最短见效路径是「把 NOT RUN 变成可答辩的数字」**，脚本和台账都已具备（`scripts/eval_retrieval_ablation.py`、`06-工程整改/*.csv`、`submission-master-plan.md` 的 M01–M05 评测设计）。这比赶工加功能更能直接拉高「方案完整性 + 技术实现」两项。

## 2. 基准一：历年国赛标准（官方口径，逐项摘录）

### 2.1 AIC 第八届（2026）算法创新赛 · 赛题 2「AI+软件创新」评分规则（100 分）

来源：官方 PDF《第八届全球校园人工智能算法精英大赛 算法创新赛竞赛规则》
`https://www.aicomp.cn/wp-content/uploads/2026/05/2026AIC算法创新赛赛题规则汇总260506-1.pdf`（PDF 第 7–9 页，已本地解析核对）

| 评分项目 | 分值 | 14–20 分档（高） | 7–13 分档（中） | 0–6 分档（低） |
|---|---|---|---|---|
| 创新性 | **20** | 采用全新 AI 技术架构或模式，解决行业重大难题，具有开创性 | 在现有技术上有显著改进，形成独特解决方案 | 创新程度较低，仅做常规优化 |
| 技术实现 | **20** | AI 算法设计科学、模型选型合理、运行高效稳定、AI 模型与软件系统适配性极佳 | 方案可行、可正常运行，但部分技术难点未完全攻克 | AI 算法无法正常运行 / 重大缺陷影响核心功能 |
| 功能完整性 | **20** | 功能完整、满足核心需求、流程流畅、无明显缺失 | 基本完整，部分次要功能不完善 | 核心 AI 功能缺失，软件无法正常使用 |
| 方案完整性 | **20** | 涵盖软件开发全流程、内容完整、逻辑清晰、图表规范 | 部分内容缺失或表述模糊 | 严重不完整，无法体现核心设计 |
| 应用价值 | **15** | 10–15：场景明确、解决行业实际痛点、有市场/转化/社会价值 | 5–9：有一定场景，但市场价值与落地可行性待验证 | 0–4：场景不清晰、难以落地 |
| 总结与展望 | **5** | 3–5：总结准确、展望合理有前瞻性 | 1–2：较完整但深度不足 | 0：简略缺乏价值 |

**作品要求 6 条**（PDF 第 7 页）：① 已完成开发的软件产品，核心功能模块完整、无重大缺陷；② **软件需深度融合 AI 算法，算法与产品功能高度契合，避免算法与软件脱节**；③ 提交软件说明文档、功能演示视频、核心算法说明、测试报告，明确技术栈/运行环境/部署方式；④ 良好兼容性与易用性，**提供在线演示地址或可安装的软件包**便于评审验证；⑤ 说明创新点与差异化优势，可附用户反馈或试点应用数据；⑥ 合规且拥有自主知识产权或合法授权。

**技术方案参考大纲 4 章**（PDF 第 9 页）：(一) 产品概述与定位（背景与目标 / 产品定位）；(二) 技术架构与创新（整体架构 / 技术选型 / 创新应用与同类对比）；(三) 功能设计与实现（核心功能 AI 实现方式 / 辅助功能协同 / 扩展性设计）；(四) 开发测试与部署（开发流程 / 关键 AI 代码 / **AI 功能专项测试方案与用例结果、据测试结果做的算法优化** / 部署方案）。

**通用基本要求与材料规范**（PDF 第 2–3 页）：
- 五条基本要求：原创性与真实性（**引用他人技术、算法或数据需在参赛材料中明确标注**；数据案例真实可靠；严禁伪造抄袭代做）、创新性与先进性（与同类成果相比在技术指标、应用效果上具备先进性）、实用性与成熟度（**已实际应用并取得良好效果，有清晰应用案例和数据证明**）、完整性与规范性、公平性（**作品方案/视频/PPT 不得出现学校名称、Logo、指导教师信息**）。
- 提交清单：作品名称 ≤20 字；简介 ≤300 字（问题-方案-效果-应用）；方案 PDF ≤10 MB；演示视频 MP4 **3–5 分钟**、≤300 MB；答辩 PPT 转 PDF；佐证材料（专利、软著、论文首页、企业合作意向书、用户反馈、试点应用证明）合并为一个 PDF；大容量代码包放网盘，按「参赛团队编号-赛题名称-作品名称-XX」命名，永久有效分享。

## 6. 创新点重构：3 个可答辩、可消融、可复现的自研算法

> 设计原则：每个创新点都必须能回答评委三问——「问题怎么形式化？」「比什么 baseline 好多少？」「实验怎么复现？」。这三问正好补上项目当前最大的空白。

### 6-A 证据充分性驱动的「假成功」检测与可信度校准（EVS）

- **问题定义**：给定执行声明 `a`、状态探针 `S`、检索证据 `E`，判定 `y ∈ {success, false_success, failure}`，并输出校准后的置信度 `p`。现有 `trust_score.py` 是 `{0.5,0.3,0.2}` 加权和且自承「不是正确概率」。
- **自研点**：把「证据独立性 + 状态探针覆盖度 + 声明-观测一致性」建模为**充分性约束**，只有满足约束才允许输出高置信；用 Platt/ isotonic 校准把启发式分数映射为概率，并给出 **Brier / ECE / 可靠性图**；不满足时主动触发「补证」而非强行判决。
- **Baseline**：① 现有 L1+L2+L4（L3 passthrough）；② 纯 LLM 判定；③ 简单多数投票；④ 加权和原始版。
- **数据/协议**：扩 `06-工程整改/eval_false_success.csv`（51 行）与 C-R9 留出集至 ≥200 条，正负样本均衡，**双人独立标注 + Cohen's κ**；固定 train/dev/test 划分与随机种子。
- **指标**：F1、AUROC、Brier、ECE、平均补证次数、P95 延迟；报告 `n=` 与置信区间，禁止只报训练集 F1（C-R9 已出现 1.0 vs 0.4762 的落差）。
- **最小实现路径**：`agent/inspector/judges/ai_judge.py` 注入真实 `judge_fn` → `inspector/pipeline.py:79` 改为注入式构造 → `knowledge/evidence/trust_score.py` 增加校准层 → `scripts/eval_false_success.py` 增加分组与留出评估。
- **可答辩产物**：消融表 + 校准曲线 + 一份「识别出一个声称重启成功但端口未监听」的完整证据链录屏。

### 6-B 版本感知的证据冲突消解检索（VACR）

- **问题定义**：候选 chunk 带 `(version, timestamp, source)`；当不同版本/相互冲突的文档同时进入上下文时，在版本约束下最大化「相关性 + 证据独立性 + 版本一致性」，输出带版本标注的证据集合。
- **自研点**：构建**证据冲突图**，把版本兼容关系（现有 `version_filter.py` 的 `COMPATIBLE` 明确「暂不实现」）与冲突消解作为检索目标的一部分，而非检索后的硬过滤；给出「版本错误率 VER」这一新指标。
- **Baseline**：BM25 only / 向量 only / 现有 hybrid / 现有 hybrid + 词法 rerank / 语义嵌入 + cross-encoder（逐层消融，正好复用 `C-R8-检索消融报告.md` 的 4 组脚本）。
- **数据/协议**：`SmartOps-Dataset/Linux/*.jsonl` 7 类场景 14 条种子 → 每类构造版本改写变体与冲突注入样本；固定 query 集与人工判定 Top-3。
- **指标**：Recall@3、MRR、nDCG、**版本错误率 VER**、冲突消解准确率、检索延迟。
- **最小实现路径**：`knowledge/embedding/factory.py` 默认切 BGE 并持久化索引（消除 hash 回退）→ `chunker.py` 改按标题/语义递归切分 → `lexical_reranker.py` 叠加 cross-encoder → `version_filter.py` 实现 `COMPATIBLE` 与冲突图 → 在 `service.py:311-390` 保持编排不变以支持前后对照。
- **与开源的区别**：RAGFlow/RAGAS 解决「检索得好不好/生成好不好」，不解决「同一问题存在多个版本且互相冲突时该信谁」——这是运维知识库的真实痛点，也是项目「版本感知」宣称的唯一可自研落点。

### 6-C 带风险门的受控反思循环（PAVR）

- **问题定义**：`Plan → Act → Verify → (Replan | Commit)`，在最大迭代 `N`、风险门 `G`、审计 `A` 约束下最大化任务成功率，且任何高风险动作必须经人工审批。
- **自研点**：**重规划判据由「证据核验结果」而非「模型自我感觉」驱动**——只有 Inspector 判定证据不足/状态不一致才允许 replan，并把每次 replan 的原因写入审计链；风险门与证据核验耦合，区别于通用 ReAct。
- **对齐睿抗 CAIP 模块三**：任务一 Planner/执行/质检角色拆解；任务二日志查询、知识库检索、告警接口三类工具；任务三跨场景 Agent 选择；任务四敏感指令识别、权限校验、操作审计（现有 `policies`/`approval`/`audit` 可直接复用）。
- **Baseline**：现有单步规则 Planner；标准 ReAct；无反思的单次 LLM 规划。
- **指标**：任务成功率、平均步数、工具调用正确率、越权拦截率、重规划收益（有/无 replan 的消融）、Token 成本。
- **最小实现路径**：`agent/planner/planner.py` 换成多步 `PlanStep`（带依赖与末步验证）→ 在 `ai-service/app/services/chat.py` 真实插入 plan/act/verify 事件（替换 `:374-388` 的静态列表）→ `agent/memory/manager.py` 改为可检索存储形成经验回流 → `agent/tools/adapters/mcp.py` 补最小 transport → 用 LangGraph 式状态图管理检查点（仅借设计，不引入整套依赖）。
- **默认配置**：演示时 `llm_provider` 切换到已验证可用的 Ollama（口径台账记录 qwen3:1.7b 五问 5/5），保留 mock 作为离线降级；补齐 `llm.py:57` 的 openai-compatible 分支。

## 附录 B：一句话结论

> 这是一个**工程完整、评测诚实、但 AI 深度偏浅**的作品：按「AI+软件创新」赛道，功能完整性与工程质量能拿分，而创新性、技术实现、方案完整性、应用价值四项受限于「默认 mock + 规则 Planner + NOT RUN 实验 + 零他证」。补强顺序应是 **口径合规 → 真实模型与真实事件 → 可复现实验 → 三个可消融的自研算法 → 佐证材料**，而不是继续堆功能；GitHub 参考应只借「评测协议与编排骨架」，把原创性留在证据校验、版本冲突消解与受控重规划这三个判据上。
