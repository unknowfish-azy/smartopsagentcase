企业用 AI 做运维有个死结：通用大模型会"说"，但不敢让它"做"。【短停顿】因为它可能引错版本的文档，可能声称"已经重启成功"其实没成功，也可能一条命令把生产环境干掉。【长停顿】

我们把它拆成三个真痛点，每个痛点对应一个确定性设计。【短停顿】知识错配——搜到 Ubuntu 的答案，机器却是 CentOS；【短停顿】假成功——AI 说已重启，服务其实没起来；【短停顿】不敢授权——一条 rm -rf 或 iptables 就能毁掉环境。【长停顿】

我们的解法是三道锁、一本账：【短停顿】证据锁——每句话能追溯到知识条目；【短停顿】风险锁——高危操作必须人工授权；【短停顿】边界锁——命令白名单、黑名单加沙箱；【短停顿】一本审计账全程留痕。【长停顿】

架构是浏览器到 Nginx，再到 SpringBoot 后端、FastAPI 的 AI 服务、Python 知识服务。【短停顿】全栈自研：后端 325 个 Java 文件、36,000 余行、79 张表、423 个接口；【短停顿】前端 Vue3 双入口、177 个页面组件，共享逻辑层 48 个模块已迁移 TypeScript；【短停顿】AI 侧是自研的混合检索与四级纠察内核，交互支持语音输入与图像证据。【长停顿】

一句话概括：AI 负责思考，人负责授权，系统负责留痕。【长停顿】

第一个算法点是版本感知检索。【短停顿】运维知识有强版本耦合，Ubuntu 22.04 的答案在 CentOS 6 上就是错的。【短停顿】我们给每个知识切片打 version 字段、检索按版本过滤；版本不一致直接告警、不进答案。【短停顿】这是通用 RAG 不管的。【长停顿】

第二个是混合检索与融合。【短停顿】词法路走 BM25，向量路走 256 维哈希嵌入的余弦相似度；【短停顿】融合是 0.6 乘向量加 0.4 乘 BM25，再重排取前 5 条。【长停顿】

第三个是可信度聚合 trust_score：0.5 乘证据质量、0.3 乘是否被支持、0.2 乘覆盖度，防止"一条证据撑起一个结论"。【长停顿】

第四个，也是我们最核心的创新——四级纠察与假成功检测。【短停顿】L1 规则查风险分级与循环调用，【短停顿】L2 证据查词元重合与版本一致性，【短停顿】L3 的 AI 判定是可选钩子、默认不调模型，【短停顿】L4 状态核验专门抓"假成功"：Agent 声称"已解决、已恢复"，但探针事实显示服务没起来，就直接判为 REJECTED 并触发重新规划。【长停顿】

第五个算法点是恢复契约——假成功检测向恢复环节的延伸。【短停顿】"服务恢复了"不能靠 HTTP 200 或自检 passed 放行，我们把它写成可执行契约：目标、版本、新鲜度、轮次、来源组全达标才判 VERIFIED。【短停顿】42 个冻结案例做可证伪对照："任意 200 算恢复"的弱基线 21 个假恢复，"passed 为真算恢复"的 17 个；【短停顿】我们的实现与独立 oracle 判定 42 比 42 一致，假恢复 0 个。【长停顿】
