"企业不敢把生产环境，交给一个只会回答问题的 AI。"

1. 开场与痛点（约 70 秒）

各位评委老师好。我们是 【团队名称 / 学校待填】 队，参赛作品是 智维Agent —— 面向中小企业的可信 AI 智能运维与知识协同平台。

先讲一个真实场景：一家 50 人的公司，半夜两点数据库告警。值班的是刚入职三个月的应届生，他打开搜索框，搜出来的排障文档，是去年旧版本的；他问大模型，大模型给了个听起来很有道理、却没法验证的方案；他照着一做——高风险命令直接执行，没有任何人复核、没有任何记录。

这不是科幻，这是中小企业的日常。它们的运维有三个共性约束：人手少、系统杂、知识散。由此带来四个具体痛点：

  1. 知识是旧版本的——检索返回过期文档，越搜越错；
  2. 结论是黑盒的——大模型说了算，运维不敢照做；
  3. 执行是没有边界的——AI 能分析，却不该能直接动生产；
  4. 过程是留不住的——处理完就散了，无法复盘、无法沉淀。

所以我们的判断很明确：企业真正需要的，不是更会聊天的机器人，而是一个"结论有证据、动作有边界、过程有留痕"的 AI 同事。

2. 解决方案：给 AI 装"三道锁 + 一本账"（约 90 秒）

智维Agent 不是一个单点的 AI 调用，而是一套可信闭环。我们把一次运维任务拆成可运行的 eleven 步：

监测 → 分析 → 知识检索 → 证据验证 → 决策规划
→ 风险判断 → 人工审批 → 安全执行 → 结果验证 → 审计留痕 → 经验沉淀

用一句人话概括：AI 负责思考，人负责授权，系统负责留痕。

工程上，它由四端协同构成：

  • 前端 Vue 3 + Vite，用户层 / 管理员层双入口；
  • 后端 Spring Boot，管账户、权限、审计、附件会话；
  • AI 服务 FastAPI，管模型网关、对话编排、RAG；
  • Python Agent 框架（可插拔算法内核），五个核心模块：planner（规划）/ executor（执行）/ inspector（核查）/ memory（记忆）/ policies（策略），经 82 个单测验证；产品级运行闭环由后端 DecisionLoopService 承载。

但比"能跑起来"更重要的是——我们给这套系统装了三道锁和一本账：

  • 第一道锁：证据锁。 没有证据支撑的结论，不得表述为确定事实。
  • 第二道锁：风险锁。 AI 可以规划，但高风险动作必须人工审批，绝不允许自作主张。
  • 第三道锁：边界锁。 工具在沙箱与权限注册表里运行，能力被严格收口。
  • 一本账：审计账。 每一次判断与动作，都结构化留痕，可回溯、可复盘。

这就是智维Agent 与所有"套壳聊天机器人"的本质区别。

3. 现场演示（约 100–120 秒，衔接 demo-script.md）

演示只走两条主线，不铺页面。提前录好 60 秒兜底视频（见第 11 节）。

主线一：一次带证据的故障问答。
我用语音说"MySQL 连接数打满"，附一张现场截图。请大家看屏幕左侧——AI 的"思考过程"被拆成六个阶段逐条点亮：图像证据解析 → 知识检索 → 证据验证 → 任务规划 → 风险判定 → 生成回答。回答右侧会列出它引用了哪些来源、命中多少条证据、可信度评分（trust_score）是多少。

这里我要特别强调一个隐私取舍：语音在浏览器内识别、音频不出端；截图只传文件名、图片内容不上传。 我们演示多模态，但不以泄露用户隐私为代价。

主线二：一个被"拦下来"的高危动作。
Agent 拆解出一个"重启核心服务"的步骤。策略引擎立刻判定为高风险，自动转入人工审批队列——未经批准，它一步也动不了。我点击批准后，后端决策环在沙箱中执行该动作，并用我们自研的四级纠察（规则 → 证据 → AI → 状态核验）做结果核验——其中"假成功"检测会拿"声称已解决"对比"真实系统状态"，一票否决；最后在审计与运行记录里，你能看到一条完整的、带风险等级与审批人的条目。

这两条线合起来，就是我们要证明的事：AI 再强，也只在人允许的范围内、在可核查的边界内，可信地工作。

4. 算法与技术深度（约 90 秒）—— *本节是算法创新赛的得分核心*

评委老师最关心的，一定是"你们的算法到底深在哪"。我讲三个我们真正做了算法设计的点。

① 版本感知的混合检索 + 可信度评分算法。
通用 RAG 只解决"召回"，但中小企业最常见的故障不是"查不到"，而是"查到的是旧版本"。我们的做法是分层算法链：

  • 召回层：BM25 关键词召回与向量召回并行，避免单路径漏召回；
  • 过滤层：version_filter 按目标环境版本过滤候选，把"知识正确但版本不对"的噪音挡在门外；
  • 收敛层：词法重排器（lexical_reranker）对候选重新排序；
  • 表达层：检索结果聚合为 Citation（来源 / chunk / 版本 / 分数），并进一步聚合为 trust_score 可信度评分。

把"版本"做成检索的一等公民，这是与通用 RAG 的实质差异，也是我们的核心算法贡献之一。

② 多级证据验证算法（inspector 四级纠察）。
结果核查不是"比对字符串"，而是规则 → 证据 → AI → 状态核验四级融合：规则层做硬约束（风险误判、审批绕过、循环、无证据先动手），证据层做一致性校验（版本匹配、结论是否有据），AI 层做语义补充判定，最后由状态核验层拿"Agent 声称已解决"对比"真实系统状态"，一票否决"假成功"（false success）。其中前三级与状态核验都不依赖模型，保证安全判定不被一个"自信的模型"带偏。

③ 风险策略引擎。
policies 基于权限注册表与风险注册表，对每一步动作打风险等级，高危动作默认拒绝或转人工。它把"安全"从一句口号，变成插在每一步执行之前的可运行代码路径。

一句话：别人在"调提示词"，我们在"设计算法 + 工程化约束"。

5. 创新点（约 60 秒，按重要性讲 3 点）

  1. 可信闭环工程化（最重要）。把权限、风险、审批、核查、审计做成可运行的代码路径，而非文档理念。这是从"AI 对话"到"AI 运维"的关键一跃。
  2. 版本感知检索。解决"知识正确但版本不对"这一行业通病，把版本做成检索一等公民。
  3. 透明推理交互。让用户看见 AI 检索了什么、命中多少证据、判了什么风险——直接提升信任度。

补充创新（一句带过）：多模态隐私边界分层、插件化工具生态（Docker/K8s/MySQL/Nginx/Redis + MCP）、可切换模型网关（默认 mock 零密钥可复现）、双入口同源前端工程化。

6. 工程质量与可复现性（约 40 秒）

一个能拿奖的作品，必须经得起"能不能跑起来"的检验：

  • 前端：146 个页面组件，用户层 / 管理员层双入口构建通过（注：前端尚未建自动化测试套件，已通过构建与类型检查验证）；
  • 后端：656 个 @Test（87 个测试类），基于 H2（MySQL 兼容模式）跑真实迁移脚本；
  • 数据库：MySQL 8，119 张表，迁移脚本幂等，启动自动补齐；
  • 可复现：mock 模型零密钥即可跑通全链路，一键切换到 Ollama / OpenAI 兼容模型。评委老师可以自己拉下来跑。

7. 诚实边界：我们如何对待"还没跑出来的指标"（约 30 秒）—— *防坑必讲*

我必须坦诚一件事：当前仓库里模型训练与基准评测尚未接入真实模型与标注数据集，所以我没有拿"准确率 99%"这样的数字来包装自己。

但我把这当成一种工程成熟度的体现——我们专门搭建了诚实的评测框架：消融实验（RAG 链、Inspector 链）、基线对比链、 leakage 检测、指标契约（任务成功率 / 根因准确率 / 证据准确率 / Inspector 精确率召回率 / 幻觉率 / 假成功率 / 安全违规率）全部设计完毕，没有真实观测数据前，系统强制返回 NOT RUN，绝不编造数字。

在算法创新赛里，我反而认为：一个知道"哪些结论还不能下"的系统，比一个什么都敢编的系统更可信。 这不是缺点，这是我们对"可信 AI"四个字的交代。

8. 社会价值与商业潜力（约 40 秒）

  • 社会价值：把大厂才有的运维体系能力，以低成本交付给中小企业与高校实验室，降低对少数"老师傅"的个人经验依赖。
  • 商业潜力：SaaS 订阅（按席位）+ 私有化部署双形态；知识库与插件作为增值模块；模型用量分成。目标客户是 10–200 人规模企业。
  • 可推广性：默认 mock 可离线演示，适合教学、实训与竞赛场景。

9. 收尾（约 20 秒）

回到开头那句话——

企业不敢把生产环境，交给一个只会回答问题的 AI。
智维Agent 想做的，是让每一位运维工程师，都拥有一个可信、可控、可复盘的 AI 同事。

0. 先想清楚：评委到底在考什么

评委不是来听你念 PPT 的，他在快速判断四件事：

  1. 这是不是真东西（有没有跑起来的系统，还是 PPT 工程）；

所以你的每一句回答，都要能落回这四件事之一。切忌：堆名词、绕边界、背稿感。

1 分钟

中小企业运维"人手少、系统杂、知识散"，最怕两件事：AI 给错建议没人发现，AI 做错动作没人拦得住。通用聊天机器人解决不了"可信"。我们做了智维Agent：一次运维任务被拆成"监测→分析→检索→证据验证→规划→风险判断→人工审批→安全执行→结果验证→审计→沉淀"的闭环。检索带版本过滤和可信度评分，执行带风险分级和人工审批，全程审计留痕。它有四端：Vue 前端、Spring Boot 后端、FastAPI AI 服务、Python Agent 框架。默认 mock 零密钥就能跑通。

3 分钟 = 1 分钟 + 现场走一遍"高危动作被拦截→审批→执行→核查→审计"的主线 + 点出三个算法：版本感知混合检索、trust_score、四级纠察。

核心记忆句

AI 负责思考，人负责授权，系统负责留痕。
三道锁：证据锁 / 风险锁 / 边界锁；一本账：审计账。

2. 核心算法"通透"讲解（被深挖时用，这是算法创新赛的命门）

2.1 版本感知混合检索：到底怎么"混"的

真实实现（knowledge/retrieval/hybrid.py）：

  • 向量检索与 BM25 检索并行跑，且都传入同一个 version；
  • 两路结果各自按本路最大分归一化（score / max_score），消除量纲差异；
  • 融合公式：final = 0.6 × 向量归一化分 + 0.4 × BM25归一化分；
  • 按 chunk_id 合并去重、排序、取 top_k；
  • 权重 0.6/0.4 是可配置参数，不是写死。

版本过滤（version_filter.py）：version 为空或 "latest" 时不过滤；否则精确匹配 result.version。也就是说版本在召回阶段就已下推（search(..., version=...)），过滤是二次保险。

为什么这么设计（通透版）：

  • 单路检索必漏：向量擅长语义、BM25 擅长精确术语（如 max_connections、错误码），运维日志两者都重要，所以并行召回；
  • 归一化必须按路做：向量分是余弦相似度、BM25 分是无界词频分，直接相加会被 BM25 量级带偏；
  • 版本下推到召回，避免"先召回一堆旧版本、再过滤到空"。

必背的"边界"（评委爱问）：精确匹配偏保守，版本号写法不一致会误杀——这是刻意用精度换召回，因为运维场景"宁缺毋滥"；升级路径是语义化版本区间 + 版本归一化。

2.2 trust_score：可信度到底怎么算的

真实公式（knowledge/evidence/trust_score.py）：

trust_score = clamp( 0.5 × mean(证据分) + 0.3 × [结论被支持] + 0.2 × min(证据数/3, 1), 0, 1 )
  • 0.5：证据本身的平均相关度（检索有多准）；
  • 0.3：结论是否被证据支持（二值，来自证据一致性判定）；
  • 0.2：证据覆盖度，3 条封顶（避免靠堆条数刷分）；
  • 结果截断到 [0,1]，保留 4 位小数。

为什么这三项：一个可信的答案，必须"检索得准 + 结论有据 + 证据够量"，缺一不可。权重是可调初始值，后续用消融实验拟合。

通透点：trust_score 不是模型黑盒打分，它是可逐条溯源的——每条 Citation 带 source / chunk_id / version / score，评委问"0.82 怎么来的"，你能拆到每一项。

2.3 四级纠察：不是三级，是四级（这是加分点）

真实实现（agent/inspector/pipeline.py）：Rule → Evidence → AI → Verifier 四级，最后聚合成一个 InspectionResult。

级别做什么不依赖模型？
L1 Rule Judge确定性规则：风险误判、审批绕过、工具循环（>10 次）、无证据就做状态变更是（纯代码）
L2 Evidence Judge证据充分性、版本匹配、结论与证据一致性（词面重合：≥0.5 支持 / ≥0.2 部分 / 否则不支持）是（启发式）
L3 AI Judge语义级综合判定，可插拔 judge_fn，默认不绑定模型（passthrough）否（可注入模型）
L4 State Verifier拿"Agent 声称已解决"对比"真实系统状态"，抓 false success是（规则）

聚合状态机（_aggregate）：

  • 出现 false_success → REJECTED（一票否决，触发 Re-plan）；
  • 最高严重级为 HIGH/CRITICAL → VIOLATION；
  • 有其它 issue → WARN；否则 PASS；
  • VIOLATION / REJECTED 或高危 → requires_human = true。

为什么这是"算法"而不只是"工程"：它把"结果可信"建模成一个多信号融合 + 状态机聚合的判定问题，核心是假成功（false success）的检测——Agent 说"已解决"、系统 502 还在，这一票否决是 LLM 自己永远给不出的。

2.4 风险策略与安全守卫：两道闸

风险分类（agent/policies/risk.py）：

  • CRITICAL：server.delete、database.drop（禁止自动执行）；
  • HIGH：server.restart、server.stop、server.delete、shell.execute（必须人工审批）；
  • MEDIUM：其它 server.*；其余 LOW。

PolicyEngine：CRITICAL → 直接拒；HIGH 且未审批 → 拒并返回 requires_approval=true；其余放行。
SafetyGuard：权限不通过 → 拒；CRITICAL → 阻断；HIGH 且未审批 → 要求审批；否则放行。

通透点：为什么两道闸而不合并？职责分离——PolicyEngine 面向"计划步骤"做准入，SafetyGuard 面向"执行动作"做最后拦截，双保险防单点失效。这是安全工程里典型的 defense-in-depth。

2.5 透明推理（SSE）：哪些是真算的，哪些是呈现

真实实现（ai-service/app/services/chat.py 的 chat_stream）：产出三类事件 thinking / token / done；思考阶段 vision(有图才有) → retrieve → evidence → plan → risk → answer。

必须诚实的一点（防坑）：阶段里的 detail 用的是真实数据（图像张数、命中证据条数、top_k），但阶段推进有 0.15s 的节奏延时，plan/risk 在对话链里是标签位——真正的规划与风险判定在 agent/ 层执行。不要说"每个阶段都是后端实时算出来的"，说"阶段由真实请求数据驱动，视觉节奏做了演示优化"。

2.6 Agent 内核：为什么自研

  • planner 出带依赖的步骤；kernel 提供插件注册、依赖解析、事件总线、生命周期；registry 管 tool/skill/model/permission/risk 五类注册表；sandbox 管文件/进程/网络策略；providers 支持 mock/模型。
  • 自研理由：要的是"策略与审批优先"的执行模型，能把风险判定插在每一步执行之前；通用链式编排做不到这种"执行前拦截"。

B. 算法与检索（12 题）—— 算法创新赛重点

B1 ⭐🔥 你的"算法创新"到底在哪？
三点：① 版本感知混合检索 + trust_score 聚合；② 四级纠察（含 false-success 状态机）；③ 风险分级→审批闸门的策略算法。强调：不是调提示词，是可公式化、可溯源、可消融的设计。

B2 ⭐ 混合检索怎么融合？
见 §2.1：并行召回 → 各自 max 归一化 → 0.6/0.4 加权 → 合并去重排序。能报出权重是加分。

B3 🔥 为什么不用 RRF？
RRF 是秩融合、鲁棒；我们用的是归一化分加权，可调、可解释、能按场景调权重。两者都合理，RRF 在消融计划内。别贬低 RRF。

B4 🔥 只用 max 归一化，outlier 会不会压扁其他分？
会，这是 max 归一化的已知局限；min-max 又对最小值敏感。当前选它是因为简单稳定，接口可换。承认局限 + 给替代。

B5 ⭐ trust_score 公式？
0.5×证据均分 + 0.3×是否被支持 + 0.2×min(证据数/3,1)，截断[0,1]。见 §2.2。能背公式是"通透"的硬证据。

B6 🔥 0.5/0.3/0.2 怎么定的？凭什么？
初始启发式权重，代表"检索准 > 结论有据 > 证据量"的优先级；是可调参数，最终应由消融实验拟合。诚实说"经验初值 + 待数据标定"。

B7 向量嵌入用的什么？
默认轻量 hash_embedding（可复现、零依赖），可切换 Sentence Transformers。承认 hash 不是语义嵌入，它是演示默认，不是能力上限。

B8 🔥 版本过滤只是精确匹配，太粗暴？
是偏保守的精确匹配，latest 不过滤；优点是不放旧版本进来，缺点是同义版本号会误杀。这是用精度换召回，升级路径是语义化版本区间。

B9 检索效果怎么评？
knowledge/evaluation 有指标与样例集；但真实基准未跑（见 E 类）。可讲设计，不编数字。

B10 证据一致性怎么判的？
词面 token 重合率：≥0.5 SUPPORTED、≥0.2 PARTIALLY、否则 UNSUPPORTED（evidence_judge.py）。这是确定性启发式，好处是不会被"自信的错误答案"骗过；升级路径是语义模型/NLI。

B11 🔥 词重叠判一致性，语义相同但用词不同的情况怎么办？
承认：纯词面会漏"同义不同词"。所以它只是 L2 的确定性基线，L3 AI Judge 做语义补充；两者融合降低漏判。这是分层设计的意义。

B12 检索复杂度 / top_k 怎么定？
top_k 默认 5（可配）；两路各取 top_k 再融合，复杂度随候选线性；工程上够用，未做大规划压测。

一、项目理解 & 定位（5 题）

Q1：用一句话说清楚你做了什么？
A：一个可信 AI 智能运维平台——用"版本感知检索 + 证据验证 + 风险策略 + 人工审批 + 全程审计"，把大模型从"会回答问题"变成"可信地完成运维任务"。一句话：AI 负责思考，人负责授权，系统负责留痕。

Q2：为什么选"可信运维"这个方向？
A：中小企业"人手少、系统杂、知识散"，最怕两件事——AI 给错建议没人发现、AI 做错动作没人拦得住。通用聊天机器人解决不了这两个"可信"问题，这是真实且未被充分满足的需求。

Q3：你们的用户是谁？场景是什么？
A：10–200 人规模企业的运维负责人/驻场工程师、技术负责人，以及高校实验室/实训机房。核心场景：故障问答定位、版本感知知识检索、受控执行、结果核查与经验沉淀、团队协同。

Q4：和通用的"运维知识库"有什么区别？
A：知识库只解决"查得到"，我们解决"查得对版本 + 答得有证据 + 做得有边界 + 过程能复盘"。知识库是零件，我们是整机闭环。

Q5：项目做到什么完成度？
A：四端全栈可运行（Vue 前端 / Spring Boot 后端 / FastAPI AI 服务 / Python Agent 框架）；前端 npm test 494 项全过、后端 122 测试类；默认 mock 零密钥跑通全链路。模型训练与真实基准评测尚未接入（见第六类诚实题）。

二、算法 / 技术深度（8 题）—— *算法创新赛重中之重*

Q6：你们的"算法创新"具体在哪？
A：三点可量化算法设计——① 版本感知混合检索：BM25+向量并行召回 → version_filter 版本过滤 → 词法重排 → 聚合为 trust_score；② 四级证据核查（规则→证据→AI→状态核验）（inspector）：规则+证据+AI 融合判定，降假成功率；③ 风险策略引擎：基于权限/风险注册表给每步动作打级，高危转人工。

Q7：RAG 为什么不用现成框架（LangChain/LlamaIndex）？
A：现成框架解决"召回"，解决不了"版本过滤 + 证据表达 + 可信度聚合"。我们在 knowledge/retrieval/version_filter.py 与 knowledge/evidence/ 做了场景化扩展，且保留可评测指标。框架是工具，算法是我们自己写的。

Q8：trust_score 怎么算出来的？可解释吗？
A：由检索命中的 Citation（来源/chunk/版本/分数）聚合得到，可逐条溯源到具体知识条目与版本。它是"证据强度"的量化，不是模型黑盒打分——所以可解释、可复核。

Q9：向量嵌入用的什么？效果如何？
A：默认轻量 hash_embedding，可一键切换 Sentence Transformers。当前未跑真实基准（见诚实题），但这套接口与评测框架已就绪，接真实模型即可出数。

Q10：Agent 是单次 LLM 调用吗？规划怎么做？
A：不是。planner 把故障拆成有依赖关系的步骤（steps.py），executor 逐步调用工具，inspector 逐步核查，memory 沉淀长期经验。这是多模块协作，不是 chain 串接。

Q11：你们自研 Agent 框架，图什么？
A：我们需要"策略与审批优先"的执行模型，而不是链式编排。自研 kernel 提供插件注册、依赖解析、事件总线、生命周期，能把风险判定插在每一步执行之前——这是通用框架难以做到的。

Q12：四级证据核查（规则→证据→AI→状态核验）里"AI 判定"不会引入新幻觉吗？
A：所以才用三级融合而非单靠 AI。规则做硬约束、证据做一致性校验，AI 只做语义级补充判断，最终结论需多路一致。即便 AI 误判，规则与证据层仍能兜底，且全程留痕可追溯。

Q13：多智能体 / 团队 Agent 体现在哪？
A：后端 TeamAgentRunService + DecisionLoopService 支撑团队协同的智能体运行与决策循环；前端有团队工作区、Agent 运行与审批、通知。单智能体闭环 + 团队级协同是我们 Agent 能力的两个层次。

三、创新点（4 题）

Q14：你的最大创新点是什么？
A：可信闭环工程化——把权限、风险、审批、核查、审计做成可运行的代码路径，而非文档理念。这是从"AI 对话"到"AI 运维"的关键一跃，且每个创新点都有代码位置与演示路径可验证。

Q15：版本感知检索算创新吗？别人没做过？
A：版本过滤在文档管理里有，但把"版本"作为检索的一等公民并融入 RAG 可信度聚合，在通用运维场景里是实质性差异。中小企业最常见的故障正是"查到旧版本"，这是真实痛点驱动的创新，不是为创新而创新。

Q16：透明推理（思考可视化）是噱头吗？
A：不是。SSE 输出 thinking/token/done 三类真实事件，思考阶段由后端真实计算（含命中证据条数、图像证据条数），前端只是渲染。它直接提升运维人员对 AI 的信任度——而信任，正是"可信运维"的命脉。

Q17：你们有多少个创新点？会不会散？
A：文档列了七个（可信闭环、版本感知检索、透明推理、多模态隐私边界、插件化工具、可切换模型网关、前端工程化），但答辩只深讲最核心的 3 个，其余一句带过。评委要的是"深"，不是"多"。

A. 检索与算法（14 题）

A1 ⚠️ BM25 中文怎么分词的？
想挖：你有没有真处理中文。答：当前 tokenize() 用正则，连续中文整体当一个 token，未分词——所以长中文句召回弱，但英文标识符/错误码（max_connections、502）召回强，中文语义由向量路补。升级：jieba/HanLP 或字符 2-gram。证据：knowledge/retrieval/bm25.py。

A2 BM25 参数？
答：k1=1.5, b=0.75（经典默认），IDF 用 log(1+(N-df+0.5)/(df+0.5))。可调，未用数据调优——诚实说"经验默认值"。

A3 向量维度多少？相似度怎么算？
答：维度随嵌入后端而定；相似度用余弦（vector_store.py 手写实现，含零向量保护）。默认 hash 嵌入，可切 Sentence Transformers。

A4 ⚠️ 内存线性扫描，规模大了怎么办？
答：当前 InMemoryVectorStore 是 O(N) 线性，适合小语料/演示；规模化换 FAISS / pgvector / Milvus，search() 接口已隔离，替换不影响上层。诚实承认"没做大规模"。

A5 两路分数怎么融合？为什么 0.6/0.4？
答：各自按本路 max 归一化，再加权（向量 0.6、BM25 0.4）。权重是可配置初值，理由：语义是主诉求，精确词是补充。未用数据拟合——诚实。

A6 🔥 为什么不用 RRF？
答：RRF 秩融合鲁棒、免调参；我们用归一化分加权，可解释、可按场景调权。两者都合理，RRF 在消融计划里。别贬低 RRF。

A7 只用 max 归一化，离群值会压扁其他分？
答：会。max 归一化对离群敏感，min-max 又依赖最小值；当前选简单稳定版，可切。承认局限 + 给替代。

A8 版本过滤怎么做的？会不会误杀？
答：version 为空或 latest 不过滤，否则精确匹配 chunk.version（召回阶段已下推）。同义版本号会误杀 → 精度换召回，升级语义化版本区间。

A9 重排用的什么？为什么不用 cross-encoder？
答：词法重排（lexical_reranker.py）做确定性收敛；cross-encoder 效果好但重、需模型，当前为可复现选了轻量，是路线图。

A10 知识库怎么更新/增量索引？
答：文档解析→分块→嵌入→入索引；当前偏全量重建，增量索引是待补。诚实。

A11 多版本文档冲突怎么处理？
答：检索按目标版本过滤 + 证据层做版本一致性检查（不匹配给 WARNING）；这是"版本为一等公民"的落点。

A12 RAG 幻觉怎么压？
答：三层——提示词"无证据不下确定结论"；证据链让用户可核对；inspector 证据层判 SUPPORTED/UNSUPPORTED。承认不能完全消除。

A13 top_k 怎么定？
答：默认 5，可配；两路各取 top_k 再融合。未做系统性调参。

A14 你的检索"算法创新"能不能形式化？
答：能——融合是归一化加权函数；可信度是 0.5·mean(score)+0.3·support+0.2·coverage；纠察是"多信号 → 状态机"。都可写成公式、可消融，这是"算法"而非"调包"。

B. Agent 与执行（12 题）

B1 ⚠️ Planner 是 LLM 还是规则？
答：规则基线（关键词：含"nginx+状态"→查状态；含"重启/restart"→重启且 requires_approval=True；否则查知识库）。好处：确定性、可测、零成本。LLM Planner 是插件化替换项。证据：agent/planner/planner.py。别说成"LLM 自主规划"。

B2 规划失败/多步依赖怎么办？
答：当前规划是单步为主、带 requires_approval 标记；多步依赖结构与 Re-plan 在路线图。诚实。

B3 ⚠️ 工具执行失败会重试吗？有回滚吗？
答：没有自动重试/幂等键/回滚。Executor = 策略校验 → dry_run → 执行 → 审计；异常返回失败并记审计，交由 inspector 触发 Re-plan。幂等/回滚是明确的下一步。证据：agent/executor/executor.py。

B4 有 dry_run 吗？
答：有。context.dry_run=True 时只返回"未实际执行"+参数，不碰生产。演示安全动作时可先 dry_run。

B5 循环/滥用怎么防？
答：RuleJudge 统计单工具调用次数，>10 次判 LOOP（HIGH）。阈值可配。

B6 权限模型？
答：RBAC（角色/部门/岗位）+ PermissionChecker 允许角色集（admin/operator）；策略引擎 + SafetyGuard 双闸。

B7 Agent 内核有什么？
答：五类注册表（plugin/skill/tool/model/permission/risk）+ 事件总线 + 生命周期（MOUNTING→MOUNTED→FAILED→STOPPED）。证据：agent/kernel/runtime/runtime.py。

B8 插件怎么装？
答：AgentPlugin 契约注册，mount/unmount 生命周期；内置 Docker/K8s/MySQL/Nginx/Redis；MCP 适配器接外部。

B9 会话隔离/并发？
答：会话按 conversation_id 隔离；存储支持 Redis/MySQL/PostgreSQL/SQLite/文件五种。高并发未压测，诚实。

B10 上下文太长怎么办？
答：目前靠检索注入少量证据（top_k 小）+ 短期记忆；长上下文压缩/滑窗是待补。

B11 记忆怎么写入/遗忘？
答：短期上下文 + 长期 operator_memory；写入以处置结论为主；遗忘/衰减策略未细化，诚实。

B12 Agent 会不会自己"发明"工具？
答：不会。工具必须先在注册表注册，Executor 只执行已注册工具；未知工具直接返回"工具不存在"。

C. 证据与可信（10 题）

C1 trust_score 公式？
答：clamp(0.5·mean(证据分)+0.3·[被支持]+0.2·min(证据数/3,1), 0,1)，4 位小数。可逐项拆解。

C2 权重 0.5/0.3/0.2 凭什么？
答：经验初值（检索准 > 结论有据 > 证据量），待消融标定。诚实。

C3 ⚠️ 证据一致性用词重叠，太粗？
答：是确定性启发式（重合率 ≥0.5 支持 / ≥0.2 部分 / 否则不支持）。好处：不被"自信的错误答案"骗过；语义升级走 NLI/模型（L3）。

C4 四级纠察是哪四级？
答：Rule（规则）→ Evidence（证据）→ AI（可插拔）→ State Verifier（状态核验）。聚合：false_success→REJECTED；HIGH/CRITICAL→VIOLATION；其余有 issue→WARN；否则 PASS。

C5 假成功怎么判？
答：StateVerifier 拿"声称已解决/恢复"对比 actual_state.resolved；声称解决但实际 false → false_success → REJECTED + Re-plan。

C6 ⚠️ AI Judge 默认是空的，那"AI 判定"是不是摆设？
答：是可插拔钩子，默认 passthrough 保证"无模型也不阻塞安全链路"；生产注入评审模型。真正的确定性安全来自 Rule+Evidence+Verifier，不依赖 LLM——这反而是优点。

C7 审计日志能防篡改吗？
答：当前是结构化留痕 + 数据库存储；哈希链/WORM 未做，生产可接哈希链或不可变存储。诚实。

C8 怎么证明不是"自评自嗨"？
答：评测契约要求统一分组集、留 artifact hash、缺失记 null 不记 0、零分母不报 0；无观测强制 NOT RUN。这是防自嗨的机制。

C9 用户凭什么信 trust_score？
答：它是可溯源的（每条 Citation 带来源/版本/分数），不是模型黑盒；但权重未标定，所以定位是"证据强度参考"，不是"绝对正确率"。

C10 证据不足时系统怎么表现？
答：证据层给 WARNING/UNSUPPORTED；提示词要求"明确说明无法确认"；不会硬编一个确定结论。
