## 0. 30 秒讲清这个项目（电梯版，背到脱口而出）

> 我们做的是**智维 Agent**——一个敢让它动手的运维智能体。
> 现在企业用 AI 运维有个死结：**通用大模型会"说"，但不敢让它"做"**——因为它可能引错版本的文档、可能声称"已经重启成功"其实没成功、可能一条命令把生产环境干掉。
> 我们的解法是**三道锁一本账**：**证据锁**（每句话能追溯到知识条目）、**风险锁**（高危操作必须人工授权）、**边界锁**（命令白名单 + 黑名单 + 沙箱），最后**一本审计账**全程留痕。
> 技术上，检索用版本感知的混合检索，结果核查用**四级纠察**并能识别"假成功"，可信度用 trust_score 聚合。
> 全栈自研：后端 SpringBoot 80 张表 296 个接口，前端 Vue3 双入口 26+ 页面，AI 侧 Python 混合检索与纠察内核。
> 一句话：**AI 负责思考，人负责授权，系统负责留痕。**

## 1. 它到底解决什么问题

### 1.1 场景
中小企业的 Linux 服务器运维：没有专职 SRE，一个人管几十台机器，出问题靠"百度 + 试命令 + 祈祷"。

### 1.2 三个真痛点（评委最吃这套，因为它对应三个算法设计）

| 痛点 | 具体表现 | 我们的对应设计 |
|---|---|---|
| **知识错配** | 搜到 Ubuntu 22.04 的答案，但机器是 CentOS 6，`systemctl` 根本不存在 | **版本感知检索**（版本过滤 + 版本一致性核查） |
| **假成功** | AI 说"已重启 nginx"，其实服务根本没起来 | **四级纠察 + 假成功状态核验** |
| **不敢授权** | 一条 `rm -rf` 或 `iptables` 就能毁掉生产环境 | **风险四档分级 + 双闸 + 命令白/黑名单** |

## 4. 核心算法知识点（算法创新赛的命根子，必须滚瓜烂熟）

### 4.1 知识入库流水线
```
文件/文本 → 解析(.txt/.md/.pdf) → 切片 → 嵌入 → 内存存储
```
- 切片：`chunk_size=800, overlap=120`（`knowledge/config.py:6-7`），字符滑窗 `start = end - overlap`
- 嵌入：**HashEmbedding，256 维**（`embedding/hash_embedding.py`）—— 对每个 token 取 `sha256(token)[:4] % 256` 累加计数后 L2 归一化
- 存储：`InMemoryVectorStore.items` 列表，**进程内存，重启即失**

### 4.2 检索三件套

**① BM25**（`retrieval/bm25.py`）
- `k1=1.5`、`b=0.75`；`idf = log(1 + (N-df+0.5)/(df+0.5))`
- 分词：`re.findall(r"[\u4e00-\u9fff]+|[a-zA-Z0-9_]+")` → **中文连续汉字当成一个 token，不是真分词**（无 jieba 依赖）
- df **每次查询全量重算**，无倒排索引

**② 向量路**（`retrieval/vector_store.py:59-73`）
- 逐条 cosine 线性扫描；**无 FAISS / HNSW / Milvus**

**③ 融合**（`retrieval/hybrid.py:89-101`）
```
score = 0.6 × vector_norm + 0.4 × bm25_norm
```
- 归一化 = **各自除以本路最高分**（max 归一，**不是 min-max，也不是 RRF**）
- 按 `chunk_id` 合并去重，单路缺失记 0，`top_k=10`

### 4.3 版本感知（我们最独特的点）
- version 是 chunk 上的字符串字段，默认 `"latest"`（`config.py:17`）
- 过滤逻辑（`version_filter.py:8-15`）：空或 `latest` 不过滤，否则**只保留 version 完全相等**的
- **举例（评委最爱听例子）**：问"Ubuntu 22.04 如何重启 nginx？"，带 `version=ubuntu-22.04`，CentOS 6 的 `service nginx restart` 就不会混进答案
- 兜底：证据版本与环境版本不一致 → inspector 打 `VERSION/WARNING`

### 4.4 Reranker（默认启用）
`reranker/lexical_reranker.py:43-46`：`final_score = 0.7 × result.score + 0.3 × 词元重合率`，取 `top_k=5`

### 4.5 trust_score（可信度聚合，必背公式）
```python
score = 0.5 × evidence_score      # 各证据 score 的均值
      + 0.3 × support_score       # 是否被支持（1.0 / 0.0）
      + 0.2 × coverage            # min(证据数/3, 1)
```
（`knowledge/evidence/trust_score.py:28-37`，裁剪到 [0,1]，保留 4 位小数，无证据返回 0.0）

> **三个分量为什么这么定**：证据质量是基础（0.5），是否被支持是硬门槛（0.3），覆盖度防止"一条证据撑起一个结论"（0.2）。

### 4.6 四级纠察（Inspector，核心创新）
`agent/inspector/pipeline.py`

| 级 | 做什么 | 关键阈值 |
|---|---|---|
| L1 **Rule** | 声明风险 < 期望风险 → HIGH；HIGH/CRITICAL 且未获批 → CRITICAL；同工具调用 > 10 次 → HIGH（循环检测）；无证据却调用状态变更类动作 → HIGH | `loop_threshold=10` |
| L2 **Evidence** | 词元重合率 ≥ 0.5 → SUPPORTED；≥ 0.2 → PARTIALLY_SUPPORTED；否则 UNSUPPORTED；证据数 < 1 → WARNING；版本不符 → VERSION/WARNING | 4 级标签：SUPPORTED / PARTIALLY / UNSUPPORTED / CONTRADICTED |
| L3 **AI Judge** | **可插拔钩子，默认 passthrough 不调模型** | `judge_fn is None → return []` |
| L4 **Verifier** | 命中"已解决/已恢复/fixed/ok"等 9 个模式，但 `actual_state["resolved"]==False` → **假成功** | `false_success=True` |

**聚合结果**：无问题 → PASS；有问题 → WARN；严重度 HIGH/CRITICAL → VIOLATION；**假成功 → REJECTED**，并建议"触发 Re-plan"。

### 4.7 风险分级与安全双闸
- 四档：`LOW / MEDIUM / HIGH / CRITICAL`（`policies/risk.py:4-12`）
- 映射：`CRITICAL = {server.delete, database.drop}`；`HIGH = {server.restart, server.stop, server.delete, shell.execute}`；`server.*` → MEDIUM
- **双闸**：CRITICAL 一律禁止；HIGH 且未标记 `requires_approval` → 直接拒绝（`policy_engine.py:27,36-46`）
- **命令白名单**（`tools/builtin/shell.py:106-132`）：Linux 19 个（cat df du free grep head hostname id ip ls netstat pgrep ps pwd ss tail uname uptime whoami）+ Windows 3 个
- **黑名单**：`rm rmdir del format shutdown reboot kill pkill killall iptables nft systemctl service mount umount chmod chown useradd userdel passwd dd mkfs docker kubectl terraform`
- 还禁元字符 `| && || ; > >> < \` $( ${` 与危险参数 `--force --delete --privileged --device --cap-add --pid=host --network=host`
- 执行护栏：`timeout=20s`、输出截断 20,000 字符、强制 `shell=False`（不给 shell 解释）

## 8. 真相清单：哪些是真做、哪些是基线（**这一节决定你会不会翻车**）

主动说出来 = 真懂；被戳穿 = 造假。

| 模块 | 真实做法 | 生产该怎么做 | 一句话答法 |
|---|---|---|---|
| Embedding | SHA256 哈希桶伪嵌入 256 维；`lower().split()` 对中文退化为单 token | bge-m3 / text-embedding-3 + 中文分词 | "零依赖可复现的哈希基线，接口可替换；中文语义目前由词法路与重排兜底" |
| BM25 | 正则伪分词，每查全量重算 df | jieba/IK + 倒排索引 | 同上，且**这是我们有 reranker 的原因** |
| 融合 | 0.6/0.4 max 归一化加权和 | RRF 或 learned-to-rank | "小语料下 max 归一比 min-max 稳，参数留了网格搜索接口" |
| 向量检索 | 内存线性扫描 | FAISS/HNSW + 持久化 | "千级 chunk 内线性扫描够用，规模化换 FAISS" |
| Planner | **3 条 if/elif 关键词规则，最多 1 步** | LLM Planner（模板已写好） | "确定性基线先跑通可测；`PLANNER_PROMPT` 已就绪，替换成本是一个适配器" |
| AI Judge (L3) | **默认 passthrough，不调模型** | 接 LLM 做语义判定 | "**真正的安全靠 L1+L2+L4，不依赖 LLM**——这是设计选择，不是缺陷" |
| LLM | `provider` 默认 **mock**；设 `ollama` 且服务可达时**真实调用 Ollama（qwen3:1.7b）**（Java 侧 `MiniAssistantEngine` 即默认连本地 Ollama） | 真实 provider + 密钥托管 | "零密钥可复现是刻意的：评委/老师没 key 也能跑通全链路；有 Ollama/Key 时切真模型只需一个环境变量" |

## 10. 三个必须能默写的"为什么"

1. **为什么做版本感知？** —— 运维知识有强版本耦合，Ubuntu 的答案在 CentOS 上是错的，通用 RAG 不管这个。**这是我们和"接个大模型就完事"的根本差别。**
2. **为什么做假成功检测？** —— Agent 最大的风险不是不会做，是**声称做成了其实没做成**。L4 状态核验专门抓这个：命中"已解决"话术但实际 `resolved=false` → REJECTED。
3. **为什么安全机制不依赖 LLM？** —— L1 规则、L2 证据、L4 状态核验都是确定性判定，**AI Judge 默认不调模型**。用不确定的模型去守确定的安全底线，是设计错误。
