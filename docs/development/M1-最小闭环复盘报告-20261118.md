路线图给出的通过条件：

1. ≥ 20 个仿真故障场景**全量跑通**；
2. 处置成功率 SR 有明确基线值；
3. 所有指标可**一键重算**。

### 3.4 失败归因（9 例，两类）

**A. 根因证据源不可用：3 例（scene-07 / 14 / 21，全部 network_error）**

- 场景设计每 7 个场景模拟 1 次根因服务不可用（`index % 7 == 6`）。
- 策略正确选择保守路径：`根因证据缺失，无法确认根因；建议先人工核查，不执行变更。`
- 但期望动作为 `rollback`，因此计入 SR 失败。**这是安全行为正确、评测口径上的失败**。

**B. 根因 Top1 排序错误：6 例（scene-04 / 08 / 12 / 16 / 20 / 24）**

- 场景设计每 4 个场景注入 1 次真值非 Top1（`index % 4 == 3`），真值排名为 2/3/4。
- 策略对「真值不在 Top1」统一给出 `wait_and_observe`，与期望变更动作不符。
- **这 6 例直接指向根因排序能力（A@1），是 SR 的主瓶颈。**

### 3.5 天花板分析

| 假设 | SR |
|---|---|
| 当前基线 | 0.625 |
| 仅补齐根因服务可用性（3 例） | 0.75 |
| A@1 提升到 1.0 且证据可用 | 1.00 |

结论：**在现有策略下，SR 的上限 = A@1（0.75）**。「取证 → 研判」环节几乎完全依赖根因 Top1，这是 M2 场景路由与候选重排最直接的价值锚点。

## 四、关键设计与经验

### 4.1 EvidenceBundle：先归一，再压缩，显式标注缺失

四路工具返回结构完全不同，直接回填 Prompt 会导致两个问题：上下文膨胀、字段名混淆。`EvidenceBundle` 只做两件事——归一与压缩，不做解释、不参与决策，边界清晰。

经验：**「缺失」必须是一等公民**。渲染时对未调用 / 不可达 / 报错的证据源显式输出「不要假设该维度结论」，这是本次 Halluc% = 0 的直接原因；如果只在这些源缺席时不输出内容，模型极易补全。

### 4.2 去重守卫：指纹化 + 不中断

`工具名 + 规范化参数` 作为指纹，重复调用不进执行器，而是把「已拦截」作为 Observation 回灌，并显式提示「请基于已有证据继续研判，或改用其他证据源」。

经验：**约束要做成可恢复的反馈，而不是硬失败**。直接抛错会让小模型陷入同一动作循环；回灌提示语能把它推向下一个证据源。这也是 Invalid% = 0、Calls 稳定为 4 的原因。

### 4.3 收尾链路：所有写回失败 fail-open

`IncidentClosure` 在反思、记忆写入、案例库写回三个环节全部 try/except，失败只记 `reason`，不中断主链路。评测中 writeback_ok% = 100%，说明链路本身稳定；同时该设计保证了「收尾失败不会反过来污染诊断结论」。

**复盘后补充**：收尾的 `outcome` 判定不能只靠推断（见 6.1 节修复）。经验：**任何涉及「成功 / 失败」二值的语义，都应该显式提供布尔入参让调用方注入，推断只做 fallback**。推断拿到的是状态（completed / needs_approval），而不是"这次处置是否达成目标"——两者有本质区别，混为一谈会导致失败经验被打成功标签、污染记忆学习。

### 4.4 可复现优先于真实感

demo 用确定性策略模型替代真实 LLM、用离线回放替代真实 HTTP，换来的是：同一份代码每次跑出完全相同的指标。

经验：**在口径还没冻结时，可复现性比真实感更重要**。真实服务接入是替换两个类（`PolicyProvider` / `ScenarioReplayHttp`）的事，口径与统计代码零改动。

## 六、问题与风险

### 6.0 已修复：`outcome` 与 SR 语义不一致（2026-11-18 同轮修复）

**现象**（修复前）：24 条归档记录 `outcome` 全部为 `resolved`，但其中 9 条 `success=false`。

**根因**：[_infer_outcome](file:///d:/SmartOpsAgent/agent/planner/closure.py#L231-L239) 只判断 `result.status == "completed"` 且反思 `pass`，未校验「最终动作是否与根因判断一致」。策略对「证据缺失」给出保守结论时，执行状态仍是 completed、反思仍 pass，于是被判为 resolved。

**影响**（修复前）：失败案例被打上 `resolved` 标签写入长期记忆与案例库，`nn.retrieve` 后续会把失败经验当成功经验召回，直接污染 M1-6 建立的学习闭环。

**修复方案**：

- [IncidentClosure.close()](file:///d:/SmartOpsAgent/agent/planner/closure.py#L143) 新增 `success: bool | None = None` 入参
- 新增 [_resolve_outcome()](file:///d:/SmartOpsAgent/agent/planner/closure.py#L244-L263) 统一决策，优先级：显式 `outcome` → 显式 `success` → 推断
- `success=False` 时绝不再判为 `resolved`；按 `result.status` 降级为 `mitigated / pending / failed`
- [bench_m1_closure.py](file:///d:/SmartOpsAgent/ai-service/scripts/bench_m1_closure.py#L305-L318) 把 ground truth 对照算出的 `success` 显式传入

**修复后效果**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| outcome=resolved | 24/24（含 9 个失败场景） | **15/15**（仅成功场景） |
| outcome=mitigated | 0/24 | **9/9**（全部 SR 失败场景） |

**回归验证**：`tests/agent` 384 passed、`ai-service/app/tests` 417 passed。两个未改的 closure 单测继续绿（它们没有 ground truth，靠 fallback 推断）。

以下为仍待处理的风险：

### 6.1 P1｜证据源不可用时无跨源兜底

3 例 network_error 全部因根因服务不可用而只能保守等待。日志分类与案例检索其实仍可用，但没有形成「日志类别 + 历史案例」的兜底根因推断。

**建议**：在 `EvidenceBundle` 之上增加轻量兜底：根因缺失但日志类别明确且历史案例 Top1 类别一致时，允许给出低置信度动作建议，而不是直接放弃。需同步定义置信度门槛，避免把兜底变成新的幻觉源。

### 6.2 P1｜SR 被 A@1 锁死，缺少候选重排

SR 上限等于 A@1，说明链路没有对「Top1 可能是错的」做任何二次校验。可用的现成信号（日志类别与候选 metric 的一致性、案例检索类别、候选分数间隔）均未被利用。

**建议**：M2 已完成 GraphSAGE/TGAT/TGPM 消融与场景路由，其价值应体现在 A@1 提升上；同时补一层轻量重排（规则或小模型），对 Top1/Top2 分数接近的样本做二次判别。这是提升 SR 性价比最高的方向。

### 6.3 P2｜Token 成本偏高且随轨迹线性增长

单次 11353.8 tokens，仅 4 次工具调用，说明 Prompt 中累积了完整 Thought/Action/Observation 历史。场景数扩大后会显著放大成本。

**建议**：历史轨迹超过 N 轮后做摘要化（保留动作与关键 Observation，丢弃完整 JSON）；`evidence_budget` 已有 1200 字符上限，可再对 `history` 设预算。

### 6.4 P2｜MTTR 口径不是真实测量值

MTTR 由场景直接注入 `40 + 8 × truth_rank (+25)`，本质是「排名惩罚项」，不包含真实的检测延迟、审批等待、执行耗时。

**建议**：对外引用时明确标注「仿真口径」；接入真实服务后改为时间戳差值采集，并与当前值并列展示，避免口径漂移。

### 6.5 P2｜F1 不代表模型精度

F1 0.9474 来自 fixture 的检出点与真值标签对比，检测器被设计为「真值全覆盖 + 每 3 个场景 2 个误报」。它验证的是统计口径正确，不是异常检测模型的真实能力。

**建议**：所有对外材料引用该指标时必须带「合成数据 / 离线回放」限定词。

### 6.6 P3｜场景覆盖偏单点

24 个场景覆盖 7 类单故障，缺少：多根因、级联故障、指标与日志矛盾、根因服务超时（而非不可用）、工具参数错误等边界场景。

**建议**：M3 评测场景数翻倍时，优先补「证据冲突」与「多根因」两类，它们最能暴露决策层的真实短板。

## 七、结论

1. **M1 验收门达成**：24 个场景全量跑通，SR 0.625 基线明确，指标一键重算且完全可复现，384 + 417 单测全绿。
2. **护栏类目标超额达成**：Invalid% = 0、Halluc% = 0、writeback 100%，说明 M1-2 证据归一与 M1-3 去重守卫这两个「防劣化」设计是有效的。
3. **能力瓶颈已定位且可量化**：SR 的 9 个失败全部可归因（6 个根因排序、3 个证据可用性），且 SR 上限等于 A@1，改进路径清晰。
4. **原语义缺陷已修复**：报告生成后同轮修复 `outcome` 语义（6.0 节），记忆库污染风险已解除——这是 M1 暴露的最关键非能力缺陷，修复代价小但杠杆极高。
5. **M1 的真正产出不是 0.625 这个数字，而是一套冻结的口径 + 一条可替换的管线**：M2 的场景路由（GraphSAGE / TGAT / TGPM）与 M3 的模型增强，都可以在同一套指标下直接比较 Δ。
