## 0. 目标服务器与全局铁律

- 服务器：阿里云 ECS **8核16G + 100G 系统盘 + 200G ESSD 数据盘 + 5M 带宽**（选型见 2026-11-16 会话结论，约 8800 元/年）。
- 操作系统建议 Ubuntu 22.04 / Alibaba Cloud Linux 3。

**铁律（违反任何一条即停手）**

1. **不打满系统盘**：所有耗磁盘/耗内存的注入只作用于 `/data`（数据盘挂载点）或专用 loop 设备。系统盘剩余空间低于 20% 立即中止清理。
2. **注入前先快照**：每个场景动手前，控制台对该实例打一次快照（或至少 `tar` 备份 `/data/smartops`）。恢复不了就回滚快照。
3. **凭证零落盘**：`.env`（含 MYSQL_ROOT_PASSWORD / MYSQL_PASSWORD / REDIS_PASSWORD / SMARTOPS_API_KEY_ENCRYPTION_KEY / SMARTOPS_INTERNAL_TOKEN / SMARTOPS_CHAT_RUN_TOKEN_SECRET）只放服务器 `~/.smartops/.env`，`chmod 600`，**绝不进 git**。
4. **长命令一律跑在 tmux**（`tmux new -s perf08`），断线不丢进度。
5. 每场景一份证据记录，落到本仓库 `docs/development/`，命名 `故障场景X-证据记录-<日期>.md`；训练语料落 `data/fault-corpus/<场景>/`。

**目录布局约定**

```
/data/smartops/            # 仓库克隆（工作区）
/data/inject/              # 故障注入专用（loop 镜像、临时文件），随场景可整体删除
/data/metrics/             # 30 分钟指标采集落盘
/data/fault-corpus/        # 带标签训练语料（JSONL）
```

**一次性环境准备**

## 1. PERF-08：真实镜像 + 探针 + 资源声明 + 扩缩容（P0）

**验收口径**：干净环境用发布产物启动声明的真实链路；指标连续 30 分钟可抓取；1→3→1 副本扩缩容；失败可回退。

### 1.1 构建并推送真实镜像（阿里云 ACR 个人版，免费）

```bash
# ACR 控制台创建 个人实例 + 命名空间（如 smartops），获得登录地址 <region>.cr.aliyuncs.com
docker login <region>.cr.aliyuncs.com -u <ACR用户名> -p <ACR密码>

cd /data/smartops
docker build -t <region>.cr.aliyuncs.com/smartops/backend:v1 backend/
# 注意：ai-service 的构建上下文必须是仓库根目录（chat.py 里 from agent...，见 compose 注释）
docker build -t <region>.cr.aliyuncs.com/smartops/ai-service:v1 -f ai-service/Dockerfile .
docker push <region>.cr.aliyuncs.com/smartops/backend:v1
docker push <region>.cr.aliyuncs.com/smartops/ai-service:v1
```

### 1.2 用 K3s 编排（推荐，与场景④共用集群）

> **已知坑，必须处理**：`deploy/docker/docker-compose.yml` 里 backend 有固定 `container_name` 和固定端口映射 `8080:8080`，**直接 `--scale backend=3` 必然冲突**。扩缩容统一走 K3s（Deployment + Service），不要用 compose scale。若坚持 compose，需先去掉 container_name 并改端口区间——不推荐。

```bash
curl -sfL https://get.k3s.io | sh -s - --write-kubeconfig-mode 644
export KUBECONFIG=/etc/rancher/k3s/k3s.yaml

# 编排文件落 deploy/k8s/backend-deployment.yaml，要点：
#   image: <region>.cr.aliyuncs.com/smartops/backend:v1   （imagePullSecrets 配 ACR 凭证）
#   replicas: 1
#   readinessProbe: httpGet path=/actuator/health/readiness port=8080
#   livenessProbe:  httpGet path=/actuator/health/liveness  port=8080
#   resources: requests={cpu:500m,memory:512Mi} limits={cpu:2,memory:1Gi}
#   env 从 Secret 注入（kubectl create secret generic smartops-secrets --from-env-file ~/.smartops/.env）
kubectl apply -f deploy/k8s/backend-deployment.yaml
kubectl get pods -w    # 期望 Ready 1/1
```

### 1.3 指标连续抓取 30 分钟

```bash
# 优先 Prometheus 端点；未启用则逐端点抓（二选一，如实记录用的是哪种）
nohup bash -c 'for i in $(seq 1 120); do
  curl -fsS http://127.0.0.1:8080/actuator/prometheus >> /data/metrics/prom-$(date +%H%M).txt 2>/dev/null
  curl -fsS http://127.0.0.1:8080/actuator/metrics >> /data/metrics/idx-$(date +%H%M).json 2>/dev/null
  sleep 15
done' > /dev/null 2>&1 &
# 30 分钟后核对：文件数 >= 119、无连续空洞，即"连续可抓取"成立
```

### 1.4 扩缩容 1→3→1 与回退

```bash
kubectl scale deployment backend --replicas=3 && kubectl get pods -w   # 期望 3/3 Ready
kubectl scale deployment backend --replicas=1 && kubectl get pods -w   # 期望回 1/1

# 失败可回退：推一个故意坏的 v2（镜像 tag 不存在）→ 观察滚更失败 → rollout undo
kubectl set image deployment/backend backend=<region>.cr.aliyuncs.com/smartops/backend:v2-bad
kubectl rollout status deployment/backend --timeout=60s   # 期望失败
kubectl rollout undo deployment/backend                   # 期望回滚到 v1，服务恢复
```

**勾选门禁**：干净环境纯发布产物可起 → 30min 指标 ≥119 个采集点 → 1→3→1 全 Ready → 滚更失败可 undo 回退。四条全过才可销项。

## 2. 场景① Nginx 502（P1）

**注入 → 观测 → 诊断 → 恢复 → 验证** 完整闭环。

```bash
# 2.1 前置：宿主机 Nginx 反代 backend
cat > /etc/nginx/conf.d/smartops.conf <<'EOF'
server {
  listen 8002;
  location / { proxy_pass http://127.0.0.1:8080; }
}
EOF
nginx -t && systemctl reload nginx
curl -fsS http://127.0.0.1:8002/actuator/health/readiness    # 基线 200

# 2.2 注入：停掉 backend 容器
cd /data/smartops/deploy/docker && docker compose stop backend

# 2.3 观测故障
curl -i http://127.0.0.1:8002/actuator/health/readiness      # 期望 502 Bad Gateway
tail -n 5 /var/log/nginx/error.log                           # 期望 connect() failed upstream

# 2.4 恢复
docker compose start backend
sleep 75   # 等待 start_period=60s + readiness 通过

# 2.5 验证恢复
curl -fsS http://127.0.0.1:8002/actuator/health/readiness    # 期望 200，连续 10 次/1 分钟无 502
```

**勾选门禁**：真实 502 触发 → nginx error.log 留痕 → 恢复动作执行 → 恢复窗口内探针连续 200。同时跑一次 SmartOpsAgent 自身诊断链路（ai-service 聊天/工具链定位"upstream 失联"），诊断结论留证据。

## 3. 场景② MySQL 连接耗尽（P1）

compose 已声明 `--max-connections=200`，直接利用。

```bash
cd /data/smartops/deploy/docker
set -a; source ~/.smartops/.env; set +a

# 3.1 注入：205 个空闲连接占满（>200 必然被拒）
for i in $(seq 1 205); do
  docker exec smartops-mysql mysql -usmartops -p"$MYSQL_PASSWORD" \
    -e "SELECT SLEEP(600)" >/dev/null 2>&1 &
done
sleep 5

# 3.2 观测故障
docker exec smartops-mysql mysql -usmartops -p"$MYSQL_PASSWORD" -e "SELECT 1"
# 期望：ERROR 1040 (HY000): Too many connections
docker exec smartops-mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" \
  -e "SHOW STATUS LIKE 'Threads_connected'; SHOW PROCESSLIST" | head -20

# 3.3 恢复：清理空闲会话
docker exec smartops-mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" \
  -e "SELECT CONCAT('KILL ', id, ';') FROM information_schema.processlist WHERE command='Sleep'" \
  > /tmp/kill.sql
docker exec -i smartops-mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" < /tmp/kill.sql
pkill -f "SELECT SLEEP" || true

# 3.4 验证恢复
docker exec smartops-mysql mysql -usmartops -p"$MYSQL_PASSWORD" -e "SELECT 1"   # 期望成功
curl -fsS http://127.0.0.1:8080/actuator/health/readiness                        # 期望 UP
```

**勾选门禁**：触发 1040 错误 → SHOW PROCESSLIST 证据 → 恢复后新连接成功且探针 UP。

## 4. 场景③ Redis 内存压力（P1）

```bash
cd /data/smartops/deploy/docker
set -a; source ~/.smartops/.env; set +a
R="docker exec smartops-redis redis-cli --no-auth-warning -a $REDIS_PASSWORD"

# 4.1 前置：临时把 maxmemory 降到 256MB（注入后改回）
$R CONFIG SET maxmemory 256mb
$R CONFIG SET maxmemory-policy noeviction   # 明确出现 OOM 写错误，便于观测

# 4.2 注入：写 512 个 1MB key（共 ~512MB，远超上限）
for i in $(seq 1 512); do
  $R SET "inject:m:$i" "$(head -c 1048576 /dev/zero | base64 | head -c 1048576)" 2>&1 | tail -1
done

# 4.3 观测故障
$R INFO memory | grep -E "used_memory_human|maxmemory_human|evicted_keys"
$R SET inject:probe 1      # 期望：OOM command not allowed when used memory > 'maxmemory'
$R GET inject:m:1          # 读不受影响（noeviction 下），如实记录现象

# 4.4 恢复
$R EVAL "for _,k in ipairs(redis.call('keys','inject:*')) do redis.call('del',k) end return 'ok'" 0
$R CONFIG SET maxmemory-policy allkeys-lru
$R CONFIG SET maxmemory 0   # 恢复无上限（与原 conf 一致为准）

# 4.5 验证恢复
$R SET inject:verify ok && $R GET inject:verify && $R DEL inject:verify
curl -fsS http://127.0.0.1:8080/actuator/health/readiness
```

**勾选门禁**：OOM 写错误留痕 → INFO memory 证据 → 清理后 SET/GET 正常且探针 UP。恢复后用 `CONFIG GET maxmemory*` 确认配置已还原，避免残留影响后续场景。

## 5. 场景④ K8s Pod 异常（P1，依赖 §1.2 的 K3s）

用一个小 Deployment `demo-app`（与 backend 分离，避免互相干扰）注入三种典型异常：

```bash
export KUBECONFIG=/etc/rancher/k3s/k3s.yaml

# 5.0 部署基线 demo-app：3 副本 nginx:alpine + livenessProbe path=/ port=80
#     （yaml 落 deploy/k8s/demo-app.yaml）

# 5.1 异常A ImagePullBackOff：镜像 tag 改成不存在
kubectl set image deployment/demo-app nginx=nginx:no-such-tag
kubectl get pods   # 期望 ImagePullBackOff
kubectl rollout undo deployment/demo-app && kubectl get pods -w   # 期望恢复 3/3

# 5.2 异常B CrashLoop（liveness 必败）
kubectl patch deployment demo-app --type=strategic \
  -p '{"spec":{"template":{"spec":{"containers":[{"name":"nginx","livenessProbe":{"httpGet":{"path":"/must-fail","port":80},"periodSeconds":5}}]}}}}'
kubectl get pods   # 期望重启计数持续上涨
kubectl rollout undo deployment/demo-app

# 5.3 异常C OOMKilled：限 8Mi 内存必然被杀
kubectl patch deployment demo-app --type=strategic \
  -p '{"spec":{"template":{"spec":{"containers":[{"name":"nginx","resources":{"limits":{"memory":"8Mi"}}}]}}}}'
kubectl get pods --field-selector=status.phase!=Running   # 期望 OOMKilled
kubectl rollout undo deployment/demo-app

# 5.4 验证恢复
kubectl get pods -l app=demo-app   # 3/3 Running，重启计数不再增长
```

**勾选门禁**：三种异常各自的 `kubectl describe pod` / `kubectl get events` 留痕 → rollout undo 恢复 → 最终 3/3 Ready。诊断层同样接入 SmartOpsAgent 定位结论。

## 6. 场景⑤ 磁盘 / inode 耗尽（P1，loop 设备隔离）

```bash
# 6.0 造一块独立 2G 文件系统挂在 loop 上——绝不碰系统盘与数据盘本体
dd if=/dev/zero of=/data/inject/fs2g.img bs=1M count=2048
mkfs.ext4 /data/inject/fs2g.img
mkdir -p /mnt/inject && mount -o loop /data/inject/fs2g.img /mnt/inject
df -h /mnt/inject

# 6.1 注入A 空间耗尽
fallocate -l 1900M /mnt/inject/big.bin
df -h /mnt/inject                       # 期望使用率 ~99%
dd if=/dev/zero of=/mnt/inject/probe.bin bs=1M count=10
# 期望：No space left on device

# 6.2 恢复A
rm /mnt/inject/big.bin && df -h /mnt/inject      # 期望可用空间恢复
dd if=/dev/zero of=/mnt/inject/probe.bin bs=1M count=10 && rm /mnt/inject/probe.bin   # 写入正常

# 6.3 注入B inode 耗尽
mkdir -p /mnt/inject/inodes
for i in $(seq 1 300000); do : > /mnt/inject/inodes/f$i; done
df -i /mnt/inject                       # 期望 IUse% 100%
: > /mnt/inject/inodes/new.txt          # 期望 No space left on device（inode 用尽）

# 6.4 恢复B
rm -rf /mnt/inject/inodes && df -i /mnt/inject   # 期望 IUse% 回落
: > /mnt/inject/probe.txt && rm /mnt/inject/probe.txt   # 正常

# 6.5 收尾：卸载并删除注入盘
umount /mnt/inject && rm /data/inject/fs2g.img
```

> 验收若要求"业务探针恢复"，可把某个服务日志目录软链指向 `/mnt/inject` 注入，再切回——按验收口径如实做，不做就写明。

**勾选门禁**：空间/inode 双注入各自触发写失败 → `df`/`df -i` 留痕 → 删除恢复 → 写入探针正常。

## 7. 训练语料落盘规范（每场景必做）

每场景一次注入-恢复循环 = 一条 JSONL 记录，落 `/data/fault-corpus/<场景>/event-<时间戳>.jsonl`：

```json
{"scenario":"mysql-conn-exhaust","ts":"2026-11-17T10:30:00+08:00",
 "fault_signal":{"error":"ERROR 1040 Too many connections","threads_connected":200},
 "metrics_excerpt":{"mysql_threads_connected":200,"backend_readiness":"DOWN"},
 "log_excerpt":"…SHOW PROCESSLIST 输出节选…",
 "root_cause":"空闲连接占满 max_connections=200，无连接池回收",
 "recovery_action":"KILL Sleep 会话 + 杀注入脚本",
 "verify_result":"新连接成功，readiness UP，观察 5 分钟无复发"}
```

- 多跑几轮（每场景 ≥3 轮）即可形成带标签训练集；根因/恢复动作字段由人工确认后写死，**不伪造**。
- 语料定期 `tar` 打包回传本机入库，服务器不留副本时可删除。
