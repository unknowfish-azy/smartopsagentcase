## 2. OPS-14 实现与验收口径

### 2.1 数据模型（[V20261106.15__finops.sql](file:///d:/SmartOpsAgent/backend/src/main/resources/db/migration/V20261106.15__finops.sql)）

- `finops_cost_record`：`(user_id, source_id, resource_id, billing_month, currency)` 唯一，重放同批次更新而不是重复入账；
- `finops_usage_sample`：`(user_id, resource_id, sampled_at)` 唯一，只存观测值；
- `finops_budget`：`(user_id, name, billing_month)` 唯一；
- 金额统一存 `amount_minor BIGINT`（最小货币单位），不使用浮点；币种为 ISO-3 大写。

### 2.2 归集与汇总（[FinOpsService.java](file:///d:/SmartOpsAgent/backend/src/main/java/com/smartops/finops/FinOpsService.java)）

| 接口 | 证据与约束 |
| --- | --- |
| `POST /api/finops/costs` | 校验批次、账期 `YYYY-MM`、资源 ID、金额 ≥0、币种 3 位；重放按唯一键 upsert，返回 `created/updated` |
| `GET /api/finops/summary?month=` | 按 `currency` 各自汇总，**绝不跨币种相加**；`allocationKey` 为空的记录单列 `unallocatedTotals`，不猜测归属 |
| `GET /api/finops/trend?months=` | 以数据中最新账期为终点倒推，只返回真实存在的账期点；无数据返回空列表，不补零 |
| `POST /api/finops/usage` | 0..100 范围校验、来源必填、时间必填、至少一个指标；同一资源同一时刻覆盖写入 |
| `GET /api/finops/recommendations` | 见 2.3 |
| `POST /api/finops/budgets` | 同名同账期重复创建返回 `FINOPS_BUDGET_EXISTS` |
| `GET /api/finops/budgets/status?month=` | 见 2.4 |

### 2.3 容量建议与采样门槛

窗口必须满足 `0 < windowEnd - windowStart ≤ 31 天`，否则 `FINOPS_WINDOW_INVALID`。每条建议都带：

`windowStart`、`windowEnd`、`windowSeconds`、`sampleCount`、`coverageRatio`、`cpuP95/memoryP95/diskP95`、`costSources`、`currency`、`monthlyAmountMinor`、`allocationKey`、`unallocated`。

判定顺序与业务约束：

1. `sampleCount < 24` 或 `coverageRatio < 0.8` → `INSUFFICIENT_SAMPLES` / `COLLECT_MORE`，**不产出规格建议**；
2. `diskP95 ≥ 90` → `DISK_PRESSURE` / `EXPAND_DISK`；
3. `cpuP95 ≤ 5` 且 `memoryP95 ≤ 10` → `IDLE` / `STOP_OR_RIGHTSIZE`；
4. `cpuP95 ≤ 20` 且 `memoryP95 ≤ 30` → `OVERPROVISIONED` / `RIGHTSIZE_DOWN`；
5. `cpuP95 ≥ 85` 或 `memoryP95 ≥ 90` → `UNDERPROVISIONED` / `RIGHTSIZE_UP`；
6. 其余 → `NORMAL` / `KEEP`。

`estimatedSavingMinor` 恒为 `null`：系统只描述方向，不把"降配幅度"换算成金额，避免虚构节省。无账单的资源仍可评估容量，但 `currency=null`、`monthlyAmountMinor=0`、`costSources=[]`。

P95 采用 nearest-rank（升序第 `ceil(0.95*n)` 个），不做插值。

### 2.4 预算与成本异常

- 预算按 `currency + allocationKey` 匹配实际成本；`allocationKey` 为空表示该币种全部成本；
- `utilization = actual / budget`，超过即 `exceeded=true`，同时返回实际成本来源 `costSources`；
- 异常只比较"上月同币种同标签"与"上月同资源"两类，`previousMinor` 缺失时**直接跳过**，不按 0 或按当前值回填；
- `changeRatio` 保留 4 位小数。

### 2.5 验证方式

建议必须先满足采样门槛，再按 P95 分类；预算状态与异常可用上月真实账期复核。集成测试覆盖：币种/标签汇总、幂等与校验、趋势不补零、利用率校验、采样不足/覆盖不足、空闲/磁盘/超载/无账单分类、窗口校验、预算超支与环比异常。

## 3. OPS-15 实现与验收口径

### 3.1 数据模型（[V20261106.16__security_posture.sql](file:///d:/SmartOpsAgent/backend/src/main/resources/db/migration/V20261106.16__security_posture.sql)）

- `security_scan_report`：`(user_id, report_ref)` 唯一；必填 `tool / tool_version / scope / target / started_at / finished_at / content_sha256`；
- `security_finding`：`(user_id, finding_key)` 唯一；保存 `first_seen_at / last_seen_at / seen_count / last_report_id / status / exception_*`；
- `security_report_finding`：报告与命中的关联，用于回答"这份新报告里还有没有这条命中"。

### 3.2 报告接入

`POST /api/security/reports`：

- `tool` 仅接受 `TRIVY / KUBE_BENCH / FALCO`，其它返回 `SECURITY_TOOL_UNSUPPORTED`；
- `toolVersion / scope / target / startedAt / finishedAt` 必填，`finishedAt > startedAt`；
- 未提供 `contentSha256` 时由服务端按 `tool|target|reportRef|startedAt|finishedAt|findingKey...` 计算；
- 严重度归一到 `CRITICAL/HIGH/MEDIUM/LOW/UNKNOWN`，无法识别的级别一律 `UNKNOWN`，不擅自升级或降级；
- 同一报告内重复命中按 key 去重，`findingCount` 为去重后数量；
- 重复 `reportRef` 返回 `SECURITY_REPORT_EXISTS`。

### 3.3 去重与状态机

`finding_key = sha256(tool|target|ruleId|location)`，由服务端计算。跨报告再次出现时：

- 保留 `first_seen_at`，更新 `last_seen_at / seen_count / last_report_id`；
- 已 `FIXED`/`EXPIRED` 的命中再次出现 → `REOPENED`，清空修复与例外时间；
- 例外未到期则保持 `EXCEPTION`，到期后再次出现 → `REOPENED`。

### 3.4 修复复测与例外

| 接口 | 约束 |
| --- | --- |
| `POST /api/security/findings/{id}/verify-fix` | 报告必须同工具同目标（否则 `SECURITY_VERIFY_REPORT_MISMATCH`）；必须晚于最近一次命中的报告（否则 `SECURITY_VERIFY_REPORT_NOT_NEWER`）；报告不含该 key → `FIXED`，写 `fixed_at=报告完成时间`、`verified_at=核验时间`；仍含该 key → 如实返回 `stillPresent=true` 与当前状态 |
| `POST /api/security/findings/{id}/exception` | 已 `FIXED` 拒绝；`until` 必须晚于当前时间；`reason` 必填；写入后状态 `EXCEPTION` |
| `GET /api/security/summary?target=` | 汇总前先把过期例外转 `EXPIRED`；返回严重度/状态计数、活动与过期例外数、受影响镜像与资产、`findingRows / observationCount / duplicateObservations`、最近报告（含工具版本与范围） |

### 3.5 主动扫描的边界

本批只接"已有报告"，不提供 `scan` 接口。主动扫描会占用集群、镜像仓库与网络带宽，且需要独立的凭据与限流，必须在单独的运行预算（并发、超时、目标范围、配额）获批后再接入；不能用"报告能导入"证明"扫描已执行"。

## 5. 已知限制

1. **没有真实账单导出**：成本与利用率由调用方按既有接口写入；未接入云厂商账单 API，也未在本机跑过真实账单文件。
2. **没有真实扫描器执行**：Trivy / kube-bench / Falco 的报告由外部生成后导入；服务端不校验报告 JSON 与工具原始格式的对应关系。
3. **建议不含金额与规格型号**：只给方向（降配/升配/扩盘/停用），不推算节省金额，也不给出具体实例规格。
4. **P95 基于已入库样本**：采集器缺失时段不会被补插值，只会体现在 `coverageRatio` 与 `INSUFFICIENT_SAMPLES`。
5. **例外到期依赖读取时触发**：没有独立调度器，`EXPIRED` 在 `summary` 调用时落库；未调用不会自动变更状态，但任何一次读取都会纠正。
6. **告警/工单联动不在本批**：命中未自动创建工单，避免与既有 Run/审批体系形成平行流程。

## 6. 回滚方式

- `git revert <sha>` 回退代码；两个迁移只新增表，回滚代码后遗留表不影响运行。
- 回滚后 `/api/finops`、`/api/security` 接口消失；已登记的成本、样本、报告与命中记录保留在库中作为审计证据。
