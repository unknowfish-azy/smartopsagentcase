## 二、发现的两个真缺陷（均为"单测全绿、HTTP 层断裂"模式）

### 缺陷 1：SEC-03 双人确认正向链路结构性不可达（设计断裂）

- **现象**：CRITICAL 预览（requiredApprovals=2）要求"非预览创建者的第二人"执行，
  但 `MultiExecService.execute` → `RunbookExecutionService.prepareAdHocBatch(执行者)` →
  `normalizeTargets` → `registry.requireOwned(target, 执行者)`——runtime 严格按 userId
  归属（内存 map，无共享），**第二审批人永远过不了归属校验**，HTTP 层返回
  `404 RUNTIME_NOT_FOUND`（修复前实证）。
- **掩盖原因**：`MultiExecServiceTest.different_subject_with_the_nonce_can_execute_critical_preview`
  **mock 掉了 prepareAdHocBatch**，真实归属校验从未在测试里执行——与 SEC-05 grantToken
  @JsonIgnore 是同一类问题。
- **修复**（`MultiExecService` + `RunbookExecutionService`）：
  1. 计划/派发的归属校验与 Run 记录都以**预览创建者**身份进行（`runtimeOwner`）；
  2. 第二审批人（≠创建者）作为触发者传入 `secondApproverId`，落库到
     `runbook_run.second_approver_id / approved_by`（新增 10 参重载，满足可追责）；
  3. 顺手收紧：低风险预览（无双人环节）**只允许创建者本人执行**，
     他人触发 → `403 PREVIEW_OWNER_REQUIRED`（新增防护，防 previewId+nonce 泄露被抢跑）。

### 缺陷 2：runbook 查询在真实 MySQL 上 ClassCastException（平台级断裂）

- **现象**：`RunbookCatalogService.loadVersion:232` 等 7 处
  `instant((Timestamp) row.get("created_at"))`——MySQL Connector/J 对 DATETIME 的
  Map 取值返回 `LocalDateTime`，强转 `Timestamp` 抛
  `ClassCastException: LocalDateTime cannot be cast to Timestamp`，**runbook/multi-exec
  的正向执行链路在真实 MySQL 上从未跑通过**（H2 测试环境返回 Timestamp，掩盖至今）。
- **修复**：两个文件各新增 `instant(Object)` 兼容重载（Timestamp / LocalDateTime /
  Date），7 处 Map 取值调用全部替换；`result.getTimestamp()` 的 RowMapper 路径不受影响。
