## 1. 优化目标与阅读方式

下一阶段重点补齐五条链路：**资产管理、专业诊断、批量执行、故障恢复、性能验证**。

项目已有 SSH 远程连接、审批与审计、Prometheus/Loki 查询，以及主机、Docker、Kubernetes、Helm 等工具基础。后续应复用这些实现，把局部工具扩展为可验证的故障处置流程。

- **P0**：先处理能力真实性、接口契约、执行恢复和交付可靠性，建立后续扩展基础。
- **P1**：完善常见故障诊断、作业流程、观测和恢复能力。
- **P2**：出现明确业务需求和数据基础后，再投入成本治理、多集群、边缘和演练。
- 所有任务勾选框均表示“本清单要求的增量改造已验收”，不代表相关领域从零开始，也不代表当前已完成。
- “未见”仅表示本轮检查范围内未发现；接单模型应先复核实际调用路径、部署配置和已有整改记录。

### 4.1 必须记录的性能口径

- 请求量、并发、p50/p95/p99、吞吐、错误率、超时率、排队时间。

- 模型首 token、生成时长、RAG 时长、工具执行时长、结果核验时长分别记录。

- 区分冷启动与预热，区分 fixture/mock 与真实 Provider，区分本地替身与远程执行。
- 复用现有前端性能基线；本轮没有更换语言、JDK、GC 或增加消息平台的性能证据。

| 勾选 | 场景 | 核心证据 | 恢复验证 |
|---|---|---|---|
| [ ] | Nginx 502 | upstream 配置、上游进程与端口、错误日志、连接状况、近期变更 | 业务探针、上游健康、错误率和延迟在约定观察窗口内恢复 |
| [ ] | MySQL 连接耗尽 | 连接来源、活动会话、慢查询、锁等待、应用连接池 | 业务查询成功率、连接占用和等待情况恢复；副作用有记录 |
| [ ] | Redis 内存压力 | 内存构成、淘汰策略、复制、持久化和慢命令 | 内存趋势、延迟、错误率、复制与持久化状态符合预期 |
| [ ] | Kubernetes Pod 异常 | Events、previous 日志、资源限制、探针、节点压力和卷 | 工作负载就绪，Service 实际连通，业务探针满足预期 |
| [ ] | 磁盘或 inode 耗尽 | 文件系统用量、增长来源、打开文件、占用进程与趋势 | 空间/inode、应用写入、错误日志和业务检查恢复；保留处置依据 |

退出码 0、命令已发送、Pod Ready 都是局部证据。完整恢复应由独立业务检查确认；证据不足时保留未核验结论。

## 7. 实施顺序与多模型分工

### 7.1 推荐批次

1. **第一批：可信基础。** OPS-01、OPS-04、PERF-01、PERF-08。先冻结工具契约和 Run 语义；纠正能力标识与实际部署差异。
2. **第二批：真实资源与诊断。** OPS-02、OPS-03、OPS-05～08；同步推进 PERF-02、03、05、06。
3. **第三批：故障闭环。** OPS-09～11、OPS-13、PERF-04、PERF-07；验收五类故障流程。
4. **第四批：交付与扩展。** OPS-12；按实际需求和数据基础决定 OPS-14～16。

独立的只读调查和设计可并行。涉及共同接口、Run 状态机、迁移与部署入口的修改应先约定负责人，按依赖顺序集成。

### 7.2 多模型任务边界

| 角色 | 主责 | 与其他模型的边界 |
|---|---|---|
| 模型 A：工具与多云基础 | OPS-01～04 | 负责工具契约、云连接、资源身份与 Run 权威语义；接口冻结后供其他模型接入 |
| 模型 B：专业诊断 | OPS-05～08 与五类证据包 | 复用 A 的接口和连接授权；不增加独立审批、凭据账或执行器 |
