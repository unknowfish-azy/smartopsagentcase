## 2. PERF-01：哨兵调度

### 2.1 数据模型（[V20261106.18__sentinel_scheduler_metrics.sql](file:///d:/SmartOpsAgent/backend/src/main/resources/db/migration/V20261106.18__sentinel_scheduler_metrics.sql)）

`sentinel_task` 新增 `last_duration_ms`：每次采集由 `System.nanoTime()` 实测后写回（成功与失败都写），下一轮据此判定慢目标，不使用估算值。

### 2.2 调度行为（[SentinelService.java](file:///d:/SmartOpsAgent/backend/src/main/java/com/smartops/sentinel/SentinelService.java)）

| 能力 | 实现 |
| --- | --- |
| 有界并发 | 通用车道 `Semaphore(maxConcurrency)` + 批次上限，槽位占满即停止认领 |
| 背压 | 通用槽位耗尽时记录 `deferredByBackpressure` 并结束本轮，不进入无界队列 |
| 慢目标隔离 | `last_duration_ms >= slow-threshold-ms` 的任务走独立 `slowLane`（容量默认 2）；车道满则 `deferredSlow`，不挤占通用槽位 |
| 租约 | 条件 UPDATE 认领 + `lease_expires_at`，过期可被其他实例重新认领 |
| 退避 | 失败后 `next_run_at = now + interval * 2^(n-1)` 并带 jitter，写 `consecutive_failures` |
| 整轮 deadline | 等待总时长不超过 `round-deadline-ms`；超时任务由租约回收，不重试 |
| 可观测 | `SchedulerStats(due, claimed, deferredByBackpressure, deferredSlow, claimedSlow, roundMs, waitMs, queueAgeMs, dueLatencyMs)` |

新增配置项（均有默认值）：`smartops.sentinel.poll.slow-threshold-ms`（2000）、`slow-lane-size`（2）、`round-deadline-ms`（45000）、`instance-id`（默认 host+pid，可显式覆盖）。

### 2.3 状态接口（[SentinelController.java](file:///d:/SmartOpsAgent/backend/src/main/java/com/smartops/sentinel/SentinelController.java)）

`GET /api/sentinel/scheduler-stats` 返回最近一轮实测指标与生效配置（并发、批次、租约、退避上限、慢车道、deadline、实例 ID）。接口需要登录；没有轮询过时返回零值。

## 3. PERF-02：共享 HTTP transport

### 3.1 共享池（[http_pool.py](file:///d:/SmartOpsAgent/ai-service/app/core/http_pool.py)）

- lifespan 启动时创建唯一 `httpx.AsyncClient`：`httpx.Limits(max_connections, max_keepalive_connections)`、`httpx.Timeout(request_timeout, pool=pool_timeout)`、`trust_env=False`；
- `asyncio.Semaphore(http_max_concurrent_requests)` 作为闸门，排队超过 `http_queue_timeout` 抛 `UpstreamSaturated`；
- 凭据、`task_id/run_id` 等上下文仍由调用方逐请求传入，共享 client 不保存任何用户态数据；
- 指标：`client_creations_total`、`in_flight`、`saturated_total`、`gate_wait_seconds`（直方图，可算排队 p95）。

配置默认值：`http_max_connections=100`、`http_max_keepalive_connections=20`、`http_max_concurrent_requests=32`、`http_queue_timeout=2.0`、`http_pool_timeout=5.0`。

## 5. 已知限制

1. **未做 30 分钟连续双副本运行**：双副本只做了 50 任务、并发轮询的集成测试；租约占位由 SQL 条件 UPDATE 保证，但长时间稳定性、时钟漂移和真实网络分区未验证。
2. **1,000 任务基线是 H2 + 本地替身**：不代表 MySQL、真实 SSH 目标与生产网络下的耗时；到期延迟、队列年龄是本地实测值，不能外推。
3. **未测真实上游 100 并发与文件句柄**：100 并发用例使用真实 `httpx` 连接池但无外部流量，"握手次数"以客户端创建次数（1）为代理指标；操作系统层文件句柄数量未采样。`gate_wait_seconds` 有直方图观测，但本批未输出具体 p95 数值。
4. **共享池只在 lifespan 生效**：绕过 lifespan 直接实例化 service 的路径（含既有单测）仍按请求创建客户端，不能据此声称连接已复用。
5. **没有新增压测脚本/看板**：指标通过 Prometheus 端点暴露，未接入 Grafana 面板。

## 6. 回滚方式

- 代码：`git revert <sha>`；`http_pool` 回滚后各服务恢复为按请求创建客户端。
- 迁移：回滚代码后保留 `last_duration_ms` 列不影响旧逻辑（旧代码不读该列）；如需清理可执行 `ALTER TABLE sentinel_task DROP COLUMN last_duration_ms`。
- 接口：回滚后 `/api/sentinel/scheduler-stats` 消失，功能接口不受影响。
