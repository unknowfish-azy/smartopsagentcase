# SmartOpsAgent 功能补充清单

> 目标：在现有“用户层 + 管理层”之外，补齐 SmartOpsAgent 的运维业务闭环、资产事实、自动化治理、平台治理和集成生态。
>
> 适用对象：项目负责人、接手实现的其他大模型、后续评审人员。
>
> 本文只提供产品分析和实施清单，不代表下列功能已经全部实现。

## 一、当前项目已经具备的能力

### 用户层

- AI 对话、SSE 流式回答和思考阶段展示。
- 语音输入、图片证据、附件会话。
- 服务器资产基础管理、指标查看和远程运维工作台。
- SSH、SFTP、文件、命令、隧道及运行记录。
- 个人知识库、团队知识、知识候选审核和版本感知检索。
- Agent 规划、风险判定、审批、受控执行和 Inspector 核验。
- Sentinel 监控、脚本、规则、告警和 Guardian 能力。
- 团队空间、邀请、成员角色、资源授权和通知。
- 模型连接、模型网关、用量统计、额度和插件/技能中心。

### 管理层

- 用户、部门、岗位、角色、菜单、字典和公告管理。
- 登录日志、审计、会话、管理员 MFA 和恢复码。
- 模型连接、路由、密钥托管、预算、用量分析。
- 管理工作台、接入检查和平台治理入口。

### 工程基础

- Spring Boot、Vue、FastAPI、Python Agent、Knowledge 服务分层。
- Prometheus/Loki 查询适配和运行记录。
- Agent planner、executor、inspector、memory、policies 基础模块。
- 训练数据、RAG 评测、前端构建、后端测试和部署脚本。

## 三、第一批：P0 必须补齐的能力

### P0-00：真实可用性门禁

这项不是新页面，而是所有新功能的基础。

待办：

- [ ] 真实登录、用户权限和管理权限路径可重复验证。
- [ ] Knowledge 服务实际加载非零语料，区分“服务存活”和“知识已就绪”。
- [ ] Sentinel 后端接线真实可用，通知未接入时明确显示“未配置”。
- [ ] AI、Java、Knowledge、Agent 使用统一的 `request_id`、`task_id`、`run_id`。
- [ ] 统一区分 `success`、`failed`、`denied`、`degraded`、`unknown`。
- [ ] fixture、mock、真实 Provider 三类结果分别标记。

验收标准：连续三次完整运行都有原始日志、运行 ID、失败证据和回滚方式；模拟结果不标记成真实生产结果。

### P0-01：事件/工单中心

当前项目已有轻量的 `ticketId`、告警、审批和运行记录，但还缺独立的 Incident/Ticket 领域模型。

最小版本：

- [ ] 状态：`OPEN → ACK → MITIGATING → RESOLVED → CLOSED`。
- [ ] 严重等级、负责人、协作者、创建时间、解决时间。
- [ ] 关联告警、Agent Run、执行证据、知识条目。
- [ ] 评论、附件、时间线、处理记录。
- [ ] SLA 计时和超时提醒。
- [ ] 关闭时填写根因、处置过程和复盘结论。
- [ ] 支持从告警、用户报障和 Agent 诊断创建事件。

验收标准：一条告警可以形成一个事件，事件可以关联 AI 分析、审批、执行、验证和复盘。

### P0-02：CMDB/资产中心

当前服务器模块主要是主机和指标，需要扩展为资产事实源。

最小资产类型：

- [ ] 主机、虚拟机、容器、Kubernetes 集群。
- [ ] 服务、数据库、中间件、域名、IP。
- [ ] 开发、测试、生产等环境。
- [ ] 负责人、团队、标签、状态、数据来源。
- [ ] 服务 → 主机、服务 → 数据库、Ingress → Service 等依赖关系。
- [ ] 资产发现、人工确认、失联和过期状态。
- [ ] 资产变更历史。

实施顺序：第一阶段采用“只读发现 + 人工确认”，避免错误自动写入。

验收标准：Agent 执行前能确定目标资产、环境、负责人和授权范围；未知目标进入人工确认。

### P0-03：告警生命周期

待补能力：

- [ ] 告警去重。
- [ ] 告警分组。
- [ ] 告警恢复和关闭。
- [ ] 静默、维护窗口和静默到期。
- [ ] 告警确认、转派和升级。
- [ ] 邮件、Webhook、企业微信、钉钉、飞书通知。
- [ ] 通知失败重试和失败记录。
- [ ] 告警与 Incident、资产和 Runbook 关联。

验收标准：同一故障产生 10 次重复告警时，只形成一个事件；故障恢复后，事件自动进入待关闭状态。

### P0-04：Runbook 与自动化作业

把脚本和命令升级成可治理的作业。

待补能力：

- [ ] Runbook 名称、版本、作者和适用环境。
- [ ] 输入参数 Schema。
- [ ] 前置检查、执行步骤和后置检查。
- [ ] 风险等级和审批要求。
- [ ] 目标选择器和目标快照。
- [ ] 超时、重试、取消和失败分支。
- [ ] 并发上限、批次执行和金丝雀执行。
- [ ] 回滚步骤和幂等规则。
- [ ] 每个目标单独记录执行结果。
- [ ] 定时执行和事件触发。

验收标准：批准的参数、目标和版本必须与实际执行内容一致；部分成功、失败、未知状态分别展示。

### P0-05：密钥与凭据中心

模型 Key 已有加密存储，但远程连接和工具凭据应统一治理。

待补能力：

- [ ] SSH、数据库、云平台、模型 Key 统一保存。
- [ ] 前端只展示凭据名称、类型和状态。
- [ ] 执行时使用 `credential_ref`，不把原始凭据传给前端。
- [ ] 日志、审计和错误信息自动脱敏。
- [ ] 支持轮换、禁用、过期和按团队授权。
- [ ] 记录凭据使用审计。
- [ ] 评估 OpenBao/Vault 的动态凭据和租约机制。

验收标准：用户界面、运行记录和普通日志中都不会出现完整密码、Token 或私钥。

## 四、第二批：P1 产品化能力

### P1-01：统一可观测性

贯通以下链路：

```text
浏览器 → SSE → Java API → AI Service → Knowledge → 模型 → 工具 → Inspector
```

待补字段：

- [ ] `request_id`、`task_id`、`run_id`、`trace_id`。
- [ ] 首 Token、总耗时、RAG 耗时、工具耗时、验证耗时。
- [ ] Provider、模型、降级原因、错误原因。
- [ ] 运行状态和最终验证结论。
- [ ] 日志、指标、Trace 的跳转关系。

### P1-02：备份与恢复

备份范围：

- [ ] MySQL 数据库。
- [ ] 知识库、向量索引和语料 manifest。
- [ ] 图片、附件和聊天证据。
- [ ] 审计日志和 Agent 运行记录。
- [ ] 配置、插件清单和密钥元数据。

验收标准：完成一次隔离环境恢复演练，记录 RPO、RTO、数据数量、哈希和引用关系。

### P1-03：集成中心

建议接入顺序：

1. [ ] Prometheus / Alertmanager。
2. [ ] Webhook。
3. [ ] 邮件。
4. [ ] 企业微信、钉钉、飞书。
5. [ ] OIDC 或 LDAP。
6. [ ] GitLab/GitHub、Argo CD。

每个集成都需要连接测试、健康状态、失败重试、超时和审计记录。

### P1-04：多租户与工作区隔离

先明确产品形态：

- 单租户、多团队平台；或
- 多租户 SaaS 平台。

然后统一给以下资源增加工作区/租户范围：

- [ ] 资产。
- [ ] 知识。
- [ ] 告警和事件。
- [ ] Runbook 和运行记录。
- [ ] 模型连接、Token 额度和成本。
- [ ] 审计和导出数据。

### P1-05：运维报表

建议加入：

- [ ] MTTA：平均响应时间。
- [ ] MTTR：平均恢复时间。
- [ ] 告警数量、重复率和静默率。
- [ ] 自动化成功率和审批等待时间。
- [ ] 知识命中率、引用覆盖率和检索准确率。
- [ ] 模型 Token、费用和失败率。
- [ ] 资产覆盖率和过期资产数。
- [ ] 变更失败率。
- [ ] SLA 达成率。

所有数字显示统计时间范围、更新时间、数据来源和口径。

### P1-06：AI 与知识质量治理

- [ ] 人工黄金集和独立测试集分离。
- [ ] RAG Recall@1/3/5、MRR、引用正确率。
- [ ] 版本误召回率和权限误召回率。
- [ ] 工具调用成功率和假成功率。
- [ ] 拒答、证据不足、冲突版本等风险样本。
- [ ] 模型、Prompt、知识版本和评测结果关联。
- [ ] 评测结果进入发布门禁。

## 八、交给其他大模型的通用任务模板

```text
请先阅读 AGENTS.md、README.md、docs/SMARTOPS_MODULE_MAP.md，
以及 docs/development 下已有优化方案。

只领取一个任务编号，不要同时改多个领域。
先判断当前能力是 DONE、PARTIAL、MOCK、BLOCKED 还是 NOT_STARTED。
先列出涉及的文件、接口、数据库表和现有状态机，再设计增量方案。
不得重复创建第二套用户、权限、审批、Run、审计或模型计费系统。
所有新状态必须定义状态转移、失败状态、未知状态和回滚方式。
所有新功能必须区分真实接入、模拟数据和未配置状态。

交付必须包含：
1. 改动文件；
2. 对照差分；
3. 验证命令和原始结果；
4. 回滚方案；
5. 未完成项和后续依赖。
```

## 九、给项目负责人的最终建议

当前项目不缺页面，主要缺四条完整闭环：

```text
资产 → 告警 → 事件/工单 → Runbook → 审批 → 执行 → 验证 → 复盘
```

```text
凭据 → 工具 → 目标 → 权限 → 审计 → 轮换
```

```text
前端 → Java → AI → Knowledge → 模型 → 工具 → Inspector
```

```text
数据 → 备份 → 恢复演练 → RPO/RTO → 审计证据
```

最适合立即交给其他模型的首批任务是：

- `P0-01 工单中心`
- `P0-02 CMDB`
- `P0-03 告警生命周期`
- `P0-04 Runbook`
