# P1-OBS-01：可观测性对照表

日期：2026-11-05  
范围：浏览器 → SSE → Java → AI Service → Knowledge → 模型 Provider 的关联字段与时间线  
性质：只读核查与契约说明；本轮不修改业务代码、不启动服务。

## 1. 结论

**状态：`IN_PROGRESS`。**

已完成可核实部分：

- 浏览器单次请求的失败状态可以复盘：`run_event` 的 `request_id` / `run_id` / `status` 会随消息持久化，刷新后仍保留；白名单会丢弃任意附加字段。
- `run_event` v1 字段集与 schema 完全一致（9 个必填字段、`additionalProperties=false`、未知状态被拒绝），见第 6 节真实命令输出。
- 前端白名单与运行记录关联的单测 10/10 通过（第 6 节真实输出）。

尚不可称为“跨层可复盘”：

1. 浏览器直接调用 AI Service（`/ai/api/chat/stream`），**不经过 Java**；Java 的 `RunCorrelationFilter` 不覆盖聊天路径。
2. Java 运行记录的 `trace_id` 由 `ObservabilityService` 单独生成，与 AI 的 `run_id` **不同源、无映射**。
3. 模型 Provider（Ollama）无独立 trace；只有 AI Service 返回的 `effective_provider` / `degraded` / `degradation_reason`。
4. 各阶段没有服务端时间戳；首 token / 总耗时由浏览器本地测量，不是服务端事实。

已由 `P0-RUN-01` 补齐（2026-11-05）：AI Service 向 Knowledge 转发同一组 ID，Knowledge 回显并记录 `knowledge.search`；AI Service 自身记录 `chat.start` / `chat.rag` / `chat.terminal`。详见 [P0-RUN-01 跨层对照表](P0-RUN-01-跨层run对照表-20261105.md)。

因此，“一次失败可复盘”当前在**浏览器 + AI SSE + Knowledge** 三层成立；跨 Java / Provider 的复盘仍依赖 `ARCH-P0-01/05`、`P0-E2E-01`、`P0-E2E-02`。

## 3. 脱敏字段白名单

| 层 | 允许字段 | 落库/落日志前处理 | 强制位置 |
|---|---|---|---|
| run_event | 9 个 schema 字段，无其他键 | `additionalProperties=false`；ID 必须匹配 `[A-Za-z0-9][A-Za-z0-9_.:-]{0,95}`；状态枚举校验 | `agent/runtime_events.py`、`run-event-v1.schema.json` |
| 前端历史 | 仅上述字段（`step_id` 允许 `null`），字符串 ≤96 且不含换行；必须同时有 `request_id` 与 `run_id` | 丢弃任意其他 `metadata` | `frontend/src/domain/chat/history.ts` |
| 前端历史（诊断补充） | `degraded`、`effective_provider`（≤80）、`rag_status`（枚举）、`top_k`（1–100）、`rag_degraded`、`rag_enabled` | 去换行；`degradation_reason` / `rag_degradation_reason` 截断 160；inspection 只保留 `status` / `severity` / `requires_human` / `reason` | `frontend/src/domain/chat/history.ts` |
| Java 关联 | 仅三个 ID 与 schema 版本 | 非法 ID 替换为新 UUID；`MDC.clear()` 收尾；不记录请求体 | `RunCorrelationFilter.java` |
| Java 运行记录 | `trace_id`、`tool_id`、范围/条数描述、退出码、固定结果摘要 | 注释明确不持久化凭据、原始 PromQL/LogQL、原始日志行 | `ObservabilityService.java` |
| AI Service | 回答、引用、`run_event`、固定档位元数据 | `terminal_event` 严格 allowlist；异常不序列化进事件 | `agent/runtime_events.py`、`chat.py` |

**已知脱敏风险**：`LLMService._mark_degraded` 使用 `f"{type(exc).__name__}: {exc}"` 生成 `degradation_reason`，异常消息可能包含内部地址；该字段会进入浏览器并持久化（截断 160 字符）。建议后续改为固定错误码（如 `ollama_timeout` / `ollama_connect_error`），保留原始异常仅进服务端受控日志。

禁止进入上述任何通道：Prompt / 完整私有原文 / Token / Cookie / 审批凭据 / 原始日志行 / 完整模型输出以外的任意异常栈。

## 4. 时间线

成功路径（当前真实代码顺序）：

```text
浏览器生成 request_id + task_id
  → POST /ai/api/chat/stream
  → SSE run(started, run_id)
  → thinking(retrieve) / thinking(answer)
  → token...
  → SSE done(metadata.run_event=succeeded) + rag/inspection/provider 元数据
  → 前端写入消息、history 白名单持久化
```

失败路径：

```text
SSE error(顶层 run_event=failed) → 前端错误态 + 可重试 + 持久化 failed run_event
HTTP 非 2xx / 流提前结束 → 前端错误（无 run_event）
模型输出中断（已输出部分 token）→ SSE error(LLM_STREAM_INTERRUPTED) → run_event=failed
```

时间线边界：

- `run_event.timestamp` 是事件生成时间，**不是**阶段耗时；没有服务端 retrieve / first-token / 总耗时。
- 浏览器 `firstTokenMs` / `totalMs` 是本地计时，属于体验指标，不可作为服务端 SLA 证据。
- 一次请求只有一个 `run_id`；Java 运行记录另有独立 `trace_id`，两者不能直接互查。

## 5. “一次失败可复盘”的现状

### 5.1 已可复盘（浏览器 + SSE）

1. 在聊天消息的“运行诊断”中取得 `request_id`、`run_id`、`status`、`event_id`、`timestamp`。
2. 刷新后仍能从历史记录还原同一组字段（白名单持久化）。
3. 可区分失败与恢复：失败消息保留 `run_event.status=failed`，重试成功后写入新的 `run_event.status=succeeded`，并以 `attempt` / `recovered` 标记区分。
4. 可在错误旁直接重试，不重复发送用户消息。

现有自动化证据（fixture 边界，**不是真实 Provider E2E**）：

- `frontend/test/chat-retry.browser.mjs`：502、partial 中断、刷新后重试；`fixture=true` / `provider_e2e=false`。
- `frontend/test/chat-diagnostics.browser.mjs`：成功与降级两种诊断字段、复制 ID、刷新持久化。
- `frontend/test/run-history-correlation.test.mjs`、`frontend/test/chat-history.test.mjs`：白名单与关联字段安全还原。

### 5.2 不可复盘（跨层）

缺少以下任一环节都使跨层复盘无法成立：

| 缺口 | 现状 | 影响 |
|---|---|---|
| 浏览器 → Java 关联 | 聊天直连 AI，不经 Java | Java MDC 中没有本次聊天 ID |
| AI → Knowledge 关联 | 已由 P0-RUN-01 转发三个 ID | 可从 `run_id` 定位知识检索请求 |
| Knowledge → 日志 | 已由 P0-RUN-01 记录 `knowledge.search`（ID/status/结果数） | 检索失败可按 ID 复盘 |
| AI → 服务端日志 | 已由 P0-RUN-01 记录 `chat.start` / `chat.rag` / `chat.terminal` | 服务端可按 ID 检索本次请求 |
| Java `trace_id` ↔ AI `run_id` | 各自生成，无映射 | 运行记录页与聊天诊断无法互相定位 |
| Provider 调用 | 无 trace | 模型超时/连接失败只能看 `degradation_reason` |

### 5.3 真实跨层复盘步骤（待依赖满足后执行，本轮未执行）

1. 浏览器诊断区复制 `request_id` / `run_id`。
2. AI Service 日志按 `run_id` 检索（依赖新增结构化日志）。
3. Java 后端日志按 `X-Request-ID` / `run_id` 检索（依赖聊天经 Java 或转发头）。
4. Loki 按 `job="smartops-backend"` 与上述 ID 检索（依赖 ID 进入日志行）。
5. Knowledge 日志按同一 ID 检索（依赖接收并记录）。
6. 在运行记录页按 `trace_id` 核对 Java 侧终态，并通过映射表关联到 `run_id`。

在上述 1–6 未闭环前，不把 fixture 通过写成真实跨服务复盘。

## 7. 缺口与后续动作（按优先级）

1. **AI Service 结构化日志**：已完成（`chat.start` / `chat.rag` / `chat.terminal`，仅 ID/状态/固定档位）。归属 `P0-RUN-01`。
2. **聊天请求经 Java 或转发关联头**：由 Java 签发并转发 `X-Request-ID` / `X-Task-ID` / `X-Run-ID`，AI/Knowledge 只接受校验后的值。归属 `ARCH-P0-01`。
3. **Knowledge 接收与记录关联 ID**：已完成（回显 + `knowledge.search`，不含 query）。归属 `P0-RUN-01`。
4. **建立 `trace_id` ↔ `run_id` 映射**：在 Java 权威 Run 账本中保存映射，前端运行记录可反查。归属 `ARCH-P0-02` / `ARCH-P0-05`。
5. **`degradation_reason` 脱敏**：改为固定错误码，原始异常只进服务端受控日志。可独立小改，不依赖真实环境。
6. **真实失败矩阵**：provider 不可达、首 token 中断、Knowledge 503、重启中断各至少 1 次真实记录。归属 `P0-E2E-02`。
