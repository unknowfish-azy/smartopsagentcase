# Trae 服务与 SmartOpsAgent 项目健康优化建议

日期：2026-11-06
依据：本次会话中的本机服务探针、启动日志、回归测试和 [项目健康复核记录](../../.runtime/project-health-verification.txt)。

## 1. 结论

项目的大部分运行链路已经可用：用户前端 5173、管理员前端 5174、知识库 8002、后端 8080、MySQL、Redis 和 Ollama 均完成了本机探活；前端 487 项测试、AI 服务 62 项测试、TypeScript 检查和前端构建均通过。

当前影响 Trae 服务稳定性的核心问题是 **8001 端口由旧 Python 进程 PID 58868 长时间占用**。旧进程的 `/api/health` 返回 200，但聊天请求没有按当前源码要求使用 `X-Run-Token`，无令牌请求还出现超时。这说明服务进程存活，却没有加载当前 `.env` 和聊天鉴权实现，属于“健康接口正常、业务接口版本错误”的假健康状态。

本次建议优先解决进程生命周期、启动前置检查和聊天鉴权，再推进跨服务可观测性、真实浏览器闭环和性能优化。

## 3. 根因与影响

### 3.1 8001 旧进程没有被纳入可靠的生命周期管理

启动脚本可以启动新进程，但未能在启动前可靠地确认旧进程归属、版本和可终止性。旧 PID 占用 8001 后，新实例因 WinError 10048 退出；如果只检查端口或 `/api/health`，会误以为新版本已经生效。

影响包括：

- 当前源码中的 `X-Run-Token` 鉴权无法在固定入口得到确认；
- `.env` 的最新服务地址和共享密钥可能没有加载到运行进程；
- 前端可能连到旧进程，出现请求超时、鉴权行为不一致或版本差异；
- 端口健康检查会把旧进程误判为当前服务。

### 3.2 健康检查只覆盖进程层，没有覆盖业务契约层

`/api/health` 返回 200 只能说明 Uvicorn 进程响应，不代表聊天鉴权、模型调用、知识库调用和 SSE 终态正确。当前已用隔离端口证明：同一份源码的业务鉴权行为正确，但固定 8001 旧实例行为不一致。

### 3.3 启动环境存在多套配置入口

项目同时包含 `.env`、启动脚本、Vite 代理、后端配置和 Python 服务配置。此前还存在 Java 默认版本、Maven 用户目录不可写以及旧服务地址不一致的问题。虽然本轮已经修正本地启动脚本和地址，但配置漂移仍然容易再次出现。

### 3.4 构建可用，但前端仍有大 chunk 提示

生产构建已通过，但 Vite 提示部分 chunk 超过 500 kB。当前不影响启动，应在稳定性问题收敛后再做按路由和重型依赖的拆分，避免把性能优化与服务恢复混在同一批改动中。

## 4. 优化建议和优先级

### P0：修复 Trae 服务固定端口的可用性和鉴权一致性

| 编号 | 建议 | 实施要点 | 验收标准 |
| --- | --- | --- | --- |
| P0-01 | 启动前做端口归属检查 | 启动 8001 前读取监听 PID、进程路径、命令行和启动时间；PID 不是当前项目 Python 命令时标记 `STALE_INSTANCE` 并阻止启动 | 不允许“端口在监听 = 当前版本已启动”；输出 PID、命令行和源码目录 |
| P0-02 | 增加受控停止和超时回收 | `stop-all-local.ps1` 与 `start-all.ps1` 使用同一服务注册表；停止失败时明确输出管理员命令，不继续启动第二个实例 | 旧进程无法结束时，启动命令退出非零并给出恢复命令；不存在双实例 |
| P0-03 | 增加版本化 readiness | `/api/ready` 返回服务版本、源码/构建标识、配置摘要哈希和启动时间；保留 `/api/health` 作为进程健康接口 | 8001 的 readiness 必须匹配当前 commit 或启动批次；旧版本直接判失败 |
| P0-04 | 把聊天鉴权纳入启动探针 | 启动后用无令牌、错误令牌和合法令牌分别验证 `/api/chat`；请求体使用固定短消息，不记录答案和密钥 | 无令牌=401 `RUN_TOKEN_REQUIRED`；错误令牌=401 `RUN_TOKEN_INVALID`；合法令牌进入业务处理 |
| P0-05 | 避免旧进程误接收流量 | Vite 代理和固定入口启动完成前不宣布前端可用；必要时使用临时端口启动、readiness 通过后再切换 | 新版本 readiness 通过前，前端不被标记为可验收 |

### P1：统一配置、可观测性和真实验收

| 编号 | 建议 | 实施要点 | 验收标准 |
| --- | --- | --- | --- |
| P1-01 | 建立单一服务注册表 | 统一记录服务名、目录、端口、启动命令、健康 URL、readiness URL、停止方式和日志路径；脚本、文档和预检均从注册表读取 | 修改端口或命令时只改一处；预检输出与实际启动命令一致 |
| P1-02 | 统一 Java、Python 和前端配置来源 | `.env` 仅保存本机覆盖值；`.env.example`、Vite 代理、Spring 配置和 Python settings 只保留明确默认值 | 预检报告列出实际生效的 AI/Knowledge/DB 地址；不出现旧地址混用 |
| P1-03 | 建立跨层运行关联 | 统一 `request_id`、`task_id`、`run_id` 和 `trace_id` 的生成、透传、日志白名单和脱敏规则 | 成功、失败、拒绝、超时、SSE 中断各有一条可追踪记录；日志不含 token、Prompt 和私有原文 |
| P1-04 | 增加真实浏览器冒烟 | 覆盖登录、助手就绪、聊天鉴权、知识库引用、刷新恢复、流中断和重试；区分 REAL、MOCK、FIXTURE、NOT_RUN | 连续 3 次干净运行；页面错误为 0；失败场景不被标记为成功 |
| P1-05 | 统一失败状态语义 | 前端和服务端分别区分 `health_up`、`authorized`、`provider_ready`、`rag_ready`、`stream_completed` 和 `business_succeeded` | HTTP 200、进程存活、审批通过和 exit 0 均不能单独生成“已恢复”结论 |
| P1-06 | 完善恢复记录 | 每次服务重启保存旧 PID、新 PID、启动命令摘要、readiness 输出、日志路径和回滚入口 | 任意一次服务恢复都能从记录重放；异常重启不覆盖原始日志 |

### P1：前端性能和维护性

| 编号 | 建议 | 实施要点 | 验收标准 |
| --- | --- | --- | --- |
| P1-07 | 继续拆分大 chunk | 对 Three.js、ECharts、知识目录、终端等重型依赖按路由动态加载；先记录首屏和交互页基线 | 首屏 JS、首屏时间和聊天页交互延迟有前后对照；不以简单压低 chunk 数量为唯一目标 |
| P1-08 | 固定前端质量门禁 | 保留 `npm test`、`npm run typecheck`、`npm run build`，并将大 chunk 作为 warning 记录而不是静默忽略 | 构建失败、类型错误、测试失败阻止发布；warning 进入构建报告 |
| P1-09 | 加入端口和代理回归 | 测试 5173/5174 的 `/api`、`/ws`、`/ai` 代理，以及管理层和用户层入口隔离 | 两个前端入口都能访问正确代理；管理员路由不能落入用户层 |

### P2：架构和长期运维

| 编号 | 建议 | 实施要点 | 验收标准 |
| --- | --- | --- | --- |
| P2-01 | 明确 Java 与 Python AI 的职责边界 | 文档明确默认聊天入口、Python 8001 的可选能力、Knowledge 8002 的调用方向，避免把“可探活”写成“生产链路已贯通” | 架构图、启动文档、接口文档和 E2E 证据口径一致 |
| P2-02 | 将 Run/审批/审计状态持久化 | 进程内 map 只做缓存，MySQL 作为状态事实源；补充幂等、重启恢复和 outbox | 杀进程、重启、重复请求和 SSE 断线后，状态不会丢失或重复执行 |
| P2-03 | 凭据改为本机外部注入 | `.env` 只保留示例和本机忽略文件；生产使用 Windows Credential Manager、密钥服务或部署变量 | 日志、健康接口、构建产物和文档均不出现明文凭据；轮换无需改代码 |
| P2-04 | 建立依赖升级矩阵 | 记录 Java 17、Python 3.10–3.12、Node、MySQL、Redis、Ollama 和模型版本；升级前做隔离验证 | 每次升级有兼容性结果、回滚版本和重新运行的健康探针 |

## 5. 推荐执行顺序

```text
P0-01/P0-02 端口归属与停止策略
    → P0-03/P0-04 readiness 与聊天鉴权探针
    → P1-01/P1-02 服务注册表与配置收敛
    → P1-03/P1-04 跨层运行关联与真实浏览器冒烟
    → P1-05/P1-06 失败语义与恢复证据
    → P1-07/P1-08 前端性能和质量门禁
    → P2-01/P2-02 长期架构与状态持久化
```

在 8001 固定端口旧进程仍未完成回收前，不应把 Trae 的聊天链路标记为完全恢复，也不应把 `/api/health` 的 200 作为业务验收结果。

## 6. 本轮可以立即执行的管理员操作

```powershell
Set-Location D:\SmartOpsAgent
Stop-Process -Id 58868 -Force
& .\.runtime\restart-ai-health.ps1
```

恢复后执行：

```powershell
$body = '{"message":"health probe","metadata":{}}'
curl.exe -i --max-time 5 `
  -H "Content-Type: application/json" `
  --data $body `
  http://127.0.0.1:8001/api/chat
```

预期结果：HTTP 401，响应中的业务码为 `RUN_TOKEN_REQUIRED`。随后再用合法运行令牌做一次最小聊天请求，并记录响应状态、`run_id`、日志文件和是否完成终态；不要把令牌或完整模型回答写入文档。

## 7. 验收清单

- [ ] 8001 只有一个属于当前项目的监听进程。
- [ ] 8001 readiness 能证明当前源码/构建批次已经加载。
- [ ] 无令牌、错误令牌和合法令牌的聊天行为符合契约。
- [ ] 前端 5173/5174 代理指向当前 8001，而不是旧实例。
- [ ] 8002 READY、8080 UP、MySQL/Redis/Ollama 仍通过探活。
- [ ] 前端 487 项测试、AI 62 项测试、typecheck 和 build 重新执行并留档。
- [ ] 真实浏览器冒烟区分 REAL、MOCK、FIXTURE 和 NOT_RUN。
- [ ] 日志和健康报告不包含密码、共享密钥、运行令牌、Prompt 或私有原文。
- [ ] 失败、超时、拒绝、降级和恢复场景均有独立状态，不把 HTTP 200 当业务成功。

## 8. 未解决项和边界

1. 本轮当前权限无法结束 PID 58868；`Stop-Process` 和 `taskkill` 均返回 Access Denied。自动提升审批服务也因模型配置返回 404，因此没有绕过审批执行提升操作。
2. 8003 隔离端口只用于验证当前源码鉴权，不能替代 8001 固定端口的最终验收。
3. 前端构建的大 chunk 只是优化项，不是本次 Trae 服务异常的根因。
4. 本文不把本机健康检查等同于生产环境验收；生产环境仍需真实账号、真实网关和真实浏览器证据。
