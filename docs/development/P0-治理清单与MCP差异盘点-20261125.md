## 2. MCP 差异盘点表

### 2.1 基线说明（先对齐"在跟谁比"）

- **规范基线**：MCP revision **`2026-07-28`**（官方规范站与 schema.ts）。该 revision 是 **dual-era** 设计：
  - **Modern**（≥2026-07-28）：**无握手**，每个请求在 `_meta` 里携带协议版本与客户端能力；服务端**必须**实现 `server/discover`；版本不支持返回 `-32022 UnsupportedProtocolVersionError` 并附支持列表；**服务端不得发起 JSON-RPC 请求**。
  - **Legacy**（≤2025-11-25）：以 `initialize` 握手建立会话，允许服务端发起请求。
- **本仓基线**：`agent/mcp/protocol.py:24-32` 声明 `MCP_PROTOCOL_VERSION = "2025-03-26"`，支持 `2025-03-26` / `2024-11-05` → **属 Legacy 时代**，stdio + tools only。
- **判定总原则**：本仓是一个**合法的 Legacy 实现**（规范明确允许 dual-era 与 legacy 互操作），但**不是 Modern 实现**。任何"完全兼容 MCP 最新规范"的表述都是越界。

### 2.3 关键结论（可直接对外说的 / 不能说的）

**可以说**
- "实现了自有 MCP 协议层：**Legacy（≤2025-03-26）时代的 stdio 传输 + tools 面**，包含 initialize 版本协商、初始化状态门控、`tools/list`、`tools/call`（经 executor 安全链）、白名单暴露控制与官方 SDK 互操作验证。"
- "工具暴露默认只读、显式 allowlist、调用留痕可审计。"

**不能说**
- ❌ "完全兼容 MCP 最新规范 / 2026-07-28" —— 我们只实现 legacy 分支，modern 的 `server/discover`、per-request `_meta`、`-32022` 全无。
- ❌ "支持 Streamable HTTP / 远程 MCP 服务" —— 未实现。
- ❌ "支持 resources / prompts / sampling" —— 未实现，且能力中也未声明。
- ❌ 把 `tools/list` 全量返回说成"支持分页发现"。

### 2.4 与竞赛分值的关系（F09：MCP 4 分）

- F09 只登记了"竞赛 AI 技术分项含 MCP 4 分"，**未定义评分细目**。因此本文不做分值承诺。
- 可核查的判断是：**tool 面的存在性证明已具备**（协议实现 + 互操作测试 + 安全链复用）；若评分细目要求多面能力（resources/prompts）或 modern 特性，则需按 §2.5 补齐。
- **不建议**为凑分盲目新增未验证面积——本仓既有纪律（"不预留假接口"、"未实测不写达标"）优先级更高。

## 3. 风险与反模式

| 风险 | 说明 | 对策 |
|---|---|---|
| 把 legacy 说成"最新规范兼容" | modern/legacy 差异被模糊 | §2.3 的"不能说"清单 + G 清单纳入自检 |
| 为凑 MCP 分值盲目扩面 | 新增未验证能力 → 违背"未实测不写达标" | 明确不做清单；先出场景再实现 |
| 工具风险只留在内部 | 对端看不到 destructiveHint，可能误调用 | 后续考虑把内部 risk 映射为 MCP annotations |
| 清单流于形式 | 无 hook 强制，靠自觉 | 承认缺口（§1.3）；可选：把 G19–G21 串成脚本 |
