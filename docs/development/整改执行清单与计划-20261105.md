## 1. 方向与取舍

### 1.1 产品叙事

一句话：**一个能说明"为什么现在还不能结单、缺什么证据、下一步查什么、何时才算恢复、证据何时失效"的运维 Agent。**

四段机制对应四个可交付物：

| 机制 | 交付物 | 可证伪点 |
|---|---|---|
| 证据义务 | `RecoveryContract` / `ObligationResult` | 200 + 业务 false 必须判 FALSE，不签 VERIFIED |
| 有预算补证 | `ProbeDecision` + WAIT/STOP | 同预算对比固定顺序，收益不成立就删"省成本"主张 |
| 恢复契约 | `VerificationReceipt` | 三组双路径满足窗口才 ACTIVE；到期/反例即失效 |
| 同证据回放 | `ReplayBundle` | 同包 100 次一致；缺录制探针必须 REPLAY_INCOMPLETE |

### 1.2 两条推进轨（互不阻塞）

| 轨道 | 内容 | 前置 | 产出 |
|---|---|---|---|
| 机制轨（先做） | N01→N02→N03→N04→N05→HC-11 | 只需 HC-00 基线 + HC-05 隔离门禁 | loopback 可运行演示、机制评测报告 |
| 平台轨（并行审计） | HC-01/02/04/05/07 → N06 → N07 真实接入 | 需 HC-00 基线；Java 侧整改需单独认领 | 四轴状态机、身份/scope、Knowledge readiness、跨层 run |

**为什么不先做平台大改**：答案答辩不需要全平台闭环才能讲清机制；机制轨在 Python 内闭环，风险低、可验证、失败可回滚。平台轨先出审计和设计，避免边改边返工。

### 1.3 三条不可越过的边界

1. `action / inspection / recovery / authorization` 四轴在数据模型和 UI 中并列，不合并成"成功/失败"。
2. `StateVerifier.passed`、工具 `exit 0`、HTTP 200、审批 approved **都不等于恢复**。
3. `fixture / mock / real / provider_e2e` 四类证据分账；缺失就写 `NOT_RUN`。

## 6. 每个任务的最小执行步骤（统一模板）

- [ ] PLAN：只读核查输入版本、既有改动、真实入口；记录前像 hash 与精确认领路径。
- [ ] PLAN：冻结输入/预期、负例、验收命令、依赖与回滚设计；声明 UNKNOWN。
- [ ] IMPLEMENT（有授权后）：备份前像；先复现负例（红阶段证据）。
- [ ] IMPLEMENT：最小改动，不改真值、不改契约阈值、不改他人文件。
- [ ] RUN：定向测试/隔离实验；失败保留；缺依赖写 `NOT_RUN/BLOCKED`。
- [ ] REVIEW：独立检查状态、权限、分母、预算、证据；四件交付齐全。
- [ ] REPORT：分别更新 `design_status / implementation_status / verification_status`。

## 7. 硬性禁止

1. 不 `reset/revert/clean` 覆盖工作区已有修改。
2. 不用 LLM 自评、`passed`、`exit 0`、HTTP 200、审批 approved 作为恢复真值。
3. 不改 Golden/测试期望以追分；不为刷绿删测试。
4. 不把 fixture、历史日志、README 自报能力写成生产证据或"已采用"。
5. 空义务集、`all([])=True`、默认值不能签发 VERIFIED。
6. 调度收益未与"同预算固定顺序"对比前，不宣称节省成本。
7. 数学/概率未校准时，不写 ECE/Brier/信息增益结论。
