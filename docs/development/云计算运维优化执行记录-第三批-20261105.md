## 2. OPS-04 本轮补齐

### 2.1 UNCERTAIN 的人工核验闭环

第一批已把"进程消失、远端是否生效未知"标为 `UNCERTAIN` 并禁止自动重试；缺的是核验出口，`UNCERTAIN` 会永久悬挂。

- 新增 `POST /api/operations/runs/{id}/verify`：
  - `decision= DONE` → `VERIFIED_SUCCEEDED`；`NOT_DONE` → `VERIFIED_FAILED`；
  - 必须填写依据（≤500 字），写入 `operation_run_evidence`（`RUN_VERIFIED`），内容含结论、依据与"不自动重试写操作"；
  - 只允许对 `UNCERTAIN` 核验：条件更新 `WHERE status='UNCERTAIN'`，并发下只有一个请求生效；
  - 非本人运行按 404 处理，不泄露存在性；重复核验返回 409 `OPERATION_RUN_NOT_UNCERTAIN`。
- 实现：[OperationRunQueryService.java](../backend/src/main/java/com/smartops/service/OperationRunQueryService.java)、[OperationRunController.java](../backend/src/main/java/com/smartops/controller/OperationRunController.java)

### 2.2 审批消费后中断的对账

团队执行顺序是「审批 → consumeGrant → 执行 → finish」。若进程在 consumeGrant 之后消失，授权已消费但团队运行停在 `RUNNING`，既不能重新审批，也不能安全重跑。

- 新增 [TeamAgentRunRecoveryScheduler.java](../backend/src/main/java/com/smartops/service/TeamAgentRunRecoveryScheduler.java)：
  - 扫描超过 `smartops.operations.team-run.recovery-stale-ms`（默认 10 分钟）仍为 `RUNNING` 的团队运行；
  - 按幂等键 `tool-run:<userId>:team-run:<runId>` 找到对应 Run：终态则**按事实回填**团队运行状态并写 `TEAM_RUN_RECONCILED` 证据；仍 `RUNNING` 则跳过；
  - 找不到任何 Run：置 `UNCERTAIN`（授权已用、结果未知），不猜成失败、不自动重跑；
  - 条件更新 `WHERE status='RUNNING'` 保证重复扫描幂等。

## 3. OPS-05 Kubernetes 诊断包

位置：`backend/src/main/java/com/smartops/diagnostics/kubernetes/`

### 3.1 调用方式

`POST /api/operations/kubernetes/diagnose`

```json
{
  "runtimeId": "runtime-1",
  "context": "prod-hz",
  "namespace": "payment",
  "workload": "payment-api",
  "pod": "payment-api-7f9c8d-xxxx",
  "container": "app",
  "sinceMinutes": 60
}
```

`context` 与 `namespace` 必填且显式传入，不使用集群当前上下文；参数按白名单校验，命令不拼接自由文本。

### 3.2 采集项与故障覆盖

所有命令均为只读 `get` / `logs`，统一带 `--context <ctx> -n <ns> --request-timeout=20s`。

| 采集项 | 命令 | 覆盖 |
| --- | --- | --- |
| `POD_STATUS` | `kubectl get pods [-l app=workload] -o json` | CrashLoopBackOff、ImagePullBackOff/ErrImagePull/InvalidImageName、Pending、OOMKilled（state/lastState）、restartCount |
| `PREVIOUS_LOGS` | `kubectl logs <pod> [-c container] --previous --tail=200` | 崩溃前日志；没有上一实例时归为数据缺失而非故障 |
| `EVENTS` | `kubectl get events -o json`（可 `--field-selector involvedObject.name=`） | FailedScheduling（insufficient → 节点压力）、FailedMount/FailedAttachVolume、Unhealthy（probe failed）、镜像拉取失败 |
| `PVC` | `kubectl get pvc -o json` | 非 Bound（Pending/Lost） |
| `NODE_CONDITIONS` | `kubectl get nodes -o json` | MemoryPressure/DiskPressure/PIDPressure、Ready=False |
| `ENDPOINT_SLICE` | `kubectl get endpointslices [-l kubernetes.io/service-name=workload] -o json` | 空 endpoints、`conditions.ready=false` |

- **时间窗**：`sinceMinutes`（默认 60，夹在 1..1440），事件按 `lastTimestamp/eventTime/firstTimestamp` 过滤。
- **预算**：单命令 25s 超时，整单最多 8 条命令；用尽置 `truncated=true`，不把"没采完"当成"没问题"。
- **结构化证据**：每个检查项给 `name/status/command/collectedAt/summary/itemCount`；每个发现给 `type/severity/resourceKind/resourceName/namespace/summary/evidenceCommand/evidenceAt/detail`，`evidenceAt` 来自事件时间或采集时刻。

### 3.3 三态判定（关键口径）

| 状态 | 判定 | 含义 |
| --- | --- | --- |
| `NO_PERMISSION` | 非 0 退出且 stderr 含 forbidden / unauthorized / cannot | RBAC 拒绝，**不能翻译成"无异常"** |
| `DATA_MISSING` | 非 0 退出且 stderr 含 NotFound / not found / no resources found，或按 workload/pod 查询为空 | 采集不到，不能当成"检查通过" |
| `FAULT` | 检查项命中真实故障特征 | 有结构化证据支撑的故障 |
| `OK` / `ERROR` | 正常 / 其他执行错误 | 采集成功或工具异常 |

结果整体附带 `permissionDenied`、`dataMissing`、`truncated`，调用方必须在两者都为 false 时才可宣称为"已观测且无故障"。

## 6. 本轮未做（明确边界）

1. **可靠事件投递**：当前没有需要外部投递的 Run 事件消费者，清单中"必要时"的前提不成立，未引入 outbox。
2. **写操作诊断**：OPS-05 只做只读诊断，不包含 rollout/restart 等修复动作；修复仍走审批 + Run 通道。
3. **EndpointSlice 过滤**：仅按 `kubernetes.io/service-name` 过滤，不做本地二次过滤；`kubectl get nodes` 按规范仍带 `-n`（集群级资源会忽略）。
4. **网络链路**：DNS→LB/Ingress→Service→EndpointSlice→Pod 的逐层串联属于 OPS-06，未在本轮展开。
