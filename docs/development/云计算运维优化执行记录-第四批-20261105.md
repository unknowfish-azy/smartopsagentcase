## 2. OPS-06 网络链路诊断

位置：`backend/src/main/java/com/smartops/diagnostics/network/`
入口：`POST /api/operations/network/diagnose`

### 2.1 调用方式

```json
{
  "runtimeId": "runtime-1",
  "context": "prod-hz",
  "namespace": "payment",
  "host": "api.example.com",
  "port": 443,
  "ingress": "payment-api",
  "service": "payment-api",
  "workload": "payment-api",
  "tls": true,
  "timeoutSeconds": 60
}
```

所有 kubectl 命令统一带 `--context <ctx> -n <ns> --request-timeout=15s`，参数走白名单正则，不拼接自由文本。

### 2.2 九层链路

| 层 | 命令 | 判定 |
| --- | --- | --- |
| `DNS` | `getent hosts <host>` | 解析成功 → OK；`not known`/NXDOMAIN → FAILED；无该命令 → UNVERIFIED |
| `INGRESS` | `kubectl get ingress <name> -o json` | `status.loadBalancer.ingress` 为空 → FAILED（负载均衡未下发地址） |
| `SERVICE` | `kubectl get svc <name> -o json` | `spec.selector` 为空 → FAILED（不会有 EndpointSlice） |
| `ENDPOINT_SLICE` | `kubectl get endpointslices -l kubernetes.io/service-name=<svc> -o json` | ready 端点为 0 → FAILED，逐个记录 `conditions.ready=false` |
| `POD` | `kubectl get pods [-l app=<workload>] -o json` | Ready 不为 True 的 Pod 计入证据，全部未就绪 → FAILED |
| `NETWORK_POLICY` | `kubectl get networkpolicy -o json` | 用 `matchLabels` 对 Pod 标签做子集匹配；命中即 OK 但摘要写明"需人工确认规则是否放行" |
| `TLS` | `openssl s_client -connect <host>:<port> -servername <host> -verify_return_error` | `Verify return code: 0` → OK；其他 code → FAILED 且证据带 code |
| `SECURITY_GROUP` | 无 | 恒定 `UNVERIFIED`：本仓库未接入云安全组只读接口，需在云侧核验，不得视为通过 |
| `ROUTE` | 无 | 恒定 `UNVERIFIED`：同上 |

### 2.3 上游阻断与状态口径

- `DNS` 失败 → `TLS` 的 `blockedBy=DNS`；
- `SERVICE` 失败/不存在 → `ENDPOINT_SLICE`、`POD` 的 `blockedBy=SERVICE`；
- `ENDPOINT_SLICE` 失败 → `POD` 的 `blockedBy=ENDPOINT_SLICE`；
- 被阻断层**仍继续采集**（作为证据），但摘要强制前缀"上游 X 未通过，本层结果不可采信"；
- 状态：`OK` / `FAILED` / `NO_PERMISSION` / `DATA_MISSING` / `UNVERIFIED` / `NOT_APPLICABLE` / `ERROR`；
- 用户未提供的输入（无 host / 无 service / 无 ingress）→ `NOT_APPLICABLE`，**不允许**默认 OK；
- 预算：单命令 15s、整单最多 10 条命令、`timeoutSeconds`（夹 10..180，默认 60）总超时，超了置 `truncated`。

## 3. OPS-07 数据库真实诊断

位置：`backend/src/main/java/com/smartops/diagnostics/database/`
入口：`POST /api/operations/database/diagnose`

### 3.1 只读与限额

| 约束 | 落点 |
| --- | --- |
| 只读账号 | 凭据引用 `credential:<operation_credential.id>`（仅本人）或 `env:<NAME>`，明文格式 `username:password`；不落库、不打印 |
| 只读会话 | `Connection.setReadOnly(true)`；真实 MySQL 额外执行 `SET SESSION TRANSACTION READ ONLY` |
| 单语句 | `ReadOnlySqlGuard`：只允许 `SELECT` / `SHOW`，拒绝多语句、`INTO OUTFILE/DUMPFILE`、`FOR UPDATE`、`LOCK IN SHARE MODE` 及任何 DML/DDL 首关键字 |
| 耗时 | 每条语句 `setQueryTimeout`（夹 1..30s，默认 10） |
| 行数 | `setMaxRows`（夹 1..1000，默认 200） |
| 字节 | 证据按 `EVIDENCE_MAX_BYTES` 截断并标 `[TRUNCATED]` |

### 3.2 五项 MySQL 检查

| 检查 | 语句 | 判定 |
| --- | --- | --- |
| `CONNECTIVITY` | `SELECT 1` | 连通即 OK |
| `READ_ONLY_SESSION` | `SELECT @@session.transaction_read_only` | 1 → OK；0 → WARNING（会话语义已强制只读，但实例不是只读副本） |
| `LOCK_WAITS` | `performance_schema.data_lock_waits` 关联 `data_locks` | 有等待 → WARNING 并给前 5 行；无等待 → OK；表不存在 → DATA_MISSING |
| `SLOW_SQL` | `performance_schema.events_statements_summary_by_digest` | 单条摘要累计 ≥1s → WARNING；`DIGEST_TEXT` 必须经 `SqlSanitizer` 脱敏后才进证据；表不存在 → DATA_MISSING |
| `REPLICATION_LAG` | `SHOW REPLICA STATUS` | 空结果 → NOT_APPLICABLE（不是从库）；复制线程未运行 → WARNING；延迟 >60s → WARNING；否则 OK |

`overallStatus`：有 FAILED → `FAILED`；有 WARNING → `WARNING`；仅 DATA_MISSING → `INCOMPLETE`；否则 `OK`。
`performance_schema` 缺失、`SHOW REPLICA STATUS` 不支持一律归 `DATA_MISSING`，**不冒充故障、也不冒充健康**。

### 3.3 慢查询脱敏

`SqlSanitizer.sanitize`：剥离 `/* */` 与 `-- ` 注释 → 单/双引号字面量替换为 `?` → 裸数字替换为 `?` → 压缩空白 → 截断 300 字。
`DatabaseCheck` 在构造时即对 `sql` 字段脱敏，避免调用方忘记。

### 3.4 审计

迁移 `V20261105.9__database_diagnosis_audit.sql` 新增 `database_diagnosis_audit`：
`actor_id / team_id / engine / target_host / target_port / database_name / credential_source / status / check_summary / error_code / created_at`。

- 成功与失败都记一行；失败带稳定错误码（`DB_CREDENTIAL_*`、`DATABASE_CONNECTION_FAILED`）；
- 越权（teamId 非成员）在写审计**之前**拒绝，不留伪造记录；
- 引擎非法/未实现不连库、不写审计；
- 审计表不存凭据、不存未脱敏 SQL。

### 3.5 工具目录契约

`OperationToolService` 中 `database-readonly`、`mysql-slow-query` 由 `TEMPLATE` 改为 `REAL`，不再渲染仓库里不存在的 `smartops db ...` CLI，渲染改为指向新端点的说明行；`target=DATABASE`、`credential=database-readonly`。目录其余工具未改动。

### 3.6 PostgreSQL / openGauss 预留

`DatabaseEngine.POSTGRESQL` / `OPENGAUSS` 已声明为 `implemented=false` 并带不可用原因；`DatabaseDiagnosticAdapter` 只按 `engine()` 选适配器，新增适配器即可接入，无需改服务层。本轮未注册适配器，也没有对应驱动依赖。

## 4. 验收对照

| 清单验收项 | 证据 |
| --- | --- |
| 每层报告检查项、实际证据和失败原因 | `NetworkLayer.checks[]` 含 `name/status/command/evidence/collectedAt/itemCount`；每层 `summary` 给失败原因 |

## 6. 本轮未做（明确边界）

1. **安全组 / 路由表**：未接入云网络只读 API，两层层固定 `UNVERIFIED`，需要在云侧或后续接 OPS-02 的云适配层补齐。
2. **KubeSkoop 等内核级数据面诊断**：清单列为参考项，未引入；当前只做控制面对象与 TLS 校验。
3. **NetworkPolicy 规则求值**：只按 `matchLabels` 判断策略是否作用于目标 Pod，不展开 `matchExpressions` 与端口/协议求值。
4. **PostgreSQL / openGauss 适配器**：仅留接口与枚举，未实现具体检查语句，也未加驱动依赖。
5. **数据库写操作**：OPS-07 只做只读诊断，不包含 kill 会话、加索引等修复动作。
