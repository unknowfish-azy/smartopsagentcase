## 2. 四层 run 关联矩阵

本次取证验证的核心契约：**一次请求的 `run_id` 必须在 5 处出现且一致**。

| 出现位置 | 形态 | 本轮证据 |
|---|---|---|
| HTTP 响应头 | `X-Run-ID`（FastAPI `correlation_headers()` 写入） | ✅ 4/4 场景全部回显，curl/httpx 可见 |
| SSE 启动事件 | `event=run → data.run_id`（AI Service `chat_stream` yield） | ✅ 4/4 场景，与 header 一致 |
| SSE 完成事件 | `event=done → data.metadata.run_event.run_id`（`chat_stream` 第 231 行注入） | ✅ 4/4 场景，与 header 一致 |
| AI Service 日志 | `chat.start` / `chat.terminal` 的 `run_id` 字段 | ✅ 结构化日志，与 SSE 一致 |
| Knowledge 日志 | `knowledge.search` 的 `run_id` 字段 | ✅ 结构化日志，由 AI Service 转发 |

完整 run_event 结构：

```json
{
  "schema_version": "1.0.0",
  "event_id": "uuid-hex",
  "request_id": "req-e2e-xxx",
  "task_id": "task-e2e-xxx",
  "run_id": "uuid-hex-or-explicit",
  "step_id": null,
  "source": "ai-service",
  "status": "succeeded",
  "timestamp": "ISO8601"
}
```

## 4. 两类"假 Bug"诊断

E2E 过程中出现两次"工具返回失败 → 推理定位 → 启动新进程 → 自动修复"的典型场景。关键教训：**pytest TestClient 不经过真实 HTTP 层，不能替代 httpx/curl 直接验证**。

### 4.1 Bug A：HTTP 响应头 correlation headers 缺失

| 项 | 详情 |
|---|---|
| 症状 | httpx + curl 调 `/api/chat` 和 `/api/chat/stream`，7 个 header 全无 `X-*` |
| 误判 | StreamingResponse chunked encoding 丢 headers？correlation_headers dict 展开不对？ |
| 真因 | AI Service 进程 PID 56128 是早期版本代码（旧版本 correlation.py） |
| 修复 | `Stop-Process -Id 56128` + 从 `ai-service/` 子目录重启 |
| 结果 | 重启后立即正常，无需改代码 |

### 4.2 Bug B：done 事件 metadata 缺 run_event

| 项 | 详情 |
|---|---|
| 症状 | done metadata 只有 rag_enabled/top_k/version/degraded |
| 真因 | 同 Bug A，运行的是旧进程 |
| 修复 | 同一次重启解决 |
| 确认 | `chat_service.chat_stream` 第 230-231 行的注入代码 HEAD 48b8af47 已存在 |

### 4.3 诊断流程摘要

```
curl 调 AI Service → 7 header 无 correlation
  → 加 print 到 chat.py 查 StreamingResponse headers dict
    → 最小复现（独立 FastAPI StreamingResponse）header 正常
      → 排除通用 bug
        → Kill 旧进程 + 重启
          → 立即正常 ✅
```
