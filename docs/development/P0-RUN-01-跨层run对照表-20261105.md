## 1. 本轮实现

| 层 | 变更 | 文件 |
|---|---|---|
| 前端 | SSE 请求同时发送 `X-Request-ID` / `X-Task-ID`，与请求体 `metadata` 使用同一组值；所有 Java API 请求携带 `X-Request-ID` | `frontend/src/api/stream.ts`、`frontend/src/utils/request.ts` |
| AI Service | 统一解析/校验三个 ID（请求体优先，Header 兜底，`run_id` 由 Header 或服务端生成）；响应回显 `X-Request-ID` / `X-Task-ID` / `X-Run-ID`；SSE 事件：启动时 `event=run`（started）、结束时 `event=done` 的 `metadata.run_event`（succeeded/failed）；两者 `run_id` 与 HTTP header 一致；`chat.start` / `chat.rag` / `chat.terminal` 结构化日志只含 ID、状态与固定档位 | `ai-service/app/core/correlation.py`、`app/api/chat.py`、`app/services/chat.py` |
| AI → Knowledge | 检索请求转发同一组关联 ID，与 `X-API-Key` 并存 | `ai-service/app/services/rag.py` |
| Knowledge | `/api/search` 接收、校验、回显关联 ID；日志只记录 ID、`status` 与结果数，不记录 query | `knowledge/server.py` |
| 执行器 | 终态日志记录 `request_id` / `task_id` / `run_id` / `status` / `step_id`；不记录命令与参数 | `agent/executor/executor.py` |

ID 规则与 `run-event-v1` 一致：`[A-Za-z0-9][A-Za-z0-9_.:-]{0,95}`；非法值被替换为新 ID，不会原样回显或落日志。

## 4. 两类"假 Bug"诊断与根因

E2E-OBS-P0-01 过程中诊断出两个"工具返回失败 → 定位 → 修复"的典型场景，实际都是**旧进程残留**：

### 4.1 Bug A：HTTP 响应头 correlation headers 缺失

**症状**：httpx / curl 真实调用 `/api/chat` 和 `/api/chat/stream`，7 个响应 header 中没有 `X-Request-ID / X-Task-ID / X-Run-ID`。

**误判**：一开始怀疑 uvicorn StreamingResponse + Transfer-Encoding: chunked 的通用 bug，或 correlation_headers dict 展开问题。

**根因**：AI Service 进程是早期启动的旧版本代码（PID 56128，命令行 `python -m uvicorn app.main:app`，从 `ai-service/` 子目录启动但加载了 `correlation.py` 有 bug 的版本）。

**确认步骤**：
1. pytest TestClient 全部通过（它不经过 uvicorn HTTP 层，直接调 ASGI app → 假阳性）
2. 最小复现（`uvicorn.run(app, ...)` 直接起一个 StreamingResponse endpoint）header 正常 → 排除通用 bug
3. **重启 AI Service**（先 stop `56128`，再从正确目录 `ai-service/` 启动）→ 立即正常

**修复**：`Kill 56128` + 正确启动命令。**代码本身无 bug**。

### 4.2 Bug B：SSE done 事件 metadata 缺 run_event

**症状**：旧进程返回的 done 事件 metadata 只有 `rag_enabled/top_k/version/degraded`，没有 `run_event` 字段。

**根因**：与 Bug A 同进程根因。`chat_service.chat_stream` 第 230-231 行的 `event["data"]["metadata"]["run_event"] = record` 早已存在（git HEAD 48b8af47），但运行中的进程是更早的版本。

**修复**：与 Bug A 同一次重启解决。

**教训**：pytest TestClient 只能验证 ASGI 应用代码逻辑，**不能替代真实 HTTP 客户端调用**。每次声称"服务已启动"后，必须用 curl/httpx 直接调一次，而不是依赖 pytest。

## 5. 仍未闭环

1. **Java 聊天入口**：前端直连 AI Service，不经过 Java。要让同一次 run 贯穿 Java，需要 ARCH-P0-01 签发信封 + ARCH-P0-02 权威 Run 账本。
2. **Java `trace_id` ↔ AI `run_id`**：两套独立 ID，无映射表。Java 环境阻塞（JDK 8 vs pom.xml 17，scoop openjdk21 与 Windows 不兼容）。
3. **Provider trace**：Ollama 调用仍无独立 span。降级只暴露 `effective_provider` / `degradation_reason`。
4. **降级原因脱敏**：`degradation_reason` 可能包含异常消息（内部地址），建议改固定错误码。
5. **真实 Provider 故障注入**：本轮降级用"不可达 Ollama"验证回退，不是真实 qwen3 中断；归 P0-E2E-02。
