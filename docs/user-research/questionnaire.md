````markdown
# 智维Agent 用户访谈方案

## 1. 访谈目的

本访谈用于验证智维Agent项目所针对的运维问题是否真实存在，以及目标用户目前的工作方式、主要痛点、对AI辅助运维的接受程度和安全顾虑。

核心目标：

```text
了解真实运维流程
        ↓
发现真实痛点
        ↓
确认用户需求
        ↓
验证产品假设
        ↓
调整产品功能
        ↓
验证商业化方向
````

本访谈不是为了证明：

> “用户一定需要智维Agent。”

而是通过真实用户反馈判断：

```text
问题是否真实
问题是否频繁
现有方法是否足够
用户愿不愿意使用AI
用户最担心什么
哪些功能最有价值
```

---

# 2. 用户研究基本原则

用户研究必须遵循：

```text
真实
客观
可追溯
不诱导
不虚构
```

---

# 3. 不允许虚构访谈数据

在尚未完成实际访谈前：

不要填写：

```text
已经采访100家企业
90%的运维人员认为……
95%的用户愿意使用……
```

也不要把：

```text
团队内部讨论
```

写成：

```text
用户反馈
```

正确状态：

```text
计划访谈
待访谈
已预约
已完成
待整理
```

---

# 4. 目标用户

优先访谈：

```text
IT运维人员
服务器管理员
开发兼运维人员
企业技术负责人
小型企业IT负责人
```

---

# 5. 用户筛选条件

优先选择有实际运维经验的用户。

例如：

```text
经常管理Linux服务器
经常处理Nginx/MySQL/Docker
处理过服务器故障
负责企业内部系统维护
使用过监控或日志平台
```

不是所有程序员都适合作为本项目核心访谈对象。

---

# 6. 用户角色分类

为了便于分析，可以分为：

```text
A：
专业运维人员

B：
开发兼运维

C：
企业IT管理员

D：
技术负责人
```

---

# 7. 访谈规模

项目初期可以采用小规模深度访谈：

```text
5～10人
```

用于：

```text
问题探索
产品验证
```

后续可以继续扩大。

注意：

> 这里是访谈计划，不是已经完成的样本数量。

---

# 8. 访谈方式

可以采用：

```text
面对面
视频会议
电话
在线语音
文字访谈
```

优先：

```text
半结构化访谈
```

即：

```text
固定核心问题
+
根据回答继续追问
```

---

# 9. 单次访谈时间

建议：

```text
20～40分钟
```

结构：

```text
5分钟
了解背景

10～15分钟
了解运维工作

10分钟
了解痛点

5～10分钟
展示概念/Prototype并收集反馈
```

具体时间根据用户情况调整。

---

# 10. 访谈开场白

建议使用：

> “我们正在做一个面向中小企业的AI智能运维系统，希望了解真实运维人员在服务器故障、知识查找和日常维护过程中遇到的问题。今天主要想听您的实际经验，没有标准答案，也不是在测试您的技术能力。”

然后补充：

> “我们会把您的回答用于产品研究，不会要求您提供密码、密钥等敏感信息。”

---

建议：

```text

```


# 24. 第十一部分：Agent任务体验

向用户展示：

```text

3. 搜索知识
```

> “这种方式和您目前的工作方式相比，有哪些地方有帮助，哪些地方可能反而麻烦？”

# 29. 用户痛点评分

可以让用户对以下问题进行：

```text
1～5分
```

评分。

| 问题         |  评分 |
| ---------- | --: |
| 找运维资料困难    | 待访谈 |
| 故障定位耗时     | 待访谈 |
| 版本知识混乱     | 待访谈 |
| AI回答不可靠    | 待访谈 |
| AI自动操作存在风险 | 待访谈 |
| 历史经验难复用    | 待访谈 |
| 缺少完整审计     | 待访谈 |

其中：

```text
1 = 非常不严重
5 = 非常严重
```

正式统计必须使用真实访谈结果。

# 36. 用户原话记录原则

非常重要的信息尽可能保留用户原话。

例如：

```text
“每次出问题我第一反应还是问老员工。”
```

或者：



但需要获得适当使用授权，并进行必要匿名化。

# 51. 用户对Evidence的验证

重点研究：

```text
用户是否真的需要Evidence？
```

不要默认：

```text
Evidence一定有价值
```

可以询问：

> “如果AI回答‘建议重启服务’，您最希望看到哪些信息？”

根据用户反馈判断：

```text
来源
版本
原因
历史案例
风险
```

哪些是真正重要的。

---

# 52. 用户对Trust的验证

不要直接问：

> “您需要Trust Score吗？”

因为用户可能不知道这个概念。

更好的问题：

> “当AI给出一个故障解决方案时，哪些信息会让您更相信它？”

再把回答映射到：

```text
Evidence
Version
Source
Explanation
```

---

# 53. 用户对Agent的验证

不要直接说：

> “我们的Agent可以自动重启服务，您觉得好不好？”

这容易诱导。

更好的方式：

分别询问：

```text
查看状态
查看日志
执行检查
修改配置
重启服务
删除数据
```

让用户逐项判断：

```text
自动
人工确认
禁止
```

---

# 54. 用户对风险等级的验证

可以从用户自然判断建立：

```text
User-perceived Risk
```

再与：

```text
System Risk
```

进行比较。

例如：

```text

重启Nginx

用户判断：
高风险

系统：
HIGH
```

这可以用于验证风险策略设计。
