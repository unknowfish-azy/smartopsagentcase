# 知识审核 · 图谱工作台 设计标准 v1

> 目标：把 `/knowledge/review`（知识审核）的主交互元素从「候选列表 + 详情」换成「一张图」。
> 图上每个节点都是真实的候选、知识条目或审核事件；采纳与驳回在图上就地完成，候选正文退到右侧栏。

| 项 | 值 |
| --- | --- |
| 复刻对象 | [jihe520/agent-graph](https://github.com/jihe520/agent-graph)（MIT，核查时点本次会话 GitHub API 实时查询） |
| 复刻边界 | 只复刻**交互模型与视觉语言**，颜色/尺寸/文案一律换成本项目 `--ds-*` 令牌，组件自己写（遵循 `design-system/MASTER.md` Open Source Intake 默认方法） |
| 落地范围 | 仅 `frontend/src/views/knowledge/KnowledgeCandidateReviewView.vue` 及其新增子组件；不动路由、导航、`api/operations.ts` 契约 |
| 宿主设计面 | 工具层（控制台）：半径 4-8px、1px 发丝线、平面底色、**零 `backdrop-filter`**、无粒子、无 WebGL |
| 状态 | 设计标准 + 参考原型；不含生产代码 |

本文件用三级措辞，和上游标准一致，含义固定：

- **必须**：模型成立的前提，为了适配不能去掉
- **应该**：推荐做法；宿主条件不允许时可降级，但要在实现说明里写清降级点
- **可以**：可选

---

## 1. 为什么换主元素

现有审核界面回答不了这些问题：

- 这条候选是要**新建**知识，还是要**补进**已有条目？补进哪一条？
- 同一个知识条目上，除了我看到的这条，还有几条候选在排队？
- 这条候选是谁、在什么运行里产出的？证据链完整吗？
- 我上一次驳回的是哪条，理由是什么？同一个条目被驳回过几次？
- 哪些运行还在跑、马上就要产出新的候选？

这些问题的答案天然是一张**有祖先关系、有时间顺序、有归属**的图，而不是一列扁平的候选卡片。

## 2. 概念映射

概念先对齐，再谈界面。左列是上游模型，右列是本项目已有的数据实体，**不新增实体，只新增聚合视图**。

| 上游模型 | 本项目概念 | 数据来源（现有） |
| --- | --- | --- |
| 项目 project | **知识库** library：一张图对应一个知识库 | `personal_knowledge_library` |
| main / 主干 | **已入库**：该知识库中通过审核的条目集合，固定最左泳道 | `personal_knowledge_entry`（`verification_status = VERIFIED`） |
| 分支 branch | **知识条目** entry：一条条目一条泳道，版本号即提交 | `personal_knowledge_entry.version` |
| worktree | **来源运行** run：候选由哪次运行产出 | `operation_run_record` |
| agent | **候选** candidate：一条待处理的知识候选 | `knowledge_candidate` |
| 子 agent | **证据/步骤**：候选正文里的运行证据与命令输出，折叠成子行 | `operation_run_evidence`、`operation_run_output` |
| harness | **来源工具** toolId（`k8s.service.diagnose` 等），用颜色+首字母头像区分 | `knowledge_candidate.tool_id` |
| 提交 commit | **审核事件**：快照 / 采纳 / 驳回，一条一行 | `knowledge_candidate.status` + `updated_at` |
| PR 号 | **Trace ID**：候选与运行共用的可追溯标识 | `knowledge_candidate.trace_id` |
| 等你 | **待审** `PENDING_REVIEW` | 同左 |
| 完成 | **已采纳** `PROMOTED`：已写入条目，等你复核 | 同左 |
| 运行中 | **生成中**：来源 run 仍在执行，候选尚未成型 | `operation_run_record.status` |
| 空闲 | **已驳回** `REJECTED`：留档但不再需要动作 | 同左 |
| 合并到 main | **采纳并入库** `POST /api/knowledge/candidates/{id}/promote` | 同左 |
| 变基 | **按新证据重新生成** `POST /api/knowledge/candidates/from-operation-run/{runId}` | 同左 |
| 移除 worktree | **丢弃候选**（仅 `REJECTED` 后可用） | — |
| 菜单里的 git 命令预览 | **将要执行的接口 + 写入目标**（库/条目/版本） | 服务端契约 |

### 2.1 节点状态（四种，和上游一一对应）

| 状态 | 含义 | 触发数据 | 呈现在图上 |
| --- | --- | --- | --- |
| **待审** | 等你采纳或驳回 | `status = PENDING_REVIEW` | 琥珀色；头像外一圈光晕 + 呼吸；右上 `!` 角标；整行从左侧淡琥珀渐隐；第二行直接给「采纳 / 驳回」 |
| **生成中** | 来源运行还在跑 | run `status = RUNNING` | 来源工具色；头像外一段旋转弧；显示已用时间与最近一次工具调用 |
| **已采纳** | 已写入条目，等你复核 | `status = PROMOTED` | 头像去饱和，右下绿色对勾角标；第二行是写入结果「条目 v3 → v4」 |
| **已驳回** | 留档，不再需要动作 | `status = REJECTED` | 中性灰，头像 `opacity .55`，无环；第二行是驳回原因 |

排序（**必须**）：条目与候选按「最需要你的」在前：

```
待审 → 生成中 → 已采纳（待复核） → 已驳回
```

同状态内按 `created_at` 由新到旧。

## 3. 布局

**必须**

- 一张图纵向分两段，共用同一套泳道，泳道与行**严格对齐**：
  - **上段「待审」**：按知识条目分组。每组依次是条目行、挂在该条目上的候选行、候选的子行（证据）。
  - **下段「演化史」**：审核事件与入库快照，从新到旧。
- 左边是泳道，右边是行内容；泳道宽度在一次会话中只增不减，避免列宽跳动。
- 上段有自己的底色（`--ds-surface-raised` 之上一层极淡面板），与下段之间留 20px 间隔；组与组之间用 1px 发丝线（`--ds-color-border`）分隔。

**应该**

- 顶栏 52px 吸附：知识库切换 · 状态汇总 · 来源工具筛选 · 着色切换 · 密度 · 图例。
- 右侧 400px（360–460）侧边栏：默认关闭；点候选行打开，再点关闭。图的宽度让出，但**图始终可见**。
- 只有一个知识库时去掉知识库切换；只有一个来源工具时去掉来源工具筛选（见 §9 适配）。
- 列变窄时依次隐藏：短 ID → Trace ID → 相对时间；候选标题可截断两行，工具名与条目名不截断。

**可以**

- 参考尺寸：候选行 56px、条目行 34px、提交行 30px、子行 28px、泳道宽 22px。
- 密度 `compact` 时行高 ×0.85（候选行 48 / 条目行 30 / 提交行 26 / 子行 24）。

### 3.1 断点

严格沿用 `src/design/breakpoints.js` 的 375 / 768 / 1024 / 1440 / 1920，不新增取值。

| 宽度 | 形态 |
| --- | --- |
| ≥1440 | 图 + 常驻 400px 侧栏 |
| 1024–1439 | 图 + 侧栏覆盖（overlay，从右侧滑入，图不重排） |
| 768–1023 | 图全宽；侧栏为整屏抽屉；顶栏收成两行 |
| <768 | 图全宽、行内操作降级为「⋯」菜单；泳道 22px 不变，行内容左对齐换行 |

## 4. 泳道与标记

**必须**

- 「已入库」固定在最左泳道（lane 0）。其余每条知识条目各占一条，放在它从主干分出的那条泳道右边，从分叉点延伸到最后一次事件；互不重叠的条目可以共用一条泳道。
- **未归类**候选单独一条泳道，固定在最右，暗灰（`--ds-lane-quiet`）。详见 §8 数据缺口 A。
- 条目行、候选行、子行都画在它所属的泳道上：
  - 条目：12×12 圆角方块（`rx 3`）；已归档时变灰
  - 候选：28px 圆形头像（来源工具首字母）+ 状态环（见 §2.1）
  - 子行（证据）：6px 圆点；有未读时轻微脉动
- 每组「待审」的最后一行用**虚线**连到该条目当前的版本位置。
- 候选要写入的是**另一个**条目时，用点线从候选连到目标条目泳道。
- 普通事件是实心点（`r 4.5`）；入库/采纳这类合并事件是空心圈（`r 5`，`stroke 2`）。

**应该**

- 两种着色方式，可切换：
  - **按来源工具**（默认）：泳道取正在该条目上产出的工具色；主干与无人产出的条目用中性灰；提交点按事件来源着色。
  - **按知识条目**：每条条目一个色，提交点跟随条目。
- 历史被折叠时，泳道延伸到底部并渐隐（`linear-gradient` 遮罩，不用 blur）。
- 分支标签（条目名 chip）显示在该条目最新事件的那一行；条目被采纳进主干后，标签带「已入库」小图标。

### 4.1 实现关键（**必须**）

泳道用一层绝对定位的 `<svg>` 覆盖在行容器上。**行高与泳道坐标必须出自同一份数据**：

```js
// 单一事实来源：一次算出所有行的 y，DOM 与 SVG 都读它
const rows = [...]                       // [{id, kind, lane, h, laneFrom, laneTo}]
let y = 0
for (const r of rows) { r.y = y; y += r.h }
const laneX = lane => PAD_X + lane * LANE_W + LANE_W / 2
```

禁止用 `getBoundingClientRect()` 反推泳道坐标：滚动、字体加载、密度切换都会让两者漂移。

## 5. 行内容

- **条目行（34px）**：条目名 · 版本 chip（`v3`）·「待审 n」·「已入库」标记 · 右侧是变更概览（`3 条候选 · +2 −1 段`）。无候选时写「无待审候选」。
- **候选行（56px，两行）**：
  - 第一行：来源工具名（粗）· 状态词 · 用时/相对时间 · 候选标题；右侧是「目标条目」chip（未归类时是 `待归类`）。
  - 第二行随状态变化：
    - 待审：`→ 采纳到「K8s Service 排障」` + `[采纳]` `[驳回]`
    - 生成中：最近一次工具调用，等宽字体，如 `kubectl get endpointslice -n demo`
    - 已采纳：`已写入「K8s Service 排障」v3 → v4` + `[查看条目]`
    - 已驳回：`驳回：证据不足（缺上游日志）` + `[重新生成]`
- **子行（28px）**：树形连接符 `└` + 名称 + 计数/状态；右侧是证据来源 `source_ref`。
- **提交行（30px）**：事件标签 chip（采纳/驳回/入库/快照）+ 说明 · 右侧是作者色块 · 相对时间 · 短 ID。

省略条目行时（开关），条目的信息（版本、待审数、Trace）合并到它的第一条候选行，没有候选的条目不显示。

## 6. 交互

### 6.1 图

**必须**

- 点候选行 → 右侧打开证据与正文；再点一次关闭。图让位但保持可见，选中行高亮并滚到可见区。
- 待审行上直接「采纳 / 驳回」，不需要进侧栏。
  - 采纳：先选目标条目（`并入已有条目` 或 `新建条目`），再提交 `POST /{id}/promote`。
  - 驳回：必须填原因（就地 popover，单行输入 + 提交），提交 `POST /{id}/reject`。
- 右键候选行 / 条目行 / 提交行 → 审核快捷菜单（见 §7）。
- 每次点击动作前**重新校验前置条件**：服务端返回 `409 KNOWLEDGE_CANDIDATE_NOT_PENDING` 时，不执行、刷新该行、把状态改成真实值并提示「该候选已被处理」。
- 动作完成后给出结果与实际请求（方法 + 路径 + 写入目标），不用模态框打断，用行内联提示 + 侧栏底部 toast。

**应该**

- 点其他行 → 聚焦该条目的整条泳道与它的候选，其余内容变淡（`opacity .4`）；再点一次取消。
- 顶栏：
  - 知识库切换，每个库标出待审数量
  - 状态汇总（`3 待审` `12 条目`），点击依次轮换到下一个该状态的行
  - 来源工具筛选：筛掉的变淡而不隐藏，图结构不变
  - 着色方式、密度、显示/隐藏条目行、子行、图例
- `Esc` 逐级退出：菜单 → 侧栏 → 聚焦 → 清空筛选。
- 实时更新不打断操作：鼠标按下时不重绘；行有稳定 ID（`candidate-{id}` / `entry-{id}`），更新后选中、菜单、文本选择都保留。
- 新行、新事件有轻微入场动画（`--ds-duration-spring` 200ms，`--ds-ease-out`），遵守 `prefers-reduced-motion`。

### 6.2 侧边栏（证据与正文）

**必须**

- 复用现有 `renderKnowledgeMarkdown` 与 `DecodeText`，不另造一套 Markdown 渲染。
- 头部：来源工具 · 状态 · 用时 · 目标条目 · Trace ID · 运行记录号 · 生成时间。
- 正文里的**版本引用可点击**（如「v3」）：图滚动到对应提交行并短暂高亮；在折叠的历史里时先展开。
- 底部固定操作条：`采纳`（主）/ `驳回并记录原因`（次）。非 `PENDING_REVIEW` 时整条置灰并写明原因。
- 侧栏打开时保留图的滚动位置，不跳到顶部。

### 6.3 键盘

| 键 | 行为 |
| --- | --- |
| `↑` `↓` | 在上段可操作行之间移动焦点（跳过子行） |
| `Enter` | 打开/关闭该行的侧栏 |
| `A` | 焦点在待审行时采纳（进入目标条目选择） |
| `R` | 焦点在待审行时驳回（进入原因输入） |
| `Esc` | 逐级退出 |
| `F` | 聚焦当前条目链 |
| `?` | 打开图例 |

## 7. 审核快捷菜单

菜单作用于一行，本质是「对一个候选 / 一个条目 / 一个事件能做什么」。

**必须**

- 菜单顶部显示对象：候选标题、目标条目、当前状态。
- 每一项要么可用，并写明**将要执行的请求与写入目标**；要么置灰，并写明**原因**。多个原因只写最根本的一个。
- 点击时重新检查条件；条件变了就刷新菜单、显示新原因、不执行。
- 执行后提示结果和实际请求。
- 写操作走现有 API 契约与权限机制，不绕过。

| 菜单项 | 什么时候不可用（按顺序检查） | 提示信息 | 将执行的请求 |
| --- | --- | --- | --- |
| 采纳并入库 | 状态不是 `PENDING_REVIEW`；未选目标条目 | 若已采纳：「已采纳于 2 小时前」，并给「查看条目」 | `POST /api/knowledge/candidates/{id}/promote` `{libraryId,title,contentMarkdown}` |
| 并入已有条目 | **本版本后端不支持**（见 §8 缺口 B）：`promote` 只新建 entry | 置灰并说明「当前后端只支持新建条目，条目合并需要 `target_entry_id`」 | 需要后端字段；暂不出现 |
| 驳回并记录原因 | 状态不是 `PENDING_REVIEW` | 原因必填：「请填写驳回原因」 | `POST /api/knowledge/candidates/{id}/reject` `{reason}` |
| 按新证据重新生成 | 来源 run 不存在；run 仍在运行 | 运行中：「来源运行还在执行，结束后可重新生成」 | `POST /api/knowledge/candidates/from-operation-run/{runId}`（会因 `UNIQUE(user_id,source_run_id)` 冲突，需后端支持覆盖；**置灰并说明**） |
| 查看证据正文 | 无 | — | 打开侧栏（纯本地） |
| 复制 Trace ID | 无 | — | 剪贴板 |
| 丢弃候选 | 状态不是 `REJECTED` | 未驳回：「先驳回，再丢弃」 | 未实现，占位并置灰 |

> **原则**：菜单里不允许出现「看起来能点、点了才报错」的项。不能做就置灰 + 写原因，这是上游标准的第 5 条原则，也是本项目 evidence-first 的直接延伸。

## 8. 数据缺口（**必须**在实现前确认）

这是把上游模型搬到本宿主时唯一真正需要决策的部分。三条都要在后端或接口层给结论，否则图会说了假话。

### 缺口 A：候选不知道自己属于哪条知识条目

`knowledge_candidate` 没有 `target_entry_id`，图上「候选挂在哪条条目泳道」无法从现有数据推出。

| 方案 | 改动 | 图上表现 | 评价 |
| --- | --- | --- | --- |
| **A1（推荐先落地）** | 无后端改动 | 候选默认挂在最右「待归类」泳道；采纳时由人选目标条目 | 立刻可上线；图永远可解释；代价是「待归类」会堆积，需要用筛选提示 |
| A2 | `ALTER TABLE knowledge_candidate ADD target_entry_id BIGINT NULL` + 生成时按标题/库做相似度预填（仅供参考） | 候选直接挂在目标条目的泳道上 | 推荐作为第二步；预填必须在 UI 上标「建议」 |
| A3 | 改 `promote` 语义：按 `libraryId + title` 匹配已有 entry 则 `version+1` | 采纳即「合并」 | 语义最贴近上游，但改变现有接口行为，需后端评审 |

### 缺口 B：采纳只能新建条目，没有「合并」语义

`PersonalKnowledgeService.createEntry` 每次新建，`version` 恒为 1。所以：

- **本版本文案必须诚实**：按钮写「采纳并新建条目」，第二行写「已新建条目 v1」，**不能**写「合并入 v4」。
- 只有在落地 A3 之后，才允许出现「合并」措辞与 `v3 → v4` 的版本推进。

### 缺口 C：候选列表拿不到「生成中」

`GET /api/knowledge/candidates` 只返回已生成的候选，不含仍在执行的 run。要让「生成中」这一行真实存在，需要二选一：

- 前端并行拉 `GET /api/operations/runs?status=RUNNING` 并按 `toolId` 关联，图上标为「生成中（未产出候选）」；
- 或后端在候选列表里补 `runStatus` 字段。

缺这一步时，「生成中」状态**不显示**，不要用假数据占位。

### 缺口 D：图需要跨页聚合

现有列表 `page/pageSize` 默认 20 条，图跨页会断线。落地时把审核图取数改为 `pageSize=200` 或新增 `status=ALL` 聚合端点；否则图上只显示「最近 20 条」，必须在图底部写明「仅显示最近 20 条 · 加载更早」。

## 9. 适配与降级

| 宿主条件 | 做法 |
| --- | --- |
| 只有一个知识库 | 去掉知识库切换与并排视图 |
| 只有一种来源工具 | 默认按条目着色，去掉工具筛选 |
| 没有子行数据（`operation_run_evidence` 为空） | 不显示子行与对应开关 |
| 没有「生成中」数据 | 不显示该状态（见缺口 C） |
| 窄屏（<768） | 顶栏只留「待审」计数与图例；候选行的目标条目 chip、相对时间、「→ 采纳到…」说明收进侧栏，行内只保留状态与采纳/驳回；条目行隐藏版本 chip |
| `prefers-reduced-motion` | 关闭呼吸、旋转、入场位移动画，状态改由静态角标 + 文字表达 |

窄屏的已知代价：泳道固定占 134px，375 宽下来源工具名会被截断成 `k8s…`，完整工具名与 Trace 从侧栏读。这是「泳道宽度不抖动」换来的，可接受，但要在实现说明里写明。

无论怎么适配，§10 的六条原则都要保留。

## 10. 原则（六条，与上游一致）

1. **图是主视图，正文从属于它。** 打开审核页先看到图；正文在右侧栏打开，关掉就回到图。
2. **一切挂在知识条目上。** 候选的位置是它要写入的条目，它的产出是版本推进。
3. **先看需要你的。** 待审排最前、最显眼，其次是已采纳待复核。
4. **就地处理。** 采纳、驳回在图上完成，不必进正文。
5. **不能做就说原因。** 不可用的操作保持可见、置灰、写明原因；可用的标出将要执行的请求与写入目标。
6. **显示的都是真的。** 每个状态都对应真实的候选、条目或运行状态；缺口未补齐前不呈现该状态。

### 11.2 泳道色（新增令牌，落在 `variables.css`）

```css
/* 来源工具 / 条目泳道色：只用于线与节点，不承担状态语义 */
--ds-lane-1: #2496ed;   /* 蓝，沿用 --ds-chart-1 */
--ds-lane-2: #7ad7f5;   /* 青，沿用 --ds-chart-2 */
--ds-lane-3: #8bcfb4;   /* 青绿，沿用 --ds-color-success */
--ds-lane-4: #9b8cf0;   /* 紫，新增（唯一新增色相，用于第 3+ 来源工具） */
--ds-lane-trunk: #8b949e;   /* 主干 = --ds-semantic-neutral */
--ds-lane-quiet: rgba(146,166,181,.45);  /* 无人产出的条目 / 待归类 */
--ds-lane-retired: rgba(159,190,207,.34); /* 已归档 */
```

规则：

- 来源工具按首次出现顺序分配 `lane-1 → lane-4`；**第 5 个起统一 `--ds-lane-quiet` + 首字母头像区分**，不扩色相（守住「语义色收敛、禁止彩虹」）。
- **琥珀 `#d29922`、红 `#f85149` 永不进入泳道色**：它们只表达「待审」「驳回」两种状态，避免与来源色混淆。
- 颜色**不是**唯一通道：每个状态同时有文字（待审/生成中/已采纳/已驳回）与角标形状。

### 11.3 字号与行高

| 元素 | 令牌 | 值 |
| --- | --- | --- |
| 顶栏英文标签、计数 | `--ds-type-overline-size` + mono + `letter-spacing .12em` | 11px |
| 元信息（时间、Trace、计数） | `--ds-type-caption-size` | 12px |
| 行正文 | `--ds-type-body-caption-size` | 13px |
| 工具名、条目名 | `--ds-type-body-size` / `500` | 14px |
| 侧栏标题 | `--ds-type-h3-size` | 18px |
| 行高 | `--ds-line-height-base` | 1.5 |

数字一律 `font-variant-numeric: tabular-nums`（`--ds-type-num`），否则相对时间会跳。

### 11.4 半径、阴影、动效

| 用途 | 令牌 | 值 |
| --- | --- | --- |
| 行 / 按钮 / chip | `--ds-radius-md` | 8px |
| 上段面板 / 侧栏 | `--ds-radius-lg` | 12px |
| 状态 pill / 头像 | `--ds-radius-pill` | 999px |
| 菜单浮起 | `--ds-elevation-3` | `0 12px 32px rgba(0,0,0,.42)` |
| 微交互 | `--ds-duration-micro` + `--ds-ease-out` | 150ms |
| 入场 | `--ds-duration-spring` | 200ms |

**禁止**：`backdrop-filter`（工具层 blur = 0）、粒子、WebGL、每帧 JS 重绘。状态环的呼吸/旋转只用 CSS `transform` / `opacity`，不改布局属性，不进入全局 rAF 调度。

## 12. 无障碍

- 行容器 `role="list"` / `role="listitem"`；选中行 `aria-selected`，可操作行 `tabindex="0"`。
- 泳道 `<svg>` 标 `aria-hidden="true"`：它是视觉冗余，状态与归属必须同时在文字里出现。
- 对比度：正文 ≥ 4.5:1，大字与图标 ≥ 3:1；「待归类」这类弱化文字不低于 `--ds-semantic-neutral`。
- 焦点可见：`2px` `--ds-focus-ring-color` + `offset 2px`，不被 `overflow:hidden` 裁掉。
- 触控：行高 ≥ 44px（候选行 56px 满足）；行内按钮热区 ≥ 32×32，`<768` 时收进菜单。
- 动效：`prefers-reduced-motion` 下所有循环动画静止，状态完整性由文字保证。
- 颜色不作为唯一信息通道（见 §11.2）。
