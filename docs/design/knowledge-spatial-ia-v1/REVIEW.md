# 对拍：并行实装 vs 本轮深度逆向

> 写这份时，`frontend/src/views/knowledge/space/` 已经有一版实装在跑（864 行，含 `useSpaceLayout.js` / `useSpaceCamera.js` / `PERF.md`）。
> 本节只做一件事：**把我这轮实测出来的差异列出来，指出哪几处值得改**，不重复设计。

---

## 1. 实装现状（读代码得到的）

| 能力 | 现状 | 位置 |
| --- | --- | --- |
| 域级虚拟化 | ✅ `mountedZoneIds` | `KnowledgeSpaceView.vue:247` |
| 卡级可见性 | ✅ `IntersectionObserver` | `:289` |
| L0 卡片 | **零卡片**（`if (lod === 0) return []`） | `:250` |

| 布局 | ✅ 抽成 `useSpaceLayout.js` | — |

整体方向与设计一致，且比我给的原型工程化程度高（拆了 composable、有 PERF）。

## 2. 三处值得改的地方

### ① L0 缺"密度肌理"——737 条看不出体量（**建议改**）

现在 L0 只有域块 + 标签 + 计数，域内是空面板。问题不是性能，是**信息**：用户在总览档看不到"这块有多密"。

我这一轮实测的做法（`space-app.html`）：**L0 用一域一个 `<svg>` 画 737 个 `<rect>`**，一次绘制，DOM 卡片仍然是 0。

```js
// 域块内加一层批量块：只在 lod === 0 时可见
const rects = z.cards.map(c =>
  `<rect x="${c.x - z.x}" y="${c.y - z.y}" width="${c.w}" height="${c.h}" rx="2"
     fill="${z.color}" fill-opacity=".16" stroke="${z.color}" stroke-opacity=".28" stroke-width=".6"/>`).join('')
```

实测依据：737 个 rect 只占一个绘制层，`layout 1.6–2.5ms`，DOM 卡片 0。**成本几乎为零，信息量差别很大。**

配套一条：某域开始挂 DOM 卡片（>4 张）后，把它的 SVG 层关掉，否则两套视觉并存：

```css
.ks-zone.ks-zone--mounted .ks-bulk { opacity: 0 }
```

### ② 卡片文字的可读性判据要用**屏幕像素**（**建议核查**）

现在 LOD 是全局档（`data-lod`），同一档里所有卡一个样式。但**同一张卡在不同缩放下的可读性不同**：

| 实测 | 值 |
| --- | --- |
| linux 域卡片世界尺寸 | 98 × 61 px |
| 68% 缩放后屏幕尺寸 | **61 × 38 px** |
| 135% 缩放后屏幕尺寸 | 132 × 82 px |

61×38 的卡塞 12.5px 字号两行标题 → 挤成一团；132×82 才读得舒服。

建议改成**按卡片**判定（我在原型里用的是这套）：

| tier | 触发（屏幕像素） | 显示 |
| --- | --- | --- |
| micro | 宽 <44 或 高 <22 | 只有色条 |
| title | 44 – 124 | 2 行标题（11.5px） |
| full | ≥124 且高 ≥80 | 标题 + 摘要 + 类型 chip |

### ③ 网格选列数要评"填充率"，不只看宽高比（**建议核查**）

`useSpaceLayout.js` 里如果只按宽高比选列数，会出现"卡片很瘦/很胖且域内下半截空着"。我在原型上踩过这个坑，最后用的评分是：

```js
score = Math.abs(cw / ch - 1.5) + Math.abs((cols * rows - n) / n) * 1.5   // 列数 1..20 枚举取最小
```

实测结果（737 条真实数据，每块面积占比与 `√n/Σ√n` **完全一致**）：

| 域 | n | 域尺寸 | 列数 | 卡尺寸 |
| --- | --- | --- | --- | --- |
| linux | 225 | 1042×1553 | 10 | 98×61 |
| network | 195 | 970×1553 | 9 | 101×64 |
| web-lamp | 104 | 2012×547 | 18 | 106×80 |
| nginx | 14 | 1171×345 | 7 | 160×150 |
| centos | 1 | 417×258 | 1 | 397×218 |

## 3. 一个已经确认没问题的点

我原型的第一个 bug 是卡片色条用了 `class="bar"`，**撞上页面顶栏的 `.bar`**（顶栏有 `height:54px; padding:0 14px`），导致色条变成占卡片 1/4 宽的色块。

实装里用的是 `.ks-zone-bar` / `.ks-card-*` 全前缀命名，已经避开了这类污染。**这条不用改，写在这里是为了让后来的人别再犯。**

---

## 4. 两边的数字不能混着比

| 指标 | `PERF.md`（实装） | `APPLIED.md`（原型实测） | 说明 |
| --- | --- | --- | --- |
| L0 首屏 | 128ms（含构建产物加载） | 无异步资源，一次 `applyCamera` | 量的是不同起点 |
| 域跳转 | 162ms（k 0.28→0.61） | 未量 | 可以互相对拍 |
| 布局计算 | 未单独记录 | **1.6–2.5ms**（10 域 + 737 卡） | 建议实装也打这个点 |
| DOM 卡片 | `mountedCards` 有读数 | 0 / 200 / 53–153（按档） | 建议把 L0 的 SVG 块数也显示出来 |
| chunk 体积 | 22.48 kB / gzip 8.54 kB | 数据 152 KB（内联 JSON） | 实装按需 import 更好 |

**建议**：在实装的状态行里补两个数——`bulk ${rects}` 与 `layout ${ms}ms`，这样两套实现的性能可以直接对拍。

---

## 5. 如果只改一处

**改 ①（L0 密度肌理）。** 它不影响性能预算，却直接把"知识库有多大"从数字变成视觉；其余两条是打磨。
